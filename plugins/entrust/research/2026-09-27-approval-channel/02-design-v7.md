## 1. `experimentalApi: true`

`initializeParams` (`:162-176`) sends `capabilities.experimentalApi: false`. It becomes `true`, and the report carries `experimentalApi: true` beside `codexVersion`. What the flag is: "Opt into receiving experimental API methods and fields" (0.155.1 `ClientRequest.json:1588-1591`, level 1). What it exposes on 0.155.1 beyond `additionalPermissions`, from the generated schema's markers (level 1): `request_user_input` as a server request with its questions and options (`ServerRequest.json:1749-1896`, "EXPERIMENTAL"), app-list metadata and its change notification, proposed-plan streaming deltas, the thread-realtime family (audio chunks, transcript deltas, WebRTC SDP, realtime items), the approval auto-review notifications (`item/autoApprovalReview/*`, "[UNSTABLE]", only under the `auto_review` reviewer the driver refuses), and a thread's path on disk. What that does to the driver: a `request_user_input` server request lands in `handleServerRequest`'s last branch, a JSON-RPC error and an `interactions` entry (`:3283-3286`), which is the classification it already has when it arrives as an `agentMessage` with questions (`:3344-3349`) and the right one, exit 7; every experimental notification is a method `handleMessage` does not name and drops, and `item/plan/delta` is already in `optOutNotificationMethods` (`:171-174`); realtime never starts without a realtime session. What the driver already reads that is marked unstable: `grantRoot` on a file-change request (`ServerRequest.json:615`, "[UNSTABLE]"), copied into the request record and acted on by nothing. Drift check: the fidelity differential compares the real server's `thread/start` answer to the fake's key by key, so a field the flag adds to the response shows there as a note before it reaches anything (the `diffItemKeys` notes, `fidelity.test.mjs`, level 1 that the comparison exists).

## 2. The widening carried by a command approval

The entry for `item/commandExecution/requestApproval` gains `permissions`: null for an escape, and for a request whose params carry `additionalPermissions`, that object copied (`fileSystem.entries`, `write`, `network`). Level 3 for the shape: Q10b's approval carried `additionalPermissions: {fileSystem: {write: ["/tmp"], entries: [{path: {type: "path", path: "/tmp"}, access: "write"}]}}` and `availableDecisions: ["accept", "cancel"]`. Neither field is in the generated schema, even with `generate-json-schema` on 0.155.1 (grep, level 1), so the record is from the wire and the fixture reproduces the wire.

Offer and display: the same predicate as the escape kind (root's current turn or a grandchild's open turn, kind `command`), `cause: "sandbox"`, and `--pending` prints, after the `COMMAND<<`/`COMMAND>>` block, one `ACCESS=<access> <type>:<value>` per entry and `NETWORK=`, exactly as for a permissions request, so the coordinator reads both the command and what it would gain. The v6 protected-root filter applies to these entries too: an added path at or inside `~/.codex`, the state directory, or their ancestors, the home itself, or `special: root`, is declined at once with `why: "protected root"`.

The rule: a command approval with `ACCESS=` lines is a widening, and the widening sentences apply: prefer it to an escape, approve a tool's own state or cache under the home when the path is not a repository, `~/.codex` or the state directory, never a network addition the plan did not name. `--decide --accept` sends `{decision: "accept"}`, the one accept shape for this method; the command then runs under Seatbelt with the paths added (Q10b: `nested=71`, the file appeared). `sandboxWidened` gains `{itemId, permissions, scope: "command", at}`, `scope: "command"` being a reading: `with_additional_permissions` is set per call, and whether the grant outlives the command was not measured, where a permissions-request grant at `scope: "turn"` measurably does (Q7e). The synthesis names it as any widening.

An approval without `additionalPermissions` stays the escape kind: offered, accepted with `accept`, run with no Seatbelt (Q2), recorded with `permissions: null`. Under the softened steering clause a true escape can still arrive; whether it does under the features was not exercised (P1: the model obeyed the hard clause in both turns), and the offer path is the same either way.

## 3. Declining

### A permissions request the coordinator declines

The driver sends the empty profile `{permissions: {fileSystem: null, network: null}}`, today's refusal and the only decline the response shape has (v6). P1 Q10a and Q10b: the model then re-issues the same command with `sandbox_permissions "with_additional_permissions"` for the same paths, which arrives as a command approval. Two shapes were weighed:

- **Two decisions for one need**: offer the re-ask; the coordinator sees the same paths again and declines again. Honest, and one declined need costs two hand-backs, the second being the first restated.
- **The coordinator's decision applied once per turn**, chosen: when a command approval's `additionalPermissions` entries all lie within the entries of a permissions request the coordinator declined in the same turn (same thread, path-for-path after the same resolution `coveredByRights` uses), the driver declines it at once, `offered: false, by: "driver", why: "the coordinator declined these paths at <id>"`, and sends `decline`. The entry is in the report, named against the first decision, so nothing is hidden; the driver adds no policy, it repeats the coordinator's answer to the question it already answered. A re-ask naming any path outside the declined set is offered, with `REPEAT_OF=<id>` in its `--pending` block so the coordinator sees the earlier decision. The declined set is kept per turn and cleared with the turn's other per-turn state at `turn/completed`.

A coordinator that declines a widening and later wants the tool to run has the escape: the model, under the softened clause, may ask to run outside the sandbox when the path is refused, and that request is offered as an escape and decided on its own.

### `--decide --decline` on a command approval

Sends `{decision: "decline"}`, whatever `availableDecisions` lists. `availableDecisions` for the widening kind is `["accept", "cancel"]` (Q10a, Q10b) and for the escape kind it never lists `decline` either (E47, P1 Q1 flag), yet `decline` was honoured on the escape kind in 27 production runs (00-escalations, coordinator's note) and the two kinds share one method and one decision enum (`CommandExecutionApprovalDecision`, pinned `ServerRequest.json:265-343`), so the server parses it. Whether it treats it as a refusal on the widening kind is level 2 until measured, and the measurement is named below. `cancel` is not sent: the schema says it "denies the command; the turn will also be immediately interrupted" (level 2), and a coordinator's no to one path is not a stop; the coordinator's stop is Stop on the card or `kill -TERM`, which cut the turn and write the report.

## 4. The steering clause

The measured text (v6) ends "Never request to run outside the sandbox (never use require_escalated)." A tool whose need no path can express, `ps` on another process, a nested sandbox, a socket, then fails and is reported, and the coordinator never sees an escape it could have approved. The last sentence becomes: "Ask to run outside the sandbox only when no path would make the command succeed." What is given up: the text is no longer the one measured verbatim (n=1); what must be measured, one Terra turn on P1's toy tool with the softened clause: the model still asks for the path first and does not escalate; and a second turn on a command with no path to ask for (P1's `ps -o lstart= -p 1` shape): the model asks for the escape. Until both are run, the softened text is a reading that the clause's first half carries the effect.

## 5. The keeper, and the launch-only form

W1's `--run` launches the driver under a detached `/bin/sh` keeper (`KEEPER`, `agent-run.mjs:245`; `launch`, `:274-286`) that owns the output files and writes `exit` after the driver ends, so the run outlives the launcher call that hands a request back; `--run`'s wait forwards `SIGTERM`, `SIGINT` and `SIGHUP` to the driver's pid from `err.txt`, holding one that arrives before the pid line exists (`:521-540`). Consequence W1 names: a hard kill of the wrapper's process group, or a `SIGKILL` of the launcher, reaches the keeper's group no longer; only the forwarded signals do (E45's path, level 3 for launcher to driver). A hard-killed wrapper leaves the driver running to its end or to the constant.

Acceptable, for three reasons. The hand-back requires it: a call that returns with a request must leave the run alive, and a driver in the launcher's group would die with the call under any group kill. The ordinary stops are the forwarded signals: Stop on the card and the session's end reach the driver as `SIGTERM` through the launcher (measured 2026-09-12 for Stop; E45 for the session's end), and the driver settles open requests, cuts the turn and publishes. And the run is bounded without a caller: the constant declines an unanswered request after thirty minutes, `--idle-timeout` and `--max-commands` bound the turn as for any agent, and the report lands in the run directory whoever reads it. What is given up: a `SIGKILL` of the launcher, which nothing in the pages sends, orphans a driver for at most the run's own bounds; and an approved command the driver was running is F10's residual as before.

The page: the codex page's stop bullet (`SKILL.md:311`) gains W1's usage sentence, "after a waiting result nothing holds the driver: to stop it, `--decide … --decline` and run the same `--run` again, or `kill -TERM` the pid on the first line of `<DIR>/err.txt`"; the orchestrate page's exit-10 row already says to answer the holder's request first.

The launch-only form, `agent-run.mjs --report-file REPORT` with no `--run`, hands the driver no mailbox (`:275`), so every request is declined at once as before the channel. Confirmed: its one caller is swarm (`swarm.mjs:135-140`: `--new`, the launch, `--status`), which runs agents nobody attends; a mailbox there would hold each request thirty minutes before the same decline, and the shape, not a flag, decides it.

## Suites and gates that move

Fixture: `widening-command` (a command approval carrying `additionalPermissions` for a file under the fixture's home, `availableDecisions: ["accept", "cancel"]`; `accept` completes it exit 0; `decline` completes it `declined`), `widening-declined-reask` (a permissions request, then, after the empty profile, the same paths as a command approval), `widening-reask-other` (the re-ask names one path more). Protocol: `initialize` carries `experimentalApi: true` and the report records it; a command approval with `additionalPermissions` is offered with `permissions` set and `cause: "sandbox"`; its accept sends `accept` and `sandboxWidened` records `scope: "command"`; a re-ask within declined paths is declined by the driver with `why` naming the first decision; a re-ask beyond them is offered; `--decide --decline` on either command kind sends `decline`. Launcher: `--pending` prints `ACCESS=` after the command block and `REPEAT_OF=` where set; `--run`'s keeper writes `exit` with `128 + signal` for a killed driver; a `SIGTERM` to a continued `--run` reaches the driver. Fidelity: the differential notes any key `experimentalApi` adds to `thread/start`. Live gates: v6's toy-tool gate run twice, once accepting the permissions request, once declining it and then deciding the command approval that follows; the softened-clause turns above.
