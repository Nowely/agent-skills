# 2026-09-27/28: live approval of a Codex agent's escalations by the coordinator

**Question.** What does a Codex agent's approval request do today, and how should the plugin change so that the orchestrator approves an agent's action itself when the plan covers it?

**Result, 0.20.0 as found.** The driver declines every request and records it; the turn goes on and the user hears afterwards. Of 914 reports on the owner's machine, 27 carry exit 6 with 37 declined requests ([00-escalations.md](00-escalations.md)): 13 `vcs` reads that fail inside the sandbox, 10 file changes that were writes into the agent's own `$TMPDIR` through Codex's edit tool (which asks by path spelling: `/private/var/…` asks, `/var/…` does not), and 14 others. Measured on codex 0.155.1 across five probe rounds ([01-probe.md](01-probe.md) to [01-probe-5.md](01-probe-5.md)): `accept` re-runs a command with no sandbox at all; the server waits for a decision without bound; a JSON-RPC error is a rejection; closing stdin on a pending request aborts the turn; with Codex's default features the model has no tool to ask for paths and never does, and with `features.request_permissions_tool` and `features.exec_permission_approvals` on it asks for the exact file a tool needs, a turn-scoped grant lets the command run inside the sandbox with that path added, and declining such a request is not a refusal because the model re-asks through a command approval; `decline` on an escape is honoured though unadvertised. `vcs` fails because its client opens its object store read-write; the grant that makes it work was measured under `codex sandbox` only, every app-server run granting Codex write into `~/.vcs/store` having been refused by the harness's classifier.

**Design**, seven iterations ([02-design-v4.md](02-design-v4.md) the first implemented shape, [02-design-v7.md](02-design-v7.md) the last; Codex Astra's critique of v2 in [03-critique-astra.md](03-critique-astra.md); the owner's principles in [06-owner-round.md](06-owner-round.md) and [15-owner-round-2.md](15-owner-round-2.md)): a mailbox for every agent inside its directory in the state directory, no flag; the driver answers yes itself to a file change whose resolved paths lie inside the agent's writable roots; every other request from the root or a child thread, an escape, a file change outside the roots or a widening for named paths, waits for the coordinator up to a 30-minute constant; `--run` hands a waiting request back through the unchanged wrapper message, the coordinator decides with `--decide` and continues the wrapper; the coordinator approves what is non-destructive and in the plan's direction, prefers a widening to an escape, and takes the rest to the owner while the turn waits; every entry carries a cause, the report shows what the sandbox gained, and the synthesis says why approvals were needed. Nothing in the driver names a tool. The 37 historical requests under the rule: 10 auto-yes, 24 approve, 3 to the owner, 0 decline.

**Implementation**, two rounds in this worktree: v4 (Opus W1, Sonnet W2; reviewed by Codex Sol R1 and Codex Astra C2, 13 findings fixed and verified by Codex Sol R2, [10](10-review-sol.md)–[12](12-verify-sol.md)), then v5–v7 after the owner's rules (reviewed by Codex Sol R3, [17-review-sol-2.md](17-review-sol-2.md), 3 findings fixed with mutation checks). Five live gates passed end to end ([09-live-gate.md](09-live-gate.md), [16-live-gates-2.md](16-live-gates-2.md)): an escape approved through the launcher and through a real Haiku wrapper's hand-back, the driver's own yes to a `$TMPDIR` write, and two widenings for a toy tool's state files with the command still under Seatbelt; one wrapper continuation was refused by the harness's classifier and finished by hand.
