## 1. Имя, место, форма страницы

`prepare-feedback`, `/entrust:prepare-feedback`, entrust; строки в README terse нет (решения владельца, 03).

**Страница.** `disable-model-invocation: true`, `metadata.version` — версия плагина. Первая строка: «Команда `/entrust:prepare-feedback`, которую набрал пользователь, — явный запуск режима orchestrate для этого прогона. Прочитай `${CLAUDE_SKILL_DIR}/../orchestrate/SKILL.md` целиком инструментом Read и действуй по нему; для батчей извлечения так же прочитай `${CLAUDE_SKILL_DIR}/../swarm/SKILL.md`; ни ту, ни другую через Skill tool не загружай. В прочитанном тексте `${CLAUDE_SKILL_DIR}` — каталог той страницы». `${CLAUDE_PLUGIN_DATA}` страница даёт явно (подставляется только в теле навыка). Та же первая фраза — в брифе foreman'а. Дальше действует orchestrate с ветки: карточка плана, композиция, капы, обёртка и опрос, одобрения, пять полей, runner, линтер, критик с манифестом (ветка добавила в манифест ledger и логи runner'а); codex загружается Skill tool, когда в плане есть Codex-агент. Страница держит только своё: меню (§2), корпус (§3), два способа чтения и что им нужно сверх страниц (§4), отчёт как публикацию и worktree (§5), приватную папку и рецензента (§6). Детали — `references/focuses.md`; один скрипт `scripts/prepare-feedback.mjs` (команды в `F1-split-04.md`). Тело — до 5 000 токенов.

## 3. Отбор сессий и область

**События — из разобранного JSON транскрипта**, не из сырых строк:

- загрузка навыка — запись `user` с `isMeta`, чей текстовый блок начинается с `Base directory for this skill: <путь>`; плагин и версия — из пути (`…/cache/nowely/<plugin>/<version>/skills/<skill>` или `…/plugins/<plugin>/plugin/skills/<skill>` для checkout, версия `unknown`);
- отказ загрузки — `tool_result` с `is_error` и текстом `cannot be used with Skill tool due to disable-model-invocation`; имя навыка — из текста, отбор по плагину; для `version` это находка, не сигнал области;
- прогон prepare-feedback — загрузка его собственной страницы; такие сессии, текущая в том числе, — отдельной строкой плана, исключены; «включи их» — `--session` с их id;
- запуск Codex — строка `REPORT=<путь>` в транскрипте; до неё — `threadId` и `receiptPath`; отчёт по пути, rollout по `threadId` под `~/.codex/sessions/`, `unknown`, когда нет обоих;
- субагенты — `<session-id>/subagents/agent-*.jsonl`.

Метод воспроизведён (`O1-count2.mjs`, разбор JSON): у O1 днём — entrust 38 загрузок (26 из кеша, 12 из checkout), terse 9 (8 и 1), 12 настоящих отказов в 11 сессиях (6 `entrust:orchestrate`, 4 `codex-delegate:orchestrate`, 2 чужого навыка); мой повтор вечером того же дня — 40 (28/12), 11 (10/1), отказы те же; сырой grep даёт на 3 файла больше у terse, и все три — цитаты. Числа плывут с каждой сессией, поэтому страница называет метод, а числа показывает план.

**Скрипт** `prepare-feedback.mjs corpus` пишет индекс в приватную папку (§6): T-id ↔ сессия ↔ проект по `cwd`, даты, версии, события, счёты (сообщения, символы, токены по `usage`, субагенты, запуски), склейка форков (одинаковые ходы и метки времени — одна задача); `parts` режет на части ~60k символов с перекрытием и страницы ≤ 18k — только для извлечения. Сводка ≤ 20 строк через runner.

**Область по фокусу и план.** `version` — все проекты, версии из слов; `run` — сессия по дате или id и её запуски; `feedback` — сессии с загрузкой плагина и вторая строка «все сессии с человеческими сообщениями: N». План перечисляет проекты по `cwd` как область, показывает строку «N сессий из checkout, версия неизвестна», строку прошлых прогонов навыка, предупреждение о хранении (30 дней по умолчанию) и малом корпусе. Ограничения — словами; «go» покрывает показанное.

## 4. Два способа чтения против страниц ветки

**Правила ветки `entrust-issue22-pages`, которые навык берёт по ссылке** (свои не пишет): bulk-ряд — `EFFORT: high` для извлечения, классификации и проверки, если пилот не выбрал иного, `low` только для механики; пилот перед любым bulk-фан-аутом — сильная модель размечает несколько единиц, bulk-модель проходит те же, recall, лишние и токены решают правки брифа и эффорт; оценка bulk-ряда по единице и снова после пилота; стоп-линия плана — 3× медианы токенов пилота на агента, агент выше неё останавливает дальнейшие запуски до новой оценки (триггер 2× прогноза ветка не взяла — и навык тоже); батч bulk-ряда — swarm под капом параллельности с одним Stop; каждый путь вывода в `TASK:` — под корнями записи агента; манифест критика несёт ledger и логи runner'а.

**Что навыку нужно сверх этих страниц** — названо на странице явно, страницы не правятся:

1. Старт swarm-батчей: страницы говорят, что swarm запускает только пользователь набранным `/entrust:swarm` (E90). У prepare-feedback план перечисляет батчи с их числом, и «go» пользователя — их старт; страница swarm читается по пути (§1), `swarm.mjs` вызывается по своему пути.
2. Единица извлечения: у swarm единица — утверждение с адресом, цитатой и вердиктом (E90: часть корпуса — не та форма). У prepare-feedback единица батча извлечения — часть корпуса: `{{UNIT}}` — путь части, закрытые метки и дословные цитаты в возврате; единица swarm'а остаётся для stress-теста.
3. Регистрация: id агентов swarm `001…050` план не принимает, и `--new` под зарегистрированным планом их отказывает (E90). Каждый батч — свой каталог прогона без `plan.txt`; в карточке батчи стоят строками текста «N батчей по ≤ 50 Luna», не строками лаунчера.
4. Роли: регистрация плана считает роль по словам `implement|writ|worker|build|fix` и `critic|verif|review|refut|judge|check|test|advis` и отказывает 12 из 22 имён roles.md (E89). Колонка роли в строке плана несёт имя из roles.md и слово, по которому лаунчер её считает: `strong reader, checks`, `measurer, checks`, `page dry run, checks`. Всё-Claude план регистрацию пропускает.
5. Токены батча: сводка swarm'а токенов не несёт (E90). `prepare-feedback.mjs tokens` читает `tokenUsage` отчётов батча, считает медиану и агентов выше стоп-линии; покрытие страниц по rollout-логам — `prepare-feedback.mjs coverage`; ни того, ни другого на страницах нет.

**Читатели по вопросу** (`version`, `run`). Один сильный читатель на задачу или сессию; критик разбиения перед фан-аутом шире одного; foreman при трёх и больше (в его брифе — фраза §1); партия — не больше шести живых; после каждой партии `tokens` по отчётам партии, медиана — первой партии, стоп-линия — 3× неё; замерщик-скрипт там, где есть числа; для entrust — аудитор Codex-запусков по отчётам; для `version` — page dry run (roles.md) и два blind proposer'а для таблицы предложений; dedup-and-rank при нескольких читателях; один опровергатель на кластер; черновик по раскладке эталона; один свежий сильный читатель с обоими брифами (полнота и публикация). Судья — там, где его держал эталон: у #16 два, у #15 ни одного. Платный повтор (контроль #1) — строка плана с ценой, по слову.

**Исчерпывающее извлечение** (`feedback`; любой закрытый фокус по многим сессиям). Корпус keep/drop, `parts` → критик разбиения на бриф и метки → пилот по протоколу, записанному до пилота (правило ветки; эталон размечает сильный ряд) → пересчёт по единице, план снова, остановка → батчи `swarm.mjs` по странице swarm, каждому свой каталог, `--concurrency` — число ядер с #21/#22 как причиной в плане → редуктор по странице swarm (не разобравшиеся и ненулевые возвраты, число эпизодов по единице) → `coverage` и перезапуск непрочитанного → слияние (сильный) и `quotes` → два независимых анализа → черновик (верхний ряд) → stress-тест swarm'ом (единица — принцип × эпизод, форма swarm'а) и контрпримеры по частям → судья (один, как #20) → сравнение с прошлым прогоном, если есть → критик полноты и рецензент публикации, два агента. `tokens` после каждого батча; идущий батч доходит до конца.

## 5. Выход

**Место решает:** корень `git rev-parse --show-toplevel` с `.claude-plugin/marketplace.json`, `"name": "nowely"` — внутри; иначе снаружи. Первая строка навыка называет выбор.

**Отчёт — публикация, не ответ.** Тело — файл в приватной папке; критик полноты читает его по манифесту (roles.md: публикация читается так же); линтер проходит только короткий ответ. После строки критика — заголовок и тело одним блоком, названным в манифесте; внешний fence длиннее любого внутреннего (четыре обратные кавычки). Навык ничего не публикует.

**Внутри репозитория.** Первый шаг, до плана: EnterWorktree под `.claude/worktrees/prepare-feedback-<slug>` (ветка `entrust-prepare-feedback-<slug>`), чтобы каталог прогона orchestrate (слаг из рабочего каталога) и research-папка были одного дерева. После вердикта критика: `prepare-feedback.mjs export --run <приватная папка> --to plugins/<name>/research/<date>-<slug>` — относительный путь; экспорт кладёт серию черновиков `01-report.md`, `02-report.md`…, `rounds.md` и `measures/`; координатор пишет строку в `plugins/<name>/research/README.md` инструментом Write и коммитит на ветке одной темой без вопроса; push, PR и merge — по слову. Команды на странице — без heredoc'ов в node, без абсолютных путей: изолированная worktree-сессия такие отказывает. `<name>` — плагин, о котором отчёт. Возвраты шагов остаются в приватной папке; `anonymized/` — только если отчёт на него ссылается.

**Формат** — раскладка эталона фокуса (`focuses.md`): `version` — #15 (`Recurring` против `CHANGELOG.md` плагина; линза ролей — #16), `run` — #1 или #22, `feedback` — #20; заголовки по образцам эталонов. Адреса — `T3:282` (задача : строка JSONL), `T3.s2:198` (субагент), `run:<id>`; карта T-id — в индексе приватной папки.

## 6. Приватность

Принцип CLAUDE.md:24–26 и комментария к #21, без списка. Приватная папка `<state>/prepare-feedback/<date>-<slug>/` под `${CLAUDE_PLUGIN_DATA}`, по образцу `experiments/`; пишет её один скрипт (`corpus`, `parts`, `add`, `coverage`, `quotes`, `tokens`), читает `export`. Транскрипты читают агенты, координатор — возвраты и сводки. Рецензент публикации — сильная модель, которая текст не писала, проверяет каждую деталь выходящего файла по двум вопросам: опубликовал бы это владелец на главной странице, и склеивается ли с уже публичным (прошлые issues, README research-папок; без GitHub — с самим отчётом); список снятого идёт пользователю с текстом. Внутри репозитория та же проверка перед `export`.
