## 2. Два расхождения: одна команда

Скрипт `O1-count2.mjs` разбирает каждый главный транскрипт как JSON. Загрузкой он считает только запись `user` с
`isMeta`, чей текстовый блок начинается с `Base directory for this skill:`: такова форма настоящей загрузки
(`skill-load-record-shape`). Отказом — только `tool_result` с `is_error` и текстом отказа. Метка запуска —
`refusals-by-skill`, `EXIT=0`:

    main_transcripts=223
    entrust: loaded_any_path=38 cache=26 checkout_or_other=12 raw_grep_files=38 grep_match_but_no_real_load=0
    terse: loaded_any_path=9 cache=8 checkout_or_other=1 raw_grep_files=12 grep_match_but_no_real_load=3
    refusal: files_with_text_anywhere=17 files_with_real_refusal=11 real_refusal_results=12
    refused_by_skill={"mattpocock-skills:grill-me":2,"codex-delegate:orchestrate":4,"entrust:orchestrate":6}

- **Кеш: верно «26 и 8» (§3).** В claims-02 №5 «26 и 12» неверно для terse: 12 — это число загрузок entrust из
  checkout. Попутно оказалось, что и §3 ошибается: у terse 9 настоящих загрузок, а не 10. Правило из claims-02 даёт 10,
  потому что считает строку, где маркер процитирован. Сырой grep даёт 12, из них 3 файла — только цитаты.
- **Отказы: верно «6» для `entrust:orchestrate`.** Всего настоящих отказов 12 в 11 сессиях. Кроме наших 6, это 4 отказа
  `codex-delegate:orchestrate` (прежнее имя плагина) и 2 — чужого навыка. «16 сессий» в claims-02 №6 (сегодня уже 17) —
  это файлы, где текст отказа просто встречается, включая сессии, которые его цитируют, в том числе работу над этим
  проектом.

## 3. Новые находки, по убыванию важности

### 1. Первая строка страницы воспроизводит закрытый для модели навык в обход — это E82, только без оправдания foreman'а (§1, «Форма страницы»)

- **Что не так.** Страница велит прочитать `orchestrate/SKILL.md` инструментом Read и действовать по нему. Пользователь
  при этом набрал `/entrust:prepare-feedback`, а не `/entrust:orchestrate`.
- **Почему, уровень 1 (текст host'а в транскриптах, метка `refusal-full-text`).** При отказе host говорит модели:
  «Ask the user to run /entrust:orchestrate themselves — it cannot be invoked via the Skill tool. Do not replicate this
  skill's workflow by other means — it is reserved for explicit user invocation.» У E82 (ISSUES.md:410–419) смягчение
  есть: пользователь запустил orchestrate и одобрил план с foreman'ом. Здесь пользователь orchestrate не запускал,
  поэтому смягчение не работает.
- **Как это ломается.** Модель, увидев на странице «действуй по orchestrate», вызывает Skill tool, получает этот текст и
  встаёт перед выбором между страницей и host'ом. Это уже случалось: в #15 F1 advisor после такого отказа остановился и
  попросил пользователя набрать `/entrust:orchestrate` и «go». На этой машине 6 отказов orchestrate и 4 отказа прежнего
  `codex-delegate:orchestrate`.
- **Предложение.** Первая строка говорит прямо: «команда `/entrust:prepare-feedback`, набранная пользователем, и есть
  явный запуск режима orchestrate для этого прогона; прочитай его страницу по пути, orchestrate через Skill tool не
  загружай». Та же фраза в брифе foreman'а закрывает E82, как предлагает сама запись.
- **Альтернатива** — крупнее. Тело orchestrate переезжает в обычный файл `orchestrate/references/`, и обе точки входа,
  orchestrate и prepare-feedback, читают его. Закрытый для модели SKILL.md тогда никто в обход не воспроизводит.
- **Проверка.** Снимет ли фраза конфликт — гипотеза. Проверяет её один живой прогон, а это платно и только по слову
  владельца.

### 2. Решение владельца о правилах bulk-ряда из #22 не отражено, а правка всё ещё спорит со страницами (§4)

- **Что не так.**
  - Шапка: правила «ложатся в orchestrate и swarm вместе с навыком».
  - §4: «здесь не переписаны… prepare-feedback ссылается на страницы, какие они есть».
  - Сам §4 при этом меняет правила этих страниц:
    - эффорт выбирает пилот, а swarm:17 и orchestrate:77 говорят «`low` for Luna»;
    - единица — путь части, а swarm:17 и orchestrate:69 определяют её как «one claim, one address, a verbatim quote,
      and a verdict»;
    - редуктор считает сбои, а swarm:29 говорит «tallies the verdicts by unit».
- **Почему.** Проект противоречит своей шапке и страницам entrust — это #15 F12/M1.
- **Предложение.** §4 перечисляет правки страниц, которые идут в том же изменении:
  - orchestrate:77 и swarm:17 — эффорт bulk-ряда выбирает пилот; дефолт `medium` для извлечения, классификации и
    проверки, `low` — только для механики (#22 п. 1);
  - swarm:17 и orchestrate:69 — рядом с «claim» определяется единица извлечения: часть корпуса, закрытые метки,
    дословные цитаты;
  - swarm:29 — работа редуктора в swarm'е извлечения;
  - дефолт `--concurrency` в swarm.mjs — по числу ядер, плюс строка брифа о повторе пустого чтения (#22 п. 2);
  - раздел Verification в orchestrate — пилот против эталона перед bulk-фан-аутом (#22 п. 7);
  - оценка по частям и правило остановки 3×/2× (#22 п. 5);
  - роль dry run — в roles.md (находка 11).

  Датчик токенов (`tokens`) и, по желанию, покрытие (`coverage`) тогда живут в swarm: они нужны любому bulk-чтению. У
  `prepare-feedback.mjs` остаются `corpus`, `add` и `quotes`.

### 3. Решение владельца о worktree не отражено, и у записи в дерево нет механизма (§5, «Внутри»)

- **Что не так.** §5 оставляет выбор «живое дерево без коммита или worktree» пользователю. Владелец решил: прогон
  внутри репозитория идёт в worktree, файлы там коммитятся без вопроса. Скрипт при этом пишет только приватную папку
  (`corpus`, `add`), а в `plugins/<name>/research/` не пишет никто.
- **Почему, уровень 1.**
  - Запись в проектный `.claude/` спрашивает, что бы ни говорили правила разрешений (orchestrate:28–29). Worktree
    владельца — `.claude/worktrees/<slug>` (заметка памяти `feedback-worktree-means-commit`).
  - Слаг каталога прогона orchestrate берётся из рабочего каталога (orchestrate:27). Если войти в worktree посреди
    прогона, отчёты агентов разъедутся по двум слагам.
- **Предложение.** Порядок: вердикт критика → EnterWorktree (штатно) → `prepare-feedback.mjs export` с относительным
  путём `plugins/<name>/research/<date>-<slug>/` (как `export` у `experiment.mjs`: серия черновиков, `rounds.md`,
  замеры, на которые ссылается отчёт, строка индекса) → коммит на ветке одной темой без вопроса. Push, PR и merge —
  по слову. Команды на странице без heredoc'ов в node и без абсолютных путей с «Git»: в изолированной worktree-сессии
  harness такие отказывает (та же заметка памяти). Строку §5 «решает пользователь словами» убрать.

### 4. Отбор считает цитаты маркеров как события (§3)

- **Что не так.** Загрузки, отказы и сессии самого навыка ищутся текстом по сырым строкам транскрипта.
- **Почему, уровень 3 (раздел 2).**
  - terse: 12 файлов по grep, 9 настоящих загрузок.
  - Отказы: 17 файлов с текстом, 11 с настоящим отказом.
  - Маркер `/entrust:prepare-feedback` в тексте поймает и сессии, где проект этого навыка обсуждается (эта работа
    — одна из них), и исключит их как прогоны навыка.
  - Отказ `mattpocock-skills:grill-me` попадёт в находки `version` о entrust.
- **Предложение.** Скрипт разбирает JSON:
  - загрузка — запись `user` с `isMeta`, текст начинается с `Base directory for this skill:`;
  - отказ — `tool_result` с `is_error`, имя навыка берётся из текста и фильтруется по плагину;
  - прогон prepare-feedback — загрузка его страницы, а не текст команды.

  В §3 исправить числа: 38 и 9; 26 и 8 из кеша; 12 отказов в 11 сессиях, из них 6 — `entrust:orchestrate` и 4 —
  `codex-delegate:orchestrate`.

### 5. При чтении по вопросу правило остановки по стоимости не действует (§4)

- **Что не так.** Остановка привязана к медиане пилота, а пилот есть только у извлечения.
- **Почему.** Дефолтный `version` при чтении по вопросу — это один сильный читатель на задачу. На машине 38 сессий с
  entrust, у #15 было 10 читателей на 29,5M (issue-15.md:414). Перерасходы у читателей были: в #15 F5 Codex-читатель
  потратил 855 530 токенов после решающего совпадения, в #22 п. 5 факт — 38,7M при плане 25–30M.
- **Предложение.** Та же проверка после каждой партии читателей. Партия — не больше шести живых (orchestrate:98), это
  естественная граница. Медиана считается по первой партии. Новых механизмов не нужно.

### 6. §8 держит судей у #16, а §4 и §0 судей в чтении по вопросу убрали

- **Что не так.** Строка #16: «два судьи по меткам (эталон держал двух)». §4: «Судьи нет: ранжирует координатор, как в
  #15». §0, строка 14: «судья — только в исчерпывающем извлечении».
- **Предложение.** Одно правило: «судья — там, где его держал эталон фокуса». Это #16 (два, source-auditing) и #20
  (один). Для `version` без линзы судьи нет.

### 7. Для эпохи codex-delegate, а значит и для #1, `REPORT=` запусков не находит (§3, §8, строка #1)

- **Почему, уровень 3 (метка `old-driver-report-lines`).** 54 транскрипта упоминают `.codex-delegate/`, и лишь в одном
  из них есть `REPORT=`. `receiptPath` встречается в 62. Каталога `~/.codex-delegate` на машине нет. rollout-логи
  начала сентября есть (`~/.codex/sessions/2026/09/01…`).
- **Предложение.** Запуск искать по `REPORT=`, а до entrust — по `threadId` и `receiptPath` в строках транскрипта. Если
  отчёта нет, брать rollout по `threadId`. `unknown` — только когда нет обоих. Строку #1 в §8 поправить: замеры #1
  восстанавливаются из rollout-логов, отчётов нет.

### 8. Версия загрузок из checkout на этой машине всегда `unknown` (§3)

- **Почему, уровень 3.** Оба каталога checkout, из которых шли 12 загрузок entrust, удалены. Правило «из манифеста по
  этому пути, если он ещё есть» даёт `unknown` для всех 12, а это как раз сессии, где владелец проверял релиз.
- **Предложение.** Ничего не строить. Строка плана: «12 сессий из checkout, версия неизвестна — включить?», решает
  пользователь словами.

### 9. Тело issue одним Markdown-блоком рвётся на вложенном fence (§5)

- **Почему, уровень 1.** Тело issue может содержать fenced-блок (он есть в теле #21). Внешний блок из трёх обратных
  кавычек закроется на первом внутреннем, и пользователь скопирует половину тела.
- **Предложение.** Одна фраза: внешний fence длиннее любого внутреннего (четыре обратные кавычки или `~~~`).

### 10. `sub:` публикует сырые id агентов харнесса (§5, «Формат»)

- **Что не так.** Нотация #15 — `sub:agent-ae868c8b1a4ef2389`, а это такой же стабильный id, как id сессии, которые
  проект заменил на `T#`, чтобы отчёты не склеивались между собой.
- **Предложение.** Субагенты — в той же карте, что и задачи (`T3.s2`); карта лежит в приватной папке.

### 11. Роль dry run описана в `focuses.md`, а не в roles.md (§4)

- **Почему.** orchestrate:102: roles.md определяет каждую роль, «a new one is named the same way».
- **Предложение.** Раз правила bulk-ряда всё равно ложатся в orchestrate (находка 2), dry run — строкой в roles.md.

## Что в правке хорошо и должно остаться

- Два способа чтения вместо ступеней. Фокус `run`. Формат задаёт эталон. Один скрипт. Отчёт — публикация в
  манифесте. Приватность — принцип и рецензент по каждой детали.
- `REPORT=` вместо договорённости о каталогах. Эффорт выбирает пилот. У каждого батча свой каталог.
- Таблица §0 с одной причиной на решение. Пересчитанные утверждения L002–L020.
