# Report data

Read this contract for every review. Save one canonical `review.json` after semantic analysis and refutation; HTML is optional. [Lifecycle and verification](#lifecycle-and-verification) apply before returning the review; [Visual evidence](#visual-evidence) applies to material visual questions.

## Format

    {
      "title": "a short name of the change", "language": "en",
      "range": "main...HEAD", "map_mode": "focused",
      "change": { "goal": "what the change is for, in a sentence", "why": "the reason, when a source gives one",
                  "parts": ["what it adds or alters, one line each"], "sources": ["the task text", "the commits"] },
      "verdict": "whether the change does its task\n- what decides that, a line each",
      "now": "the solution as written",
      "target": "the cleanest solution, by the design standard",
      "recommendation": "accept, fix in place or rewrite as the target, in a sentence",
      "steps": [{ "text": "what to do first", "findings": [1] }, { "text": "what to do next", "findings": [2] }],
      "requirements": [{ "id": 1, "text": "...", "source": "task" },
                       { "id": 2, "text": "...", "source": "discussion", "met": "read", "not_checked": "how it looks on screen",
                         "doubt": "what contradicts it" }],
      "findings": [{ "id": 1, "title": "what is wrong", "direction": "behavior", "evidence": "read",
                     "at": "path:line", "what": "...", "shown_by": "the caller at path:line", "fix": "...", "breaks": [1] },
                   { "id": 3, "title": "the import cannot take a rule without its writes", "direction": "design", "evidence": "judgment",
                     "at": "path:line", "what": "...", "shown_by": "scenario 1", "fix": "...", "scenarios": [1] },
                   { "id": 2, "title": "what no test would catch", "direction": "tests", "evidence": "read",
                     "at": "path:line", "what": "...", "shown_by": "the regression that passes", "fix": "...", "untested": [2] }],
      "checks": [{ "from": "the state to start from", "do": ["the first step", "the next"], "expect": "what a person sees",
                   "requirements": [2] }],
      "ideas": [{ "title": "the idea", "at": "path:line", "text": "what it gains and what it costs" }],
      "screens": [{ "name": "the screen and its state", "mockup": "https://...", "before": "before.png", "after": "after.png",
                    "differences": [{ "what": "how the result differs from the mockup", "why": "the reason given" },
                                    { "what": "a difference nothing explains", "finding": 1 }],
                    "missing": "what you could not compare, and the picture that would settle it" },
                  { "name": "a screen whose result is the mockup", "mockup": "mockup.png", "after": "after.png", "match": true }],
      "scenarios": [{ "id": 1, "change": "rows from a blocked domain are rejected with a reason", "requirements": [2],
                      "now": { "edit": ["src/import.js: importContacts, the loop"], "read": ["src/import.js: the counters and the writes in that loop"] },
                      "target": { "edit": ["src/import.js: planImport"], "read": [] } },
                    { "id": 2, "change": "the store's write takes a second argument", "now": { "edit": ["src/import.js:40"] } }],
      "units": [{ "name": "importContacts", "jobs": ["parses", "validates", "writes"], "uses": ["ContactStore"],
                  "verdict": "split", "findings": [3], "reason": "a rule cannot change without reading the writes around it" },
                { "name": "ContactStore", "existing": true, "jobs": ["keeps the contacts"] }],
      "mechanisms": [{ "name": "bounded import retries", "change": "added", "units": ["importContacts"],
                       "purpose": "retry transient writes", "basis": "task requirement 1",
                       "instead": "the shared writer retries already: src/store.js:40",
                       "benefit": "survive transient failures; frequency unknown", "cost": "duplicate retry state, latency and tests",
                       "decision": "remove local retries; retain the shared writer policy", "evidence": "judgment", "findings": [1] }],
      "target_units": [{ "name": "importContacts", "jobs": ["reads the rows", "applies the plan"],
                         "uses": ["planImport", "ContactStore"] },
                       { "name": "planImport", "jobs": ["decides what each row does"] },
                       { "name": "ContactStore", "existing": true, "jobs": ["keeps the contacts"] }],
      "blocks": [{ "path": "src/a.js", "added": "1-2, 10-16", "removed": "7", "unit": "importContacts",
                   "does": "...", "serves": [1], "verdict": "remove", "findings": [1] }],
      "questions": [{ "at": "path:line", "text": "what is unexplained, and what would settle it" }],
      "coverage": "what you read and could not check, and the contracts with where you read each",
      "labels": { "findings": "the report's own word, in the user's language" }
    }

Each field holds what the same part of the report holds, and these rules are checked:

- **Map mode.** The reviewer writes `map_mode: "focused"` by default, and `complete` only on explicit request. The field distinguishes intentional selective mapping from accidental missing ownership; omission in old JSON still means legacy `complete`, not the author's default. Complete requires exactly one owner for every nonblank changed line. Focused permits unowned lines and an empty `blocks` array, but never overlapping blocks or invalid references/dispositions. Unowned means **no decision in the line map**, neither `keep` nor automatically unread. The same full semantic analysis, all four directions and refutation precede either mode; actual unread scope stays in `coverage`.
- **Semantic record.** The canonical JSON retains compact, source-backed decisions and reasons for the changed parts examined, including kept parts and refuted candidates. Put a part's rules, required job and rationale in `units.jobs`/unit `reason`, mechanism `basis`/`decision`, `coverage`, or its finding; refer rather than duplicate. Group parts sharing a rationale. For example, record which producer guarantee justifies keeping a guard or refutes a suspected defect, not just “validated” or a unit name. Preserve unknown premises and actual unread scope. This is a checkable semantic account without mandatory per-line ownership, a second file or new fields; the script cannot prove its truth or completeness.
- **Requirements.** `source` says where the requirement comes from: `task`, the task as given; `discussion`, a decision made while the work was discussed; `question`, a point the discussion left open; `assumption`, yours or the author's. `met` says how you know the change meets it: `ran`, you executed it and saw the result, or `read`, you followed the code and did not run it. Leave it out for a requirement you did not check or that a finding breaks. `text` holds the requirement and nothing about your checking: a part of it you did not check, such as how it looks on screen, goes in `not_checked`. `doubt` is for a requirement you would not take as given: say what in the code or in a contract contradicts it, so that whoever decided it can decide again.
- **Verdict, now, target.** Each is a text of a few lines; a line that starts with `- ` is drawn as an item of a list.
- **Steps.** What to do, in order, a short line each, with the findings it settles. Leave the list out when the recommendation is one thing. Do not restate a finding: name it by its number.
- **Findings.** `direction` is one of `behavior`, `necessity`, `design`, `tests`; `evidence` one of `ran`, `read`, `judgment`. `shown_by` is the report's "Shown by" line, and a candidate with nothing to put there goes to `questions`. `breaks` lists the requirements the finding shows unmet. A finding about tests breaks none: it lists under `untested` the requirements a regression of which no test would catch. Leave either out when it is empty.
- **Checks.** The report's "Check by hand": `from`, the state to start from; `do`, the steps; `expect`, what a person sees; `requirements`, what it shows. Leave the list out when the report has no such section.
- **Ideas.** `title` and `text`; `at` when the idea has a place. Leave the list out when there are none.
- **Screens.** Optional, when a requested or material visual question needs image evidence; otherwise omit the section, even for a visible change. Follow [Visual evidence](#visual-evidence). `mockup`, `before` and `after` are each a supplied or authorized-scope picture: a file, by its path from the data's directory, which the page takes in whole, or an `https` link, which stays a link. A difference has `what`, and `why` or the `finding` it is. `"match": true` says you compared the result with the mockup and found no difference: it needs both pictures. A screen with no difference and no match was not compared, and says in `missing` what would settle it.
- **Blocks.** Always an array. `added` and `removed` list changed lines in one file as numbers and ranges; a decision spanning files is one block per file. Mapped blocks are disjoint in both modes. In focused, every stated number must be positive and present on that changed side of the diff; reversed ranges, nonexistent lines and unchanged context lines are errors. `"all"` names every such line of the file, and only a block to remove may use it: code that stays is listed by its lines. `serves` lists recorded requirement links; absence alone establishes neither unnecessary code nor missing implementation. `verdict` is `keep`, `fix` or `remove`, and a block to fix or remove names its findings. `unit` names the unit the block is part of; leave it out for a test or a line outside any unit.
- **Scenarios.** The changes of the task you walked through the code, written before the target as [the design standard](design-standard.md#scenarios) says: `id`, `change`, the `requirements` it varies, and `now` with `edit`, the places you would edit (at least one), and `read`, the code you would read to make the change safely. `target` holds the same for the target; leave it out where the target leaves those places as they are. A place is `path: function` or `path:lines`. Scenarios are optional; use them when a grounded concrete change helps explain the design. A finding can reference them through `scenarios`. The checker validates references and shape, not the merit of the tradeoff; counts of places alone do not decide it.
- **Units.** Every changed unit retains `jobs` (including rules and precedence), the units it `uses`, a `reason` even when kept, and a `verdict` of `keep`, `fix`, `split`, `merge` or `remove`, with findings unless kept: `fix` stays one unit and changes inside. Complete requires at least one block per changed unit. In focused, a changed unit without a block instead requires `at: "path:line"` or `path:start-end`, naming a changed file with positive, forward line numbers. The default addresses the new version, or the old version if the new one has no lines (including deleted-only files). Use `old:path:line` or `old:path:start-end` explicitly for removed code in a surviving file. Every supplied changed-unit `at` is checked in focused, including units with blocks. This address is not line ownership. Block-derived requirement links may be partial; describe required behavior in jobs and requirement evidence rather than inferring absence. `"existing": true` marks untouched connected code, never changed code omitted from the line map.
- **Target units.** The same for the target, when it differs. A name that is also a unit of the change is carried over; a name that is neither that nor existing is to be written. A unit to split has what it splits into here.
- **Mechanisms.** A compact inventory of meaningful behaviors/coordination concepts, not a count of functions. Each has `name`, `change` (`added`, `reused`, `changed`, `removed` relative to the base), `units` referring to the current map when applicable (empty or omitted for a file/config-level mechanism; cite its location in `basis`), `purpose`, `basis`, `benefit`, `cost`, `decision`, and `evidence` (`ran`, `read`, `judgment`); optional `findings` links relevant findings (omit or `[]` when none). Cite requirements and contracts in `basis`; their definitions stay in the existing map. A mechanism that is `added` or `changed` also has `instead`: where what it obtains or does is already available, with the `path:line` you read, or the places you read that do not supply it. It is answered from the code and the installed contracts, not from the change's own reason, and the check refuses an answer that cites no `path:line`. `decision` is the proposed disposition, distinct from what the diff currently does. Group one lifecycle as one mechanism even if it spans several units. Explain the cost dimensions that actually apply, and say what is unknown instead of inventing numbers. Use `judgment` for maintenance tradeoffs. Supply `mechanisms: []` when none are material. Legacy reports may omit the field.
- **Mechanism weight.** The reviewer may set `mechanism.blocks` to unique 1-based indices of existing `blocks` (the B numbers shown in the report). The renderer cannot infer attribution from unit membership: one unit can contain several mechanisms. Every referenced block needs explicit `kind: "code" | "test" | "other"`; `kind` is optional elsewhere and never inferred from a path or unit. This prevents test/config/generated lines being silently charged as production code. Attribute a block only when all its included lines reasonably belong to the mechanism, exclusively or as shared work. If a composite block mixes unrelated work, split it at a meaningful boundary or omit the attribution as unassessed. Shared imports must not be charged to one mechanism alone. Do not fragment code purely for a precise-looking count.
  - Omit `blocks` when attribution is unavailable and explain why in `basis` or `cost`. This is unassessed, not zero. `blocks: []` is allowed only for `reused` without changed integration lines. When focused leaves nonblank changed lines unmapped, nonempty attributions show only their mapped footprint, with total weight unknown; empty attribution remains unassessed rather than a verified zero. An unmapped line's mechanism cannot be inferred from its unit.
  - Counts are derived from the referenced nonblank diff lines, including comments, with additions/removals and code/test/other separate. No duplicated numeric totals in JSON, net-delta weight, AST analysis or score. Existing helpers are not charged as newly added code. Blocks referenced by several mechanisms are shared, displayed separately with their names, never divided arbitrarily or added to each mechanism's exclusive total. Counts are exact for the chosen mapping; attribution remains a review judgment that the checker cannot validate semantically and does not establish that every counted line can be deleted.
  - `benefit` states the scenario, observable loss without the mechanism, and frequency with its grounds or explicitly unknown; do not invent numbers. `cost` explains relevant lifecycle/coupling/reading and change burden, not just a defect or line count. `instead` supplies existing capabilities and checked boundaries; `decision` weighs the evidence. For a material mechanism whose necessity is unresolved, describe in `decision` a simpler alternative without it: what triggers the remaining behavior, its inputs, what is lost and what is unknown, or why no alternative is established. Record a material unresolved owner decision in `questions` or `ideas`; a provisional recommendation is not an owner decision. Record uncertainty about whether the mechanism works separately. Behavior established by the task, discussion or contract stays binding; omission from the task alone does not mandate removal. Do not ask about every minor convenience. Unknown frequency alone does not prevent removing a proven duplicate while preserving the contract, and does not justify dropping required behavior. No new field is needed.
- **Language and labels.** The reviewer sets `language` to the session language code because the renderer cannot infer the reader's language from mixed code and prose. Built-in `en` and `ru`, including regional forms such as `en-US` and `ru-RU`, cover controls, annotations and exports; omitted language preserves legacy English. `labels` overrides built-in strings. Other languages need a complete dictionary; new `focused.*` entries are required only for focused reports (weight entries only with mechanisms), preserving old custom catalogs for complete reports. `node "<skill-dir>/scripts/report.mjs" labels [en|ru]` prints a catalog. Preserve `{n}`. Write content in the session language; keys, enums, paths and code stay unchanged.

Do not persist derived totals or unmapped ranges in JSON. `check(review, files, directory)` and `modelOf(review, files, owner, directory)` keep their signatures; focused adds derived `unmapped` entries with `path`, `added`/`removed` line arrays, `size` and `where`, excluding blanks. The model also exposes `focused: true`. Requirement links, failures and test gaps are derived from explicit references, never from missing map entries. The checker cannot detect semantically false attribution.

The line map covers parsed text hunks, not binary or mode-only changes, other diff metadata or EOF markers. Focused rendering additionally shows the full raw `git diff --binary --no-color --no-ext-diff` output for the same range, safely escaped/fenced in HTML/Markdown. Raw output is derived `model.rawDiff`, never a JSON field, mapped ownership or evidence that those changes were reviewed. The renderer propagates Git/256 MiB output-limit errors; it never substitutes an empty diff. Record the semantic review of non-text changes in the existing report fields.

Focused CLI checks get old/new source line counts from a full-context Git diff of the same range, preserving the displayed three-line context. This validates numeric bounds against the selected versions, not the current working file or whether the address actually names the claimed unit. Programmatic callers can supply `file.sourceLines: { old, new }` from `diffOf(range, { sourceBounds: true })`; with hunks alone, only fully present address ranges can be verified, and other addresses fail as unverifiable, not proven nonexistent. Source identity still needs the snapshot checks below; binary/non-text changes without parsed hunks have no verifiable line address.

Legacy/complete checks retain unowned-line errors and existing success stdout. Their pre-existing tolerance of extraneous block range numbers remains unchanged: passing complete validation does not establish that every stated number exists. Focused rejects such numbers and reports unmapped counts/addresses. A checker predating `map_mode` may reject a focused record; use this checker, not fabricated filler blocks.

## Lifecycle and verification

- Record immutable base/head revisions and diff identity in `change.sources` and `coverage`. For uncommitted inputs, preserve the exact diff and necessary source snapshot outside the project. Preserve referenced local images and their digests; identify HTTPS references as unarchived. Verify input identity before delayed rendering. A moving range alone is not a reproducible source.
- Finalize evidence and dispositions after refutation. Missing evidence stays unknown or in `not_checked`; empty findings/targets/mechanisms are valid. Writing artifacts is not permission to modify source or publish comments. If artifact writes are prohibited, return the complete JSON inline and name validation you could not run.
- Validate from the reviewed repository with `node "<skill-dir>/scripts/report.mjs" check /path/to/review.json`. This checks structure, references and changed-line ownership without writing HTML. Record what passed and what could not be checked. The reviewer chooses `check` when only data is requested: `render` would create an unrequested artifact.
- Read back the saved JSON itself. Check that examined changed parts retain their compact semantic decisions and reasons even without blocks. For each surviving finding, compare `now`, `target`, current/target unit jobs, mechanism decisions and recommendations. Resolve conflicting descriptions, orphaned state/effects after removal, and targets silently dropping a required rule. Check block descriptions and unit addresses against source; numeric validity does not establish semantic attribution. Verify the session language throughout. A passed script cannot prove natural-language consistency, truth or semantic completeness.
- Trace every required scenario and any recorded design scenarios through the final target, including relevant timing and failure behavior. An owner-approved omission is recorded with its consequence and source; a newly suggested tradeoff remains a question or idea until accepted. Recheck claims of missing information against the supplied contracts, utilities and UI/input paths. A prior report or scout is evidence to verify, not an authority to copy.
- For visible behavior, include manual scenarios only when the starting state, actions and expected result are grounded in the implementation. Name the requirements they exercise. These are proposals, not executed checks. Follow Visual evidence below for image work; keep missing visual verification out of requirement text.
- Derive the short response from this record. Later HTML uses the same JSON bytes and source snapshot, without new analysis. If new evidence changes a conclusion, save an explicit revised review and identify the change rather than presenting it as display-only work.

## Visual evidence

- Identify the concrete visual question before opening or comparing images. Use images already supplied or collected during the task first, checking their source revision, screen/state and relevant viewport. If identity or relevance cannot be established, mark that evidence uncertain rather than treating it as the current result.
- When comparing images, distinguish supported requirements, unexplained visual differences and unspecified states; a difference alone is not a defect. Inspect only the images/states needed for the question. A data-flow issue established from code does not require screenshots; do not build a visual comparison merely to populate a report. Omit `screens` when no material visual question remains.
- If visual evidence is necessary but missing, say which conclusion remains unchecked. New capture, app startup or broader visual coverage must fit the user's authorized scope; request a scope decision only when the needed work would expand it. Existing authorization is not asked for again. Do not generate illustrative images as evidence of application behavior.
- Preserve the existing report/image identities for delayed HTML rendering. Rendering uses the already established evidence; it does not start a new screenshot hunt or substantive review.
