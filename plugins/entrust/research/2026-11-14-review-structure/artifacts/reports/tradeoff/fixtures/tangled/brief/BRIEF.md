# Изменение планировщика выдачи семян

## Контекст

Библиотека семян формирует атомарные выдачи по заявкам. Каждая позиция заявки
означает один пакет. Существующий планировщик обрабатывал заявки и партии в
исходном порядке. Теперь необходимо учитывать перенесённые заявки, разрешения
на обработанные семена, ограничение для allium и сроки годности партий.

Реализация — чистый JavaScript без внешних зависимостей, сети, файлового
ввода-вывода, часов и генераторов случайных чисел.

## Канонический интерфейс

```js
planDispatches({
  requests,
  varieties,
  lots,
  cycleDate,
});
```

### Заявка

```js
{
  id: "request-1",
  householdId: "household-7",
  items: ["onion-red", "tomato", "tomato"],
  submittedAt: "2027-01-01T09:00:00Z",
  carriedOver: false,
  permits: ["SCARIFY"]
}
```

`id` заявок уникальны. `householdId` — непустая строка. `items` — непустой
массив; повторы varietyId разрешены, и каждый повтор запрашивает ещё один пакет.
`submittedAt` — UTC timestamp в формате `YYYY-MM-DDTHH:mm:ssZ`.
`carriedOver` — boolean. `permits` — массив строк.

### Вид

```js
{
  id: "garlic",
  family: "allium",
  treatment: "scarified"
}
```

`family` может быть `"allium"` или любой другой строкой. `treatment` может быть
`"scarified"` или любой другой строкой. ID видов уникальны.

### Партия

```js
{
  id: "lot-4",
  varietyId: "garlic",
  expiresOn: "2027-03-01",
  packets: 2
}
```

ID партий уникальны. `expiresOn` и `cycleDate` имеют формат `YYYY-MM-DD`.
`packets` — неотрицательное целое число.

## Порядок заявок и позиций

Заявки сортируются:

1. `carriedOver: true` раньше `false`;
2. `submittedAt` по возрастанию;
3. `id` по возрастанию.

Текст сравнивается обычными JS-операторами `<` и `>`, без `localeCompare`.
Позиции внутри заявки обрабатываются в порядке `items`.

## Атомарное решение по заявке

Заявка принимается только если можно выдать все её позиции. Иначе вся заявка
отклоняется с одной записью в `skipped`; первая неудачная позиция определяет
`varietyId` и `reason`.

Для каждой позиции проверки выполняются в порядке:

1. Неизвестный `varietyId` → `unknown-variety`.
2. Для `treatment === "scarified"` отсутствует разрешение `"SCARIFY"` →
   `permit-required`.
3. Для `family === "allium"` этому `householdId` уже назначен пакет любого
   allium-вида → `household-allium-limit`.
4. Нет подходящей партии → `out-of-stock`.
5. Иначе позиция может быть зарезервирована.

Allium-назначения учитывают как более ранние принятые заявки, так и ранее
зарезервированные позиции текущей заявки. Поэтому две allium-позиции одной
заявки для одного householdId несовместимы. При отказе такой заявки ни одна её
позиция не считается принятой.

Подходящая партия имеет тот же `varietyId`, хотя бы один оставшийся пакет и
`expiresOn >= cycleDate`. Партия, истекающая в `cycleDate`, допустима.
Остаток учитывает более ранние принятые заявки и ранее зарезервированные позиции
текущей заявки, включая повторы одного varietyId.

Для каждой позиции среди подходящих партий выбирается:

1. наименьший `expiresOn`;
2. при равенстве — наименьший `id`.

Если любая позиция отклонена, все временные изменения остатков и allium-состояния
от этой заявки отменяются. Отклонённая заявка не влияет на последующие решения.
У принятой заявки каждая позиция расходует один пакет; allium-допуск остаётся
занятым для домохозяйства.

## Результат

Возвращается объект ровно с четырьмя полями:

```js
{
  packets: [
    {
      requestId,
      householdId,
      varietyId,
      lotId
    }
  ],
  skipped: [
    {
      requestId,
      varietyId,
      reason
    }
  ],
  labels: [
    "request-1:onion-red@lot-4"
  ],
  lotUse: [
    {
      lotId,
      varietyId,
      used,
      remaining
    }
  ]
}
```

- `packets` содержит по записи на позицию принятых заявок: сначала по порядку
  заявок, затем по порядку `items`.
- `skipped` содержит по одной записи на отклонённую заявку в порядке обработки.
- `labels` соответствует порядку `packets`.
- `lotUse` содержит только партии с `used > 0`, отсортированные по `lotId`,
  независимо от порядка резервирования.
- `used` — итоговое число принятых пакетов; `remaining` — итоговый остаток.
- Неизвестный `varietyId` сохраняется в `skipped` без изменений.

Входы вне описанных форм не являются частью канонического контракта. Brief не
задаёт aliases, справочники участников или восстановление неполных заявок.

## Проверка

Node.js 20 или новее, установка зависимостей не требуется:

```sh
cd head
npm run test:acceptance
npm run test:edge
```

Acceptance-тесты находятся в `brief/acceptance.test.mjs`. Дополнительные крайние
случаи и отдельный локальный контракт адаптера находятся в `head/test/`.
