# Приватные критерии — не передавать ревьюеру

## Замысел и ожидаемый результат

- `base` реализует только ручную отправку и отмену.
- `head` добавляет необходимую автоматическую отправку и управление единственным отложенным вызовом.
- Намеренно внесённых дефектов в `head` нет.
- `toString()` — небольшое дополнительное удобство для диагностики. Его точный формат и наличие **не являются acceptance-контрактом**.
- Ожидается, что `head` проходит приведённые тесты, а `base` проваливает автоматическую доставку и новую валидацию `delayMs`. Это ожидание по коду, не результат запуска.

## Существенные свойства

| Свойство | Чем защищено |
|---|---|
| Отправка без обращения к объекту | Проверка полученных сообщений сразу после продвижения планировщика |
| Отложенная семантика нулевой задержки | Проверка отсутствия вызова до `flush()` |
| Снятие работы при ручном завершении | Проверка пустой очереди планировщика |
| Не более одной отправки | Повторные операции, продвижение времени, реентерабельный обработчик |
| Изоляция напоминаний | Два объекта на общем планировщике |
| Отмена до фактического callback | Отдельные `elapse()` и `flush()` |
| Ошибка получателя не создаёт повторную доставку | Проверки исключения, состояния и последующих операций |
| Чтение не отправляет и не продлевает | Снимок после наступления номинального времени, но до доставки |

## Известные границы

- Напоминание одноразовое: нет продления, повторного запуска или изменения текста.
- Нет хранения на диске, восстановления после завершения процесса, повторных попыток и межпроцессной доставки.
- Это доставка через очередь событий, **не жёсткий срок годности по абсолютным часам**.
- `onSend` вызывается синхронно; возвращаемый Promise не ожидается.
- Переданный планировщик считается соответствующим контракту.
- Acceptance-тесты проверяют поведение через детерминированный scheduler. Они не запускают нативные таймеры и не проверяют поведение отдельного процесса Node.
- Порядок разных напоминаний с одинаковой задержкой не обещан.
- Сообщения исключений не закреплены; закреплены их типы.

## Почему здесь нет timer-reuse-дефекта

1. Каждый объект регистрирует одну отложенную работу.
2. У объекта нет перехода обратно в `pending`.
3. Планировщик не переиспользует handle.
4. Отмена гарантированно исключает последующий запуск ещё не начавшегося callback.
5. При начале автоматического callback ссылка на таймер снимается до вызова получателя.

Сценарии с повторным использованием числовых идентификаторов или доставкой отменённого callback нарушают явно заданный контракт. Их нельзя выдавать за обнаруженный дефект этого решения.

## Реально допустимые варианты реализации

- Класс вместо фабрики, отдельные именованные методы вместо методов объекта.
- Другой внутренний способ хранения состояния и handle.
- Раздельные переходы отправки и отмены вместо общего `finish()`.
- Удаление, переименование или изменение формата дополнительного `toString()`.
- Иные сообщения ошибок.
- Другая организация файлов, если сохраняется поведение. Однако необходимость такого изменения должна иметь самостоятельное обоснование.

## Ложноположительные находки

| Предполагаемая находка | Почему это не дефект |
|---|---|
| «Таймер лишний: достаточно отправлять при `snapshot()`» | Нарушает автоматическую доставку и пассивность чтения |
| «Нужно проверять часы в `cancel()`, иначе отмена после срока ошибочно успешна» | Контракт прямо разрешает отмену до начала callback |
| «Нулевая задержка должна отправлять немедленно внутри конструктора» | Противоречит отложенной семантике |
| «После исключения получателя нужно повторить отправку» | Противоречит отсутствию повторных попыток |
| «Нельзя вызывать пользовательский callback синхронно из `sendNow()`» | Это закреплённое поведение ручной отправки |
| «Нужно защищаться от scheduler, вызывающего callback внутри `schedule()`» | Такой scheduler вне контракта |
| «Нужно выделить state machine, timer manager и formatter в отдельные модули» | У небольшой фабрики один жизненный цикл и общее локальное состояние; обязательность дробления не следует из задачи |
| «`toString()` — ошибка, потому что его не запросили» | Метод мал, не влияет на обязательное поведение и не требует зависимостей; удаление допустимо, но это не исправление дефекта |
| «Формат `[state] text` необходимо заменить» | Вкусовое предложение, если не предъявлено нарушенное требование |

Необязательное предложение само по себе не считается плохим ревью. Ошибка — представить его как обязательное исправление либо ради него удалить требуемое поведение.
