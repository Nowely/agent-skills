# Private review rubric

Этот файл не входит в материалы для ревьюера.

## Назначение и граница утверждений

Head предназначен для оценки design review при поведенчески корректном контракте.
Acceptance и дополнительные тесты проверяют текущее поведение, но не доказывают,
что выбранная структура единственно возможная или что изменение обязательно.

Нагрузка ниже описывается по наблюдаемым операциям кода. Не следует выдавать
гипотетические будущие ошибки за существующие функциональные дефекты.

## Наблюдаемая структурная нагрузка

Атомарность и allium-допуск реализованы через изменяемое состояние с откатом:

1. До обработки позиций сохраняется `hadAlliumBeforeRequest`.
2. Каждая успешно зарезервированная позиция сразу уменьшает `lot.remaining` и
   увеличивает `lot.used`, хотя исход всей заявки ещё неизвестен.
3. Allium-позиция сразу добавляет household в общий `alliumHouseholds`; последующие
   позиции той же заявки читают этот же Set в проверке отказа.
4. При любой ошибке остатки и счётчики восстанавливаются отдельным обратным
   проходом по `staged`, а Set отдельно восстанавливается через сохранённый flag.
5. `packets` и `labels` создаются только после завершения позиций, то есть запись
   выходных представлений отделена от уже выполненных изменений запасов.

Это конкретная нелокальность: для проверки инварианта «отклонённая заявка не
влияет на следующие решения» нужно совместно проследить поиск партии, две
операции с lot, условное добавление в Set, обратный проход и восстановление Set.
Для проверки FEFO при повторяющемся varietyId также необходимо учесть, что следующая
позиция видит уже уменьшенный остаток. Независимое вычисление позиций без учёта
этих provisional reservations не сохранит контракт.

Владение allium-правилом фактически разделено между тремя местами: проверкой
`has`, provisional `add` и восстановлением через `hadAlliumBeforeRequest`.
Владение остатком разделено между резервированием и rollback. Это основание для
design-замечания, а не утверждение о текущей ошибке.

### Почему решение может быть оставлено

Код напрямую выражает последовательное резервирование и использует один источник
остатков для всех позиций. При небольшом числе заявок такой transaction-style
подход может быть приемлем. Наличие rollback само по себе не доказывает чрезмерную
сложность; важны конкретные места синхронизации состояния.

### Альтернатива с сохранением всех эффектов

Можно сначала построить для заявки локальный список резерваций и локальные
дельты по партиям. При выборе очередной партии доступный остаток вычисляется как
общий `remaining` минус уже локально зарезервированное число для этой партии.
Локальный allium-flag учитывается вместе с Set ранее принятых заявок. После успешной
проверки всех позиций дельты применяются одним commit, а выходные записи создаются
из того же списка в исходном порядке. При отказе локальные данные просто не
применяются.

Это сохраняет:

- первый failing item и порядок причин;
- FEFO и влияние повторных позиций на остаток;
- конфликт двух allium-позиций одной заявки;
- отсутствие эффектов отклонённой заявки;
- порядок packets, labels, skipped и lotUse.

Допустим и другой вариант: сохранить rollback, но инкапсулировать все изменения
одного request в отдельной transaction-границе. Rubric не требует конкретных
функций, классов, имён или числа файлов.

## Необязательный механизм ручного ввода

`operatorAids` имеет отдельную локальную роль: преобразование ручных itemCodes и
member references до канонического планирования. Brief его не требует. README не
утверждает востребованность; этот вопрос должен решаться по реальным вызывающим
сценариям.

Границы теперь явно проверяемы:

- при отсутствии аргумента создаётся identity adapter, который возвращает тот же
  объект заявки;
- variety aids и member defaults не требуют друг друга; при этом создание адаптера
  всегда строит индекс видов, поэтому member-only конфигурация также может выявить
  collision канонических ID видов;
- member aids обязаны содержать householdId;
- после адаптации отсутствие householdId приводит к TypeError, а не к решению с
  `undefined` household;
- canonical `items` не проходят alias-подстановку;
- неизвестный itemCode сохраняется и получает обычный `unknown-variety`;
- alias/canonical и alias/alias конфликты отклоняются при настройке;
- неизвестный member reference является явной ошибкой адаптации.

Допустимо поставить вопрос о цене поддержки адаптера и его отдельном API. Нельзя
без проверки вызывающих мест называть его мёртвым кодом или требовать удаления.
Если он сохраняется, focused tests из `head/test/edge.test.js` фиксируют его
локальный контракт; дополнительные сценарии всё равно могут быть предложены.

## Что засчитывать как сильное ревью

- Ссылка на конкретные provisional mutations и rollback, с объяснением того,
  какой контрактный инвариант они поддерживают.
- Предложение уменьшить разделённое владение состоянием без потери атомарности,
  FEFO, порядка и allium-ограничения.
- Отдельный вопрос о необходимости operator aids и стоимости его самостоятельного
  контракта, без предположения о востребованности.
- Признание допустимости как локального staging/commit, так и аккуратно
  инкапсулированного rollback.

Отсутствие замечаний о производительности или о конкретном архитектурном шаблоне
не является пропуском.

## Уточнение о сортировке lotUse

Выражение `lotState.filter(...).sort(...)` сортирует новый массив, созданный
`filter`; порядок исходного массива `lotState` оно не меняет. Объекты партий в
новом массиве те же, но на этом этапе планирование уже завершено. Любое противное
утверждение является ложной находкой.

## Другие ложные находки

- Лексикографическое сравнение ISO-дат и UTC timestamps соответствует форматам
  контракта.
- `expiresOn === cycleDate` допустимо.
- Повторы в `items` разрешены; это не дубликаты, которые нужно отклонять.
- Две allium-позиции одной заявки действительно конфликтуют, но после rollback
  домохозяйство не сохраняет provisional допуск.
- Первый failing item определяет пропуск; не требуется глобальный приоритет всех
  причин по всем позициям.
- `lotUse` сортируется по lotId, а не по FEFO или порядку packets.
- Линейный поиск партии не является доказанной проблемой производительности без
  требований к объёму.
- Identity adapter при omitted aids не разрешает aliases и не подставляет member
  defaults; это соответствует заявленной границе.
- Ошибки некорректного partial aids конфигурирования документированы; тесты
  проверяют отсутствие householdId, unknown member и alias/canonical или
  alias/alias collisions, но не все ветки валидации: например, неверные типы
  operatorAids/member fields и collision канонических ID не покрыты.

## Чего не должно быть в ревью

- Выдуманного failing case, противоречащего контракту.
- Утверждения, что сам связный цикл или функция accept доказывают нагрузку.
- Подсказок, основанных на комментариях кода: преднамеренных комментариев о
  проектных решениях в head нет.
- Требования конкретной декомпозиции или безусловного удаления operator aids.
- Исправления поведения, которое уже явно покрыто acceptance и edge tests.
