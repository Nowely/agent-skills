### Сквозная сверка неожиданного наблюдения по `src/rule-cache.js:9-15` (во всех восьми отчётах)

Все восемь отчётов независимо выделили как находку №1 асинхронный зазор между отклонением промиса, возвращённого `loadRule(kind)`, и удалением обёртки из `requests` в `src/rule-cache.js:9-15`:

```js
const request = Promise.resolve()
  .then(() => loadRule(kind))
  .catch(error => {
    requests.delete(kind);
    throw error;
  });
```

Сверка с кодом, стандартом очереди микрозадач ECMAScript и `brief.md`:

1. **Механическая воспроизводимость трассировки — `supported`:**
   - **Вариант с синхронным `emit` (`review-04`, `review-05`, `review-06`, `review-07`):** на `src/intake.js:88` `emit({ type: 'crate.accepted', ... })` вызывается синхронно для ящика `A`. Если обработчик `emit` синхронно вызывает `reject(cause)` у отложенного промиса `loadRule(B)`, внутренний промис `B` немедленно переходит в состояние `rejected`, ставя реакцию в очередь микрозадач. После возврата из `emit` цикл `for` в том же синхронном стеке переходит к ящику `B` и вызывает `rules.load(B)` (`src/intake.js:61`) до выполнения `.catch(...)` (`src/rule-cache.js:11-14`), получает прежнюю обёртку `request` и завершает партию с `RULE_LOAD_FAILED`.
   - **Вариант с `queueMicrotask` между разрешением `A` и отклонением `B` (`review-01`, `review-02`):** когда `load('a')` и `load('b')` уже ожидают внешние `def_a.promise` и `def_b.promise`, вызов `def_a.resolve(...)` ставит в очередь выполнение `P_then_a` (тик 1), а `queueMicrotask(() => def_b.reject(cause))` исполняется на тике 2 — до возобновления `processShipment` на тике 5, но удаление `requests.delete('b')` в `.catch` выполняется только на тике 6. На тике 5 `rules.load('b')` возвращает старую обёртку и приводит к `RULE_LOAD_FAILED`.
   - **Вариант с ассимиляцией уже отклонённого промиса (`review-03`, `review-08`):** если `loadRule('a')` синхронно возвращает объект правила `{ maxKg: 10 }` (допустимо по `brief.md:9`), а первый вызов `loadRule('b')` возвращает `Promise.reject(cause)`, возврат промиса из колбэка `.then(() => loadRule('b'))` требует `PromiseResolveThenableJob` + `PromiseReactionJob` + `.catch`, поэтому `loadRule('b')` успевает вернуть уже `rejected` промис до продолжения `processShipment` после `A`, но `requests.delete('b')` срабатывает позже вызова `rules.load('b')`.
2. **Контрактная оценка относительно `brief.md:48,60` — неоднозначна (`unknown` как безусловный дефект спецификации, `supported` как расхождение с формулировкой `README.md:19` и риск граничного тайминга):**
   - `brief.md:60` формулирует правило мягко: *«A rejection that settled before acceptance began awaiting that attempt is not itself an intake failure and emits no intake event. The earlier attempt **may** be discarded; when a rule for that kind is subsequently awaited, a fresh attempt **may** be started and **may** succeed.»*
   - С одной стороны, если под `that attempt` понимать исходный промис `loadRule(kind)`, его отказ уже `settled` до `await rules.load(B)`, а `README.md:19` обещает без оговорок: *«A failed attempt is removed; a later on-demand load may retry. If acceptance is already awaiting that attempt, its rejection is reported as `RULE_LOAD_FAILED`.»*
   - С другой стороны, `brief.md:60` использует разрешительное **`may`** (*может* быть отброшена и *может* быть повторена, а сама фоновая ошибка не создаёт сбой/событие сама по себе), и в стандартном JavaScript у произвольного `Promise`, возвращённого `loadRule(kind)` (`brief.md:9`), нет синхронного API чтения `[[PromiseState]]` без микрозадачи (на это прямо указывают `review-04`, `review-05`, `review-07`).
   - Главное следствие для альтернативы: отказ от read-ahead устраняет это микрозадачное окно лишь потому, что **убирает предварительные попытки вообще** — в результате при любом transient отказе первой попытки `loadRule(B)` ленивая альтернатива **всегда** падает с `RULE_LOAD_FAILED` (включая основной сценарий `private/coordination.test.mjs:51-89`, где `head` успешно восстанавливается на повторном вызове). Ни один из восьми отчётов не отметил эту потерю автоматического recovery после уже завершившегося спекулятивного отказа.
