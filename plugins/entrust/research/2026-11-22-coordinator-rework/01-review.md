## 1. Вердикт

1. Страница не делает главного агента координатором «всегда»: раздел «Your own hands» прямо разрешает ему разведку и правки в своём контексте, а затем 2 000 знаков учит, как самому запускать проверки.
2. До первого агента координатор в Claude Code обязан прочитать около 39,5 тыс. знаков (≈10 тыс. токенов) в пяти файлах и выполнить не меньше шести служебных команд. Это прямой расход того контекста, который навык обещает беречь.
3. Чужие провайдеры втянуты по умолчанию в четырёх местах: обязательный опрос всех адаптеров при планировании и ещё раз перед запуском; правило «половина оценивающих агентов — Codex»; советник «другого семейства» по умолчанию; описание навыка `codex`, которое разрешает модели выбрать Codex самой.
4. 33 строки тела `SKILL.md` (3,5 тыс. знаков, 23 %) посвящены внешним исполнителям, прокси и адаптерам — в сессии только с родными агентами они не нужны.
5. Состав по умолчанию назван в трёх местах и по-разному: есть ли у простой задачи проверяющий, из страницы однозначно не следует.
6. Перед записью никто не критикует сам подход (в каком модуле жить изменению, что переиспользовать). `split critic` смотрит разбиение работы и запускается только при «нетривиальном разбиении»; остальные критики читают уже написанный код.
7. Главный агент называется тремя словами (`coordinator`, `parent orchestrator`, `parent`), а `foreman.md` зовёт «coordinator» субагента.
8. После компакции Claude Code заново прикладывает тело вызванного навыка, но не справочники. Сейчас это тело само разрешает работать руками, поэтому роль координатора не восстанавливается (раздел 4.6).
9. Механические проверки зелёные; переработка затронет закреплённые тестами места (рецепты `capture-check`/`lint-draft` и блок пяти полей в `SKILL.md`; запрет навыка с именем `coordinator`). Тесты я называю, но доводом «оставить как есть» не считаю.

## 4. Рекомендации по целям

### 4.1. Цель 1 — состав по умолчанию

- **A. Ничего не менять.** Простая задача уже «1 worker + completeness critic». Остаётся противоречие F7 и критик не того предмета.
- **B. Явный состав: исполнитель(и) + критик + проверяющий.** Критик читает план до первой записи (подход и, если есть, разбиение), и его же поток продолжается, чтобы прочитать замороженный черновик ответа против запроса. Проверяющий — свежий агент, который запускает проверки на итоговом дереве и не видит выводов исполнителя. Убирается: отдельный агент «completeness critic» из состава по умолчанию. Теряется обязанность: «свежесть» чтеца ответа (`answer.md:13` «One fresh strong-row reader») — критик уже видел план и может судить ответ по плану, а не по запросу. Разделы, всего 70–80 строк, 5,5–6,5 тыс. знаков:

2. **Команда** (≈12 строк). Таблица из трёх строк: исполнитель (по одному на владение файлами), критик, проверяющий — что делает, что может писать, что возвращает, уровень. Одна строка: «другая роль — когда план называет причину: `references/roles.md`».

5. **Проверка** (≈8 строк). Свежий агент, сырые артефакты; `unknown`, если решающая проверка не запустилась; не более двух кругов исправления.

Ссылки без пересказа: `references/external.md` — пользователь назвал другого провайдера; `references/roles.md` — нужна роль сверх трёх; `references/plan.md` — больше трёх исполнителей, bulk, пилот, профили; `references/foreman.md`; `references/approvals.md`; `references/results.md`; `references/answer.md`.

Команда по умолчанию: N исполнителей (обычно 1, уровень strong или cheap), 1 критик (strong; top — когда решение необратимо или меняет публичный интерфейс), 1 проверяющий (strong; cheap — когда проверка механическая).

### 4.5. Цель 5 — критик архитектуры

Различие с существующими ролями **[2]**:

| Роль | Предмет | Когда | Почему не то же |
|---|---|---|---|
| split critic (`roles.md:16`) | разбиение работы, распределение ролей и моделей, порядок | после одобрения, до брифов, при нетривиальном разбиении | не смотрит, где в коде жить изменению; при одном исполнителе не запускается |
| architect (`roles.md:17`) | создаёт дизайн | задача на дизайн | автор; не оценивает собственный дизайн |
| judge (`roles.md:31`) | вердикт по критерию среди кандидатов | конец раунда | нужен набор кандидатов |
| advisor (`roles.md:18-19`) | ответ на вопрос координатора | по вызову | отвечает на заданный вопрос, а не читает план целиком |
| cross-reviewer / направление design (`roles.md:24`, `review/references/agents.md:67-69`) | написанный diff против стандарта дизайна | после исполнителя | поздно: код уже написан |
| final reviewer (`roles.md:33`) | всё изменение перед посадкой | после кругов исправления | ещё позже |

Вывод: роль отличается временем (до первой записи) и предметом (намеченное решение в этой кодовой базе). Дубликатом она становится только рядом со split critic — оба читают один план в один момент.

Варианты:
- **A. Не вводить.** Подход проверяется постфактум ревью. Дёшево; ошибка размещения стоит круга переделки.
- **B. Расширить split critic до «критика плана»** с двумя предметами: подход (всегда) и разбиение (когда исполнителей больше одного). Один агент, одно чтение, число ролей не растёт. Переименование затрагивает живой тест (см. раздел 5).
- **C. Отдельная 23-я строка рядом со split critic.** Два агента читают один план; при одном исполнителе работает только новый.

Позиция рецензента: **B**; это и есть «критик» из состава 4.1.

Определение роли (для строки в `roles.md`):

- **Что делает.** До первой записи читает запрос, план и названные в нём места кода. Проверяет: какой модуль владеет изменением и почему он; что из нужного уже есть в коде или контрактах; какие новые понятия (механизм, флаг, слой, состояние) план вводит и какое требование их оправдывает; что будет затронуто у потребителей; есть ли более дешёвый вариант, включая «не делать». При нескольких исполнителях — ещё разбиение, порядок и общие интерфейсы. Меряет по `review/references/design-standard.md` (ссылкой, без пересказа).
- **Может писать.** Ничего.
- **Возвращает.** Пять полей; в `result` — вердикт `sound | change | stop` и не более пяти возражений по убыванию, каждое с `path:line` и наименьшей поправкой плана; в `open` — что не смог прочитать. План не переписывает.
- **Когда.** После одобрения карточки, до первого брифа исполнителю; один раз. Поправки, меняющие объём или состав, идут пользователю на одобрение (как сейчас у split critic, `SKILL.md:77-79`).
- **Уровень.** strong по умолчанию; top — когда план вводит новый модуль, публичный интерфейс или необратимое действие.

### 4.6. Контракт координатора, который переживает компакцию (ввод владельца 2b)

Наблюдение владельца: главной сессии приходится напоминать, что она координатор, и после компакции это теряется.

**Что известно.**

- `scripts/skills.test.mjs:243-256` **[1]**: после компакции Claude Code 2.1.280 заново прикладывает тело каждого вызванного навыка — целиком до 20 001 знака, иначе первые 19 900; на все приложенные навыки общий предел 25 000 токенов, «newest first». Это запись чтения исходников и сверки трёх блоков в одной сессии, сделанная автором теста; сам я это не воспроизводил.
- Файлы, прочитанные инструментом Read, заново не прикладываются (ввод владельца; в репозитории записи об этом я не нашёл). Значит, `plan.md`, `roles.md` и `answer.md` — 18,4 тыс. знаков обязательного чтения — после компакции пропадают.
- `claude/SKILL.md:82-84` **[1]**: навык с `disable-model-invocation` загружается инструментом Skill только в ходе, где пользователь набрал команду; «in any other turn, read its SKILL.md with the Read tool». То есть страница orchestrate, прочитанная по пути (бригадиром или в позднем ходе), не переживает компакцию **[2]**.
- В плагине нет хуков: `plugins/entrust/plugin/.claude-plugin/` содержит только `plugin.json` **[3]** (`ls`, `find -name "hooks*"`).
- Поведение Codex после компакции: **неизвестно**. В репозитории нашлось только имя настройки `compact-prompt` в `codex/references/why-not-the-plugin.md:93` **[1]**; что Codex делает со страницей навыка — не записано нигде.

**Почему роль теряется — гипотезы, ни одна не измерена.**

1. Страница сама разрешает работать руками (F2). Тогда повторно приложенный текст восстанавливает именно это разрешение, а не роль. Это единственная причина, которая видна прямо в тексте **[1]**.
2. Роль — одно предложение (`SKILL.md:12`) в странице на 15,8 тыс. знаков, 23 % которой про внешних исполнителей (F8).
3. Правила состава и ролей лежат в справочниках и после компакции исчезают.
4. Общий предел 25 000 токенов отдаёт место новым навыкам. Orchestrate вызывается первым, адаптеры и `review` — позже, поэтому он самый старый в очереди. Что происходит с самым старым при нехватке — обрезка или пропуск, — в тесте не записано; неизвестно.
5. Состояние прогона (одобренная карточка, живые агенты, их id) живёт только в разговоре и зависит от качества сводки.

**Что нужно контракту по существу.** Безусловная формулировка роли; место в первых строках тела вызванного навыка; маленькое тело, чтобы его не вытеснил общий предел; никаких обязательных для роли фактов в справочниках; строка «если одобренной карточки нет в контексте — не планируй заново, прочитай её по пути …» с записью карточки в файл при одобрении.

**Варианты.**

- **A. Оставить словами, как сейчас.** По опыту владельца не работает.
- **B. Перестроить `orchestrate`: первый экран — контракт, тело 5,5–6,5 тыс. знаков** (эскиз 4.4). Новых механизмов нет. Работает, пока навык вызван командой и хватает общего предела. Повторный набор `/entrust:orchestrate` посреди прогона должен означать «перечитай контракт и продолжай», а не новое планирование — это одна строка на странице.
- **C. Отдельный навык `coordinator`, тело — только контракт (1,5–2,5 тыс. знаков).** Плюсы: почти не зависит от общего предела; пользователь одним словом возвращает роль, и навык становится самым новым в очереди; годится без карточки плана. Минусы: второй вход; `orchestrate` не может загрузить его сам инструментом Skill, если навык только для пользователя (см. `claude/SKILL.md:82-84`), а чтение по пути не переживает компакцию. Остаются три способа, у каждого цена: пользователь набирает обе команды; навык вызывается моделью (тогда он может сработать без просьбы); контракт повторён в начале `orchestrate` и закреплён в `plugins/entrust/evals/fragments.mjs` как литерал — это копия, пусть и под проверкой.
- **D. Хук плагина `SessionStart` с источником `compact`, который печатает контракт.** Единственный вариант, не зависящий от того, что модель вспомнит. Но хук срабатывает в каждой сессии с плагином, поэтому ему нужен признак «режим включён» — файл состояния, который кто-то ставит и снимает. По правилу Flags (`AGENT.md:49-51`) такой признак рождается только с ответом «что ломается без него»; пока не измерено, что повторное приложение навыка не срабатывает, ответа нет. Что именно `SessionStart`/`PreCompact` добавляют в контекст в версии 2.1.280, я здесь не проверял — по памяти вывод `SessionStart` попадает в контекст, а `PreCompact` после сводки ничего не вставляет; это нужно подтвердить по документации или опыту. В Codex хуки плагина — неизвестно.
- **E. B + измерение, затем C или D по результату.**

**Позиция рецензента: E.** Сначала B: без безусловной формулировки и короткого тела ни отдельный навык, ни хук не помогут — они будут заново вставлять текст, который разрешает работать руками. Затем одно измерение уровня 3: сессия Claude Code с вызванным навыком, двумя-тремя другими большими навыками, `/compact`, и чтение транскрипта — что приложено заново и делегирует ли следующий ход. Если роль держится — C и D не нужны. Если страница вытеснена общим пределом — C (маленькое тело решает именно это). Если страница приложена, а модель всё равно работает сама — D, и тогда у признака «режим включён» появляется обоснование.

Если владелец хочет отдельный навык уже сейчас, не дожидаясь измерения, чистая форма такая: `coordinator` — единственный вход с контрактом и тройкой ролей (эскиз 4.4), а нынешний `orchestrate` перестаёт быть навыком и становится его справочниками для больших команд. Это тот же вариант A из 4.4 с другим именем команды; два навыка с общим назначением при этом не появляются.

Тесты: B — как в разделе 5; C — `orchestrate.test.mjs:75-80`, `package.test.mjs`, строка README, `agents/openai.yaml`, при копии контракта — новый фрагмент в `fragments.mjs`; D — новый файл хуков в пакете (`package.test.mjs` перечисляет состав) и тест самого хука.
