---
name: adaptive-frontend
description: Implement or change an interactive interface that adapts to available space. Use when matching several design frames, embedding a shared component in different hosts, or preserving a user action as the layout changes.
---

# Deliver one responsive user journey

**Choose the journey and its consumers.** Follow the existing public entry into the screens that use it. Identify which paths the request changes and which public behavior their callers rely on. A shared change needs checks in its affected consumers; broader redesign needs its own scope. Open a real story or consuming screen. Perform the user's primary action. Identify what the user needs to read, the feedback that indicates selection or progress, and the observable outcome of the action. Record a small baseline you can replay. Before coding, turn the design and the existing journey into a short acceptance contract: what must remain recognizable, what may change with context, and which observable outcome would send the work back. Use the same criteria on the first slice and at final review. If the request changes one step, the rest of this journey is the behavior to preserve.

**Read the design as a group.** Compare the same region across the supplied frames. Identify what stays together, what wraps or moves, which information becomes implicit, and where an action remains reachable. Check the actual containing element in the host and in the story. Record both its measured CSS width and the viewport. Follow the code that controls available space before choosing a breakpoint. A screenshot filename or a viewport preset cannot establish the component width.

**Resolve interaction gaps against a working screen.** Use the input contract to learn what data can occur and the existing consumer to learn what an action means. Perform the action in the closest working screen. Record what appears on the first gesture, the next step and the observable result so a reviewer can replay the same path. Trace the trigger, active state and state owner to the reusable code. When the design shows only the closed control, follow that interaction where it fits the consumer's contract. When the open state in the design changes the number of actions, the selection or the result, show the difference and its consequence before implementing it. If the sources still allow two materially different outcomes, show the owner what the user would see under each and ask only for that decision. Proceed on independent parts. Record the answer with the affected behavior. If a decision later changes, update the dependent paths and checks together.

**Build through the real entry point.** Match each materially different design state to inputs that actually render its visible content. Identify any depicted state the public API cannot produce. Separately keep one record unchanged for the whole action and resize sequence. Pick one valid variation where nearby regions compete for space, derived from the input contract or consumer examples. Render the public component with normal state, handlers, styles and theme. Start with the smallest change that delivers the whole journey. When a layout decision will be repeated across hosts, render one complete slice with real content first. Compare it against the intended visual and interaction criteria while changing the shared approach is still cheap. A story may supply data and a resizable host. Presentation belongs in the component that users receive.

**Close the browser loop.**

1. For a public local story, use a clean Playwright context. For a host requiring sign-in, use its configured persistent Playwright profile. Give that profile one owner at a time. If occupied, continue the public-story checks in isolation.
2. Compare each distinct design state using its matching inputs, measured content width, locale and scale. Look at reading order, alignment, typography, whitespace and the visual prominence of the action. Inspect the element whose geometry accounts for a discrepancy. Fix the material difference and repeat. Disclose unavoidable differences in the evidence.
3. In one **mounted** instance, enter the meaningful state, resize the parent through the change of layout and finish the action. Observe its user-visible result or the value delivered to the public callback. If a change moved stateful content to a new parent, run the closest existing behavior check. Replay the first gesture in the precedent and the implementation using the same input method. Compare the immediately visible options, next required action, and focus when it affects the journey. Choose a value different from the initial one, verify the observable result, and follow dismissal to its stable end state.
4. Use the variation where nearby regions compete for space. Keep its data and state fixed in the same mounted instance while varying the container through the supported range. Probe the width where the content is under pressure and capture that state. Check visible text, neighboring regions and reachability. After crossing layout modes in sequence, measure the document against the viewport and the affected content against its host. Verify any unexpected overflow in the browser. Resize the viewport as well if host behavior depends on it. Where a control owns scrolling or dragging, try the page gesture across it and the deliberate gesture inside it. Observe which surface moves, verify the intended action completes, and identify the evidence source (emulated layout, synthesized input or real device). A sweep can locate a suspect width; verify the actual content and action there.

**Decide whether the change is ready.** Revisit the acceptance contract. For every material requirement, identify an observation that proves it on the surface the user will actually receive. For a distributed component, exercise the built artifact through a real consuming entry. For an action nested in another interactive surface, verify both the intended result and the surrounding state that must remain unchanged. Run any missing check you can perform. If it fails, fix the cause and replay it. Declare readiness only when every material requirement is supported. If a required check is genuinely blocked, report partial completion, the blocker and what would resolve it.

**Hand off the proof.** Give the public route, representative inputs, measured width, matching visual evidence and observed action result. Point to the decisive checks for each affected consumer. Include material deviations and the reason for any unresolved checks.
