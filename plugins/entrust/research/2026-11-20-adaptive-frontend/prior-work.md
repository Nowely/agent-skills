# Prior work and independent opinions

The search question was whether an existing frontend skill already offered an end-to-end path from changes in an **existing** responsive interface to evidence that its public consumers still worked. The search was for primary instruction files with inspectable procedures. The studies did not measure these external packages, their popularity or installation success.

The external review also prompted a check of OpenAI's [task completion guidance](https://developers.openai.com/api/docs/guides/latest-model#task-completion) and [long-horizon completeness and verification guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4#force-completeness-on-long-horizon-tasks). They recommend checking whether the requested outcome has actually been achieved and continuing a feasible verification or repair. We adapted that idea to a UI delivery boundary: a packaged entry needs an actual consumer; a nested action needs the intended effect and the preservation of surrounding state. [Testing agent skills with evals](https://developers.openai.com/blog/eval-skills) also distinguishes outcome, process and efficiency goals. This informed the separation of tool activity, first-submission correctness and total time to acceptance. Documentation is a source of design ideas, not evidence that the resulting prompt improved these trials.

## Independent readings of v3

Kimi, GLM Flash and Qwen independently received the same v3 text and an anonymized description of the first three pilots. The public-skill shortlist and the other reviews were withheld. All three completed a review. These were editorial and engineering judgements on the supplied record. They did not implement a UI or run a controlled trial of v3.

| Reader | Specific concern | Decision |
|---|---|---|
| Kimi | “Material difference” leaves the implementer to decide whether a mismatch matters. Asked for an observable consequence, a repeat of the same check and a distinction between a successful story and an unavailable authenticated consumer. Suggested the project's existing browser harness for portability. | Kept measured container width, real entry points, separate per-state and resize fixtures, and concrete handoff evidence. Retained the owner's choice of clean Playwright for public stories and the configured profile for authenticated work. An unavailable host remains an explicit limit. |
| GLM Flash | A later reviewer might not be able to replay a loosely described baseline. The instruction to ask about ambiguity can be hard to apply in an unattended run. Suggested following the closest consumer and leaving the unresolved decision for handoff. | Adopted the emphasis on a reproducible observable result. A material product choice still belongs to the owner when sources support different outcomes. The agent can continue independent work. Earlier pilot failures cannot be attributed to the wording of an untested later version. |
| Qwen | A correct eventual callback can conceal an extra opening click or unwanted focus. A visual sweep of individual components can miss whole-document overflow triggered only by a transition. | Preserved the gesture and immediate state check in final verification, compared input/focus where it affects the journey, and used actual document and host measurements. A deliberately scrollable control must remain usable; a zero-overflow assertion everywhere would reject legitimate layouts. |

Two design choices follow from this record. The skill remains usable by one implementer. A coordinator can assign an independent replay when there is a concrete cost of propagating a wrong slice. The browser recommendation is tied to the surface being proved, so a clean story and an authenticated application need different treatment. Neither choice establishes that adding more instructions, validators or people will improve time to acceptance.
