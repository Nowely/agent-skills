## Change

Adds CSV contact import to the address book.

1. Reject rows with an empty name or invalid email, reporting line and reason without stopping.
2. Match email case- and space-insensitively; create or rename contacts. Count each email once per file, with the last row winning.
3. Return created and updated counts and rejected rows.
4. Write nothing if the file cannot be parsed.
5. Ignore blank lines.

Sources: `brief.md`; the reviewed commit adds `src/contacts/import.js` and `test/import.test.js`.

## Verdict

The import handles a basic file but fails the parse atomicity, address validation and duplicate-count requirements. It also silently drops some valid addresses and exposes a mode that stops on rejected rows.

Target: use the existing CSV parser to parse the entire file before writing, and the existing email validator and normalization. Validate rows, retain the last valid row per normalized email, then apply each retained contact once and return counts and rejections.

Recommendation: fix in place, starting with parsing before writes, duplicate counting and validation. Remove the unsupported modes and silent skips, then add tests for the required behavior.

## Findings

### 1. Malformed CSV can write contacts instead of failing atomically (behavior; traced)

`src/contacts/import.js:16`: Rows are written while the file is being parsed, and the parser never checks `inQuotes` at the end of a line. For `name,email\nAnn,ann@site.test\n"Bob,bob@site.test`, Ann is inserted and the unclosed quote is treated as a row instead of a parse failure. This breaks requirement 4.

Fix: call `parseCsv` on the whole text before any store operation; let its `CsvError` propagate.

### 2. Quoted multiline fields are split into separate rows (behavior; traced)

`src/contacts/import.js:13`: Splitting on `\n` before interpreting quotes breaks valid CSV such as `name,email\n"Ann\nSmith",ann@site.test\n`: neither physical line is imported as the intended contact. The existing parser supports quoted line breaks and records their starting line. This breaks requirements 1 and 2.

Fix: reuse `parseCsv` and its record line numbers.

### 3. Duplicate emails are counted more than once (behavior; traced)

`src/contacts/import.js:76`: A new email appearing twice increments both `created` and `updated`; an existing email appearing twice increments `updated` twice. The last name wins, but each email must count once under requirement 2.

Fix: collect valid rows by normalized email before writing, retaining the last valid row; apply and count each retained email once.

### 4. Import accepts addresses rejected by the address book (behavior; traced)

`src/contacts/import.js:1`: The local expression accepts `ann@site` and `a@b@c`, while `isEmail` in `src/contacts/email.js:1` rejects both. Such rows are inserted instead of being reported under requirement 1.

Fix: reuse `isEmail`.

### 5. Valid addresses at `example.invalid` disappear silently (behavior; traced)

`src/contacts/import.js:72`: `ann@example.invalid` passes the project’s email validator, but this branch neither imports nor rejects it. This breaks requirements 1–3.

Fix: remove the domain exception and its test.

### 6. Strict mode stops an import on a rejected row (behavior; traced)

`src/contacts/import.js:59`: With `{ mode: "strict" }`, an empty name throws instead of reporting the row and continuing. Earlier rows may already have been written. The same applies to invalid emails at line 66. This breaks requirement 1.

Fix: remove strict mode and always collect row rejections.

### 7. Insert failures are retried and then hidden (necessity; traced)

`src/contacts/import.js:83`: The supplied `ContactStore.insert` is synchronous and has no transient failure path; its explicit error is a duplicate, already checked immediately beforehand. Three identical attempts add no recovery for that store, and a thrown error is ultimately converted into an omitted row with no indication to the caller.

Fix: insert once and let errors propagate.

### 8. The importer adds an unused mode and result field (necessity; traced)

`src/contacts/import.js:5`: The semicolon `legacy` mode is not requested, and no existing caller uses it. `result.rows` at line 7 is likewise outside the requested result and has no consumer beyond the new test. These add another format and output contract to maintain without serving a requirement.

Fix: remove the mode and `rows` field, along with their tests.

### 9. Tests do not establish the required outcomes (tests; traced)

`test/import.test.js:6`: The main test checks counts and rejection length, but not the resulting contacts, rejection line or reason. It would pass if the existing contact were not renamed or the wrong row were reported. There are no importer tests for duplicate normalized emails, invalid addresses, multiline CSV, or a malformed file after a valid row; regressions in findings 1–4 would pass.

Fix: assert store contents and rejection details, and add focused cases for those behaviors. Replace tests that require strict mode and the domain skip.
