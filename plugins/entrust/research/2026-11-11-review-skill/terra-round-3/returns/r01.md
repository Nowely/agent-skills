## Change

The nightly job is extended to email customers about overdue invoices. Source: `brief.md`; the commit message gives no additional requirements.

Requirements:

1. Select unpaid invoices whose due date has passed, using UTC calendar dates.
2. Send an email naming the invoice number, amount and due date.
3. Do not notify an invoice twice.
4. Continue after a failed send and retry that invoice the next night.
5. Preserve the existing paid-invoice closing step.

## Verdict

The change does not meet the task: it sends on the due date, sends a generic message, and sends again on every subsequent run. Its tests exercise the new notification machinery but do not exercise the requested nightly behavior.

Target: a nightly overdue step selects unpaid, previously unnotified invoices with `dueDate < today`, formats the message using `formatAmount`, calls the existing mailer, and records success through `repo.update`. It catches each send failure so later invoices continue. `runNightly` calls that step after closing paid invoices; the event bus, channel framework, configuration and template engine are unnecessary for this task.

Recommendation: rewrite toward that target, addressing findings 1–3 first and adding the integration tests in finding 6.

## Findings

### 1. Successful sends are repeated on every run (behavior; traced)

`src/invoices/overdue.js:2`: Every unpaid overdue invoice is emitted on every invocation, and neither this step nor `NotificationService.notify` records a successful send. Running the job again with the same repo sends the same invoice again, breaking requirement 3. The service also swallows send errors, so its caller cannot distinguish success from failure.

Fix: have the overdue step await the mailer, record notification success on the invoice only after it resolves, and skip invoices already recorded as notified. Catch failures per invoice so they remain eligible for retry.

### 2. The overdue template is never selected (behavior; traced)

`src/notifications/templates.js:2`: The template is keyed `invoice_overdue`, but `runNightly` and `detectOverdue` use `invoice.overdue`. `getTemplate` therefore returns the generic fallback, whose subject and body contain no invoice number, amount or due date. Every default-path email breaks requirement 2.

Fix: use the same key throughout, or directly format the single required email.

### 3. Invoices are notified on their due date (behavior; traced)

`src/invoices/overdue.js:3`: For an unpaid invoice due on `2026-03-12`, a run on that UTC date satisfies `<=` even though the due date has not passed. This breaks requirement 1.

Fix: compare `invoice.dueDate < today`.

### 4. Configuration can disable required delivery (behavior; traced)

`src/jobs/nightly.js:11` and `src/notifications/NotificationService.js:17`: A caller can pass `{ events: { "invoice.overdue": { enabled: false } } }`, or an empty channel list, and the job silently sends nothing for eligible invoices. The task requires the nightly job to send the email and specifies no opt-out, so this breaks requirements 2 and 4.

Fix: remove the new configuration parameter and send through the supplied mailer.

### 5. A generic notification framework obscures the one required job (design; judgment)

`src/jobs/nightly.js:14`: A single fixed email traverses an event bus, service, registry, channel, template lookup and template engine. Changing or tracing that email requires following those units and keeping event keys consistent, as finding 2 demonstrates. The existing `closePaidInvoices` step is a direct function called by `runNightly`, and `mailer.send` is already the app’s mail interface.

Fix: use one direct overdue step, `formatAmount`, `mailer.send` and `repo.update`; remove the framework and its framework-only tests.

### 6. No test checks the requested nightly notification behavior (tests; traced)

`test/notifications.test.js:87`: The only enabled-event test asserts the recipient and count, so the generic message passes. No test invokes `runNightly` with overdue invoices, repeats a run, checks the due-date boundary or paid invoices, or makes one send fail before another succeeds. The defects in findings 1–3 and a regression that stops processing after a rejection all pass the present tests.

Fix: test the public nightly job with past, current and future UTC dates and paid invoices; assert the recipient and all required message fields; repeat the run after success; and reject one send while verifying another succeeds and the failed invoice is retried on the next run.
