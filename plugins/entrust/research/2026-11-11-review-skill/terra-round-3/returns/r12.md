## Change

Adds CSV contact import using the existing parser, email validator and contact store.

Sources: `brief.md`; the diff from `HEAD~1` to `HEAD`.

Requirements:

1. Reject rows with an empty name or invalid email, reporting line and reason without stopping the import. **Fails:** findings 1 and 2. Source: task.
2. Match emails ignoring case and surrounding spaces; rename existing contacts and create new ones. **Met by tracing.** Source: task.
3. Count an email once per file, with the last row winning. **Met by tracing for valid rows; end-to-end coverage is incomplete:** finding 4. Source: task. Assumption: rejected rows do not participate in selecting the winner.
4. Return created and updated counts and rejected rows. **Fails for discarded records:** finding 1. Source: task.
5. Write nothing if parsing fails. **Met by tracing:** parsing finishes before the first write. Source: task.
6. Do not treat a blank line as a row. **Partly met:** physical blank lines are skipped, but a quoted empty field is also skipped; finding 1. Source: task.

## Verdict

The import handles the main creation, rename and deduplication paths, but it silently drops a CSV record and accepts some invalid addresses. The tests also do not exercise duplicate counting through the public import entry point.

Target: parse the whole file, validate and collect the last valid row per normalized email, then apply each distinct contact once while counting the result. Reuse the parser, validator and store after correcting their relevant contracts; retain the current rejection reporting and deduplication.

Recommendation: fix in place. Correct record detection and email validation (1–2), simplify the planning interface (3), and cover duplicate imports end to end (4).

## Findings

### 1. A quoted empty record is silently discarded (behavior; traced)

`src/contacts/import.js:31`: `importContacts('name,email\n""\n', store)` returns no rejection. `src/lib/csv.js:10`–`12` treats a single empty cell as a blank line even when the source contains quotes. The parser accepts missing cells as empty at `src/lib/csv.js:35`, so this record should reach validation and be rejected for its empty name. This breaks requirements 1, 4 and 6.

Shown by: the CSV input permitted by the task and the parser’s quoted-field contract at `src/lib/csv.js:3`–`5`.

Fix: preserve whether a record contained CSV syntax or other source characters, so `""` is a record while a physical blank line remains skipped. Add an import test asserting its line and rejection.

### 2. Invalid addresses pass the shared validator (behavior; traced)

`src/contacts/import.js:6`: `Ann,ann@site..test` passes `isEmail` and is inserted, although the domain contains an empty label. The expression at `src/contacts/email.js:1` accepts consecutive dots. This breaks requirement 1.

Shown by: the task’s invalid-address rejection requirement and the path through `src/contacts/email.js:7`–`8` to `src/contacts/store.js:12`–`16`.

Fix: correct the shared email validation contract and cover invalid domain labels in both validation and import tests. This also changes validation for the existing single-contact form, which uses the same function.

### 3. The exported plan and its write lists add an unneeded interface (necessity; judgment)

`src/contacts/import.js:11`–`27`: the exported `planImport` and separate `create` and `rename` arrays expose an intermediate representation used only by its tests. The task requires parsing to finish before writes, which the eager `parseCsv` call already guarantees; deduplication requires the `names` map, but not another plan containing two write lists.

Shown by: `src/lib/csv.js:6`–`35`, which returns all rows or throws, and the only `planImport` callers at `src/contacts/import.js:31` and `test/import.test.js:10`, `:18`.

Fix: keep validation and the normalized-email map, then apply each map entry directly and accumulate counts. Test observable import results through `importContacts`.

### 4. Duplicate counting is not tested through import (tests; traced)

`test/import.test.js:15`–`20` checks a repeated new address only in the intermediate plan. The integration test at `:23`–`30` has no duplicate rows. A regression that counts or applies a repeated existing address more than once in `importContacts` could pass these tests, breaking requirement 3.

Shown by: the task’s repeated-email requirement and the inputs of the two tests.

Fix: import a CSV containing repeated existing and new addresses with case and spacing variations; assert final names and one count per distinct email.

## Questions and oddities

- `src/contacts/store.js:20`–`22`: every rename scans all contacts, so updating many existing contacts takes quadratic work. Expected address-book and import sizes would determine whether this needs attention.
- The task does not specify malformed headers or whether a rejected later duplicate should supersede an earlier valid row. The current implementation treats missing columns as empty and lets the last **valid** row win; a product decision would settle those cases.
