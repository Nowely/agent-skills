## Change

The change adds an overdue-invoice notification step to the nightly job, using UTC calendar dates and the existing mailer interface.

- `notifyOverdue` selects unpaid, overdue, unmarked invoices, sends mail and records successful sends.
- `runNightly` calls the step after closing paid invoices.
- Tests cover dates, message content, sequential repeat runs and a refused send.

Sources: `brief.md`; commit `b37b6b63b33082014290dd231aaa7505dd528cb0`.

Requirements:

1. Notify an unpaid invoice after its due date, using UTC calendar dates — task; traced for the supplied date representation. The UTC boundary is not tested (finding 2).
2. Include the invoice number, amount and due date — task; traced and tested.
3. Do not notify an invoice twice — task; traced and tested for sequential runs. Overlapping runs are unresolved below.
4. A failed send must not stop other sends and must be retried next night — task; traced. The test does not directly verify delivery to the other invoice (finding 1).

## Verdict

The implementation follows the requested flow for sequential runs. The main gaps are in verification: the failure test checks counters instead of the other customer’s message, and no test distinguishes UTC from a different calendar date.

Target: retain `runNightly` as the coordinator and `notifyOverdue` as the invoice-notification step, reusing the repository, amount formatter and mailer. The change is already this solution for sequential runs.

Recommendation: fix in place. First assert the other invoice’s delivery after a refusal (1), then add a UTC-boundary case (2). Resolve the overlapping-run question if the scheduler can run jobs concurrently.

## Findings

### 1. The failure test does not verify that the other customer received mail (tests; traced)

`test/nightly.test.js:38`: the test checks `{ sent: 1, failed: 1 }` and the next night’s recipients, but never inspects `refusing.sent`. A regression that sends the second invoice to the wrong address while still marking it successful can pass. This leaves requirement 4 incompletely tested.

Shown by: the two-invoice refused-send scenario at `test/nightly.test.js:39`.

Fix: assert that `refusing.sent` contains the message addressed to `c8@shop.example`, then retain the next-night retry assertion.

### 2. UTC date selection has no boundary test (tests; traced)

`test/nightly.test.js:6`: every test night is at `01:00:00Z`. A regression selecting the date in a fixed UTC+3 zone would produce the same dates for these inputs and pass, although it can notify early around midnight UTC. This leaves requirement 1 incompletely tested.

Shown by: the task specifies UTC calendar dates; `src/jobs/nightly.js:6` currently selects them correctly.

Fix: add a case near midnight UTC where the UTC date and another calendar date differ, and assert that an invoice due on the UTC date is not yet notified.
