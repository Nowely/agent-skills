## Change

Uppercase currency codes wherever prices are shown, so archived invoices display consistently with service invoices.

1. Uppercase currency in the invoice list.
2. Uppercase currency on the invoice page.
3. Uppercase currency in the CSV export.
4. Preserve the invoice’s currency and amount while changing their presentation.

Source: `brief.md`.

## Verdict

The change covers the list, but the CSV still emits lower-case archive currencies, and the invoice page substitutes USD for valid currencies outside a three-code list. The added fallbacks also rely on an obsolete client contract.

**Target:** Keep `formatPrice` as the shared screen formatter and uppercase the code there. Uppercase the CSV currency field using the same simple conversion; retain the existing amount formatting. The list and page should continue to use `formatPrice`.

**Recommendation:** Fix in place, starting with CSV coverage and currency preservation, then remove the unsupported fallbacks and add tests for all three outputs.

## Findings

### 1. CSV export still emits lower-case currency (behavior; traced)

`src/export/csv.js:2`: An archive row with `cur: "usd"` passes through `readArchive` unchanged and exports as `usd`. This breaks requirement 3.

**Fix:** Uppercase the currency field when constructing the CSV row.

### 2. The invoice page changes valid currencies to USD (behavior; traced)

`src/invoices/price.js:8`: A service invoice with `currency: "CAD"`, or an archive invoice with `cur: "cad"`, is displayed on the page as USD. The installed billing client accepts three uppercase letters, and the archive schema permits three lowercase letters; neither restricts currencies to the three listed here. This breaks requirements 2 and 4.

**Fix:** Uppercase the supplied code without restricting it to a list or replacing it with another currency.

### 3. Missing-currency handling contradicts the input contracts (necessity; traced)

`src/screens/list.js:3` and `src/invoices/price.js:4`: The list fallback and normalizer’s missing, non-string, empty and whitespace handling are based on `docs/billing.md`, which says it describes client 1.x. The installed 2.3.0 client validates a required three-letter uppercase string; the closed archive schema requires a three-letter lowercase string. The fallback parameter has no production caller supplying it. These mechanisms serve no supported input for requirements 1–4.

**Fix:** Remove the fallbacks, trimming and associated invalid-input tests. Correct or remove the stale comment.

### 4. The page masks formatting errors with a fabricated price (necessity; traced)

`src/screens/page.js:5`: The catch replaces any exception with `USD 0.00`, hiding the failure and presenting a price unrelated to the invoice. The supported sources provide a currency string and integer amount, so their normal formatting path does not need this recovery.

**Fix:** Remove the catch and use the shared formatter.

### 5. Screen price formatting is duplicated (design; judgment)

`src/screens/list.js:5` and `src/screens/page.js:6`: Both screens now own copies of the amount conversion formerly shared in `formatPrice`. A change to price formatting must be made in multiple places, and currency handling has already diverged. This complicates requirements 1, 2 and 4.

**Fix:** Restore both calls to `formatPrice` and put the uppercase conversion in that formatter.

### 6. Tests do not protect the requested outputs (tests; traced)

`test/price.test.js:10`: The new test checks the helper and list only; the existing formatter test uses uppercase EUR. A regression leaving CSV lowercase or substituting USD for CAD on the page passes these tests. The added unknown-currency test instead pins the incorrect substitution.

**Fix:** Test lower-case archive currency through list, page and CSV, and a valid currency outside the current list. Retain a check that the amount is preserved.
