## Change

Adds CSV contact import with row validation, store updates and tests.

Sources: `brief.md`; commit `6ea0f4a` against `HEAD~1`.

Requirements:

1. Reject empty names and invalid email addresses, reporting line and reason while continuing — task; **fails** (#3, #5).
2. Match email regardless of case and surrounding spaces; rename existing contacts or create new ones — task; **fails** for valid addresses at the skipped domain (#4); normalization otherwise traced.
3. Count each email once per file and let its last row win — task; last name wins for valid rows, but **counting fails** (#2).
4. Return created and updated counts and rejected rows — task; **fails** for duplicates (#2); test coverage is incomplete (#8).
5. Write nothing if the file cannot be parsed — task; **fails** (#1).
6. A blank line is not a row — task; traced for blank physical lines.
7. Import CSV records, including quoted fields — task; **fails** for multiline records and malformed quoting (#1).

## Verdict

The import handles the basic example, but it does not meet the parsing, validation and counting requirements. Its custom parser also duplicates an existing parser that already handles the relevant CSV cases.

Target: parse the whole file with `parseCsv`, validate with `isEmail`, then collect valid rows by normalized email before writing each distinct contact once. Return counts and rejected rows; retain tests for the required behavior.

Recommendation: fix in place.

1. Replace the parser and align validation (#1, #3).
2. Deduplicate before writing and counting; remove the skipped domain and modes (#2, #4, #5).
3. Remove unnecessary retry and result data (#6, #7), then cover the resulting behavior (#8).

## Findings

### 1. Parsing neither detects malformed CSV nor handles multiline records (behavior; traced)

`src/contacts/import.js:13`: Splitting into physical lines and toggling quotes locally accepts an unclosed quote and writes earlier rows before discovering nothing is wrong. A valid quoted field containing a newline is instead split into separate rows. This breaks requirements 5 and 7.

Shown by: task sentences “Nothing is written if the file cannot be parsed” and “Add CSV import”; `src/lib/csv.js:16-30` handles multiline fields and throws for invalid quoting before returning records.

Fix: call `parseCsv` on the entire input before any store operation and use its record line numbers.

### 2. Duplicate emails are counted more than once (behavior; traced)

`src/contacts/import.js:76`: A new email appearing twice increments `created` on its first occurrence and `updated` on its second; an existing email appearing twice increments `updated` twice. Requirement 3 says it counts once.

Shown by: task sentence “The same email twice in one file counts once, and the last row wins.”

Fix: collect valid rows by normalized email, keeping the last row, and then write and count each distinct email once.

### 3. Email validation disagrees with the address book (behavior; traced)

`src/contacts/import.js:1`: The expression accepts `ann@site` and `a@@b`, although the existing contact form rejects addresses without a domain suffix and its validator also excludes additional `@` characters. This breaks requirement 1.

Shown by: `src/contacts/create.js:5-6`, `src/contacts/email.js:1-8`, and `test/create.test.js:11-13`.

Fix: reuse `isEmail`.

### 4. Valid addresses at one domain are silently skipped (behavior; traced)

`src/contacts/import.js:72-75`: `Ann,ann@example.invalid` is neither imported nor rejected, despite satisfying the project’s email validator. This breaks requirement 2.

Shown by: task’s create-or-update rule and `src/contacts/email.js:1-8`.

Fix: remove the domain exception and its test.

### 5. Strict mode stops the import on rejected rows (behavior; traced)

`src/contacts/import.js:58-69`: With `{ mode: "strict" }`, an invalid row throws instead of reporting it and continuing; earlier rows may already have been written. This breaks requirement 1. The task also gives no need for a separate legacy separator mode.

Shown by: task sentence “Rejected rows are reported with their line number and the reason, and do not stop the import”; the only callers supplying these modes are `test/import.test.js:16-22`.

Fix: remove the modes and their tests; use the existing CSV parser.

### 6. Insert retries hide errors without a supported retry case (necessity; traced)

`src/contacts/import.js:83-95`: Three identical insert attempts catch every error and silently omit the contact if all fail. The repository’s synchronous `ContactStore.insert` throws only for a duplicate, which the preceding lookup excludes in this path; no caller supplies another store implementation.

Shown by: `src/contacts/store.js:8-17` and `src/contacts/import.js:76-77`. The store and import calls have no asynchronous boundary between lookup and insert.

Fix: insert once and let an unexpected error propagate.

### 7. The result includes an unused list of imported rows (necessity; traced)

`src/contacts/import.js:7`: `rows` duplicates imported data, and its only consumer is the new test. Requirement 4 asks for counts and rejected rows; no repository caller needs this list.

Shown by: the return contract in `brief.md` and `test/import.test.js:13`.

Fix: remove `rows`, its push and its assertion.

### 8. Tests do not verify the stored result or rejection details (tests; traced)

`test/import.test.js:6-14`: The test checks counts and rejection length, but never verifies that the existing contact was renamed, that the new contact was stored, or that the rejected row has the correct line and reason. Regressions in those outcomes can pass, breaking requirements 1, 2 and 4. The remaining tests instead pin the unsupported behaviors in #4 and #5.

Shown by: `test/import.test.js:6-26`.

Fix: assert stored contacts and exact rejected entries; cover duplicate emails, invalid addresses, malformed CSV with no writes, and multiline CSV.
