## Change

Adds CSV contact import, with row validation, store writes, counts and import tests.

Sources: `brief.md`; commit `3cf02c8`.

Requirements:

1. Reject empty names and invalid email addresses, report physical start line and reason, and continue importing — **fails**: findings 2, 4, 6 and 7. Source: task.
2. Match emails ignoring case and surrounding spaces; rename existing contacts or create new ones — **partly met by tracing**; valid addresses can be skipped or rejected incorrectly: findings 2 and 5. Source: task.
3. Count each email once per file; the last valid row wins, and an invalid duplicate must not replace it — **fails**: findings 2 and 3. Source: task.
4. Return created and updated counts and rejected rows — **fails**: findings 3 and 5. Source: task.
5. Write nothing if CSV parsing fails — **fails**: finding 1. Source: task.
6. Ignore blank physical lines; treat nonblank rows with missing columns, including `""`, as rows; report the record’s physical start line — **fails**: findings 4 and 6. Source: task.
7. Use the address book’s existing email validation — **fails**: finding 2. Source: task.

## Verdict

The import works for the simple example in its test but does not meet the parsing, validation and duplicate-counting requirements. In particular, malformed CSV can leave writes behind.

Target: parse the entire file with `parseCsv` before any store writes; validate with `isEmail`; collect the last valid row per normalized email; then apply each unique contact once and return counts and rejections. Reuse `ContactStore` for lookup and writes. Keep the import entry point and rejection reasons.

Recommendation: **fix in place**.

1. Replace the parser and use the existing validator, addressing findings 1, 2, 4 and 6.
2. Deduplicate valid rows before writing and remove the domain exception, addressing findings 3 and 5.
3. Remove unsupported modes and retry machinery, and add requirement-focused tests, addressing findings 7–10.

## Findings

### 1. Malformed CSV can be accepted after earlier writes (behavior; traced)

`src/contacts/import.js:13`: The importer processes and writes each physical line immediately and never checks whether quotes were closed or legally placed. For `name,email\nAnn,ann@site.test\n"broken`, Ann is inserted and the malformed final row is merely rejected, although requirement 5 says nothing may be written.

Shown by: the task’s parse-failure requirement; `src/lib/csv.js:27` and `:31` reject malformed quotes, but the importer does not call that parser.

Fix: call `parseCsv` on the whole text before touching the store; propagate its parse error.

### 2. Email validation differs from the address book (behavior; traced)

`src/contacts/import.js:1` and `:65`: The local regex accepts `ann@site` and `a@b@c.test`, while `isEmail` rejects them. They can therefore create or rename contacts instead of being reported, violating requirements 1, 3 and 7. An invalid later duplicate can also replace an earlier valid name if the address is accepted only by this regex.

Shown by: `src/contacts/email.js:1-8`; `src/contacts/create.js:5-6` uses `isEmail`.

Fix: use `isEmail(email)` and remove the duplicate regex.

### 3. Repeated emails are counted and written more than once (behavior; traced)

`src/contacts/import.js:76-96`: In an empty store, two valid rows for the same normalized email produce `created: 1, updated: 1`, rather than counting one created contact. For an existing contact, both rows increment `updated`. This breaks requirements 3 and 4.

Shown by: the task’s “same email twice … counts once” requirement; `ContactStore.findByEmail` sees the first row’s insert at `src/contacts/store.js:8-17`.

Fix: retain the last **valid** row per normalized email before applying any of them; classify and count each resulting contact once.

### 4. Quoted multiline records are split into separate rows (behavior; traced)

`src/contacts/import.js:13-16`: `name,email\n"Ann\nLee",ann@site.test\n` is processed as two records, so the valid contact is not imported and rejection lines do not describe the original record. This breaks requirements 1 and 6.

Shown by: `src/lib/csv.js:21-26` supports line breaks inside quoted fields and tracks record start lines; `test/csv.test.js:5-6` illustrates the contract.

Fix: use the records and line numbers returned by `parseCsv`.

### 5. Valid addresses at one domain disappear without a result (behavior; traced)

`src/contacts/import.js:72-75`: `Ann,ann@example.invalid` passes the existing validator but is silently skipped: it is neither created nor rejected. This violates requirements 2 and 4.

Shown by: `src/contacts/email.js:1-8` accepts this address; the task provides no domain exclusion.

Fix: delete the domain-specific branch and its contrary test.

### 6. A whitespace-only physical line is silently skipped (behavior; traced)

`src/contacts/import.js:21-23`: For `name,email\n   \n`, the physical line contains characters and is a row with an empty name after trimming, but it produces no rejection. This breaks requirements 1 and 6.

Shown by: the task distinguishes a blank physical line from a nonblank row; `src/lib/csv.js:20` records non-newline characters and `:37` fills missing columns with empty strings.

Fix: use `parseCsv` records and validate the resulting name.

### 7. Strict mode stops on a rejected row (behavior; traced)

`src/contacts/import.js:59-61` and `:66-68`: Passing `{mode: "strict"}` throws on a bad row, so later valid rows are not imported and the caller receives no rejection list. This contradicts requirement 1.

Shown by: `test/import.test.js:16-17` invokes that path; the task requires rejected rows not to stop the import.

Fix: remove strict mode and always collect row rejections.

### 8. Legacy mode adds an unsupported CSV dialect (necessity; traced)

`src/contacts/import.js:5-6`: The added option switches to semicolons, but the task specifies CSV and the project parser uses commas. There are no production callers requiring the option; its only caller is its new test.

Shown by: `src/lib/csv.js:25`; `test/import.test.js:20-22`.

Fix: remove the option and use the existing parser. Standard CSV import remains supported.

### 9. Retrying inserts hides failures without a supported retry case (necessity; traced)

`src/contacts/import.js:83-95`: Every insert exception is swallowed up to three times, then the contact is silently omitted from all counts and rejections. In the supplied synchronous store, the only explicit insert error is a duplicate, excluded here by the immediately preceding lookup; retrying unchanged input cannot resolve it.

Shown by: `src/contacts/store.js:8-17` and the lookup at `src/contacts/import.js:76`.

Fix: call `insert` once and allow an unexpected error to reach the caller.

### 10. Import tests do not verify the required outcomes (tests; traced)

`test/import.test.js:6-13`: The only general import test checks counts and lengths, not stored names, rejection line/reason, or failure atomicity. Regressions in findings 1–6 pass these assertions. The other tests pin unsupported behavior instead of the task.

Shown by: `test/import.test.js:16-26`; existing parser tests exercise the parser directly, not the importer.

Fix: test stored contacts and exact results for normalized duplicates, last valid versus invalid duplicate, invalid addresses, missing fields and physical line numbers; test multiline CSV and verify the store remains unchanged after a late parse error.
