# Independent evaluation of code reviews

Each numbered directory is one change, shown as base/ and target/, the task in brief.md, and two reviews rNN.md. Compare the code and task directly. The two reviews concern the same target, and you do not know how they were produced. Do not read anything outside this directory or run code or tests.

For each review independently evaluate: (1) accuracy and completeness relative to the given task and contracts; (2) concrete maintainability and reading cost, without counting lines/functions or assuming a split is necessary; (3) whether any removal and reuse are supported and preserve behavior; (4) whether the complete proposed target is coherent and actionable; (5) calibration, including unsupported mandatory changes and unverified assumptions. Inspect the actual code before deciding that a missing structural finding is material. On clear cohesive code an evidence-consistent no-findings conclusion is acceptable; an optional better structure alone is not a defect. An actual unsupported assertion should be distinguished from a genuinely unresolved contract.

For each review report: id; a 0/1/2 assessment of diagnosis, actionable coherent target, reuse/necessity and calibration; N/A where the relevant problem is absent and honest silence is appropriate; specific evidence supporting each mark; what material point was missed; each harmful or unsupported recommendation; and justified noncritical alternatives. A score of 2 means demonstrated and actionable or a justified no-change outcome when no issue exists; 1 means directionally useful but materially incomplete; 0 means materially missing or incorrect, with a concrete reason. Do not award a perfect design score simply for listing phases or citing a preferred implementation. Do not penalize a single function, number of helpers, or departure from any imagined reference. Assess test-gap findings separately from claims that behavior is wrong. Do not sum dimensions into an overall quality percentage.

Return an assessment for all eight run IDs. Keep uncertainty explicit and explain disagreements with task assumptions rather than inventing inputs.
