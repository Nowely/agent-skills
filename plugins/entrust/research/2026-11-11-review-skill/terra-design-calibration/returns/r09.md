## Change

The change adds CSV contact import, including row validation, duplicate handling, writes, and a result object. The task requires valid rows to be imported independently while a parse failure leaves the store untouched.

Source: `brief.md`. The commit provides no additional rationale.

Requirements:

1. Import the `name` and `email` columns; reject empty names and invalid emails with their physical starting line and reason, continuing the import. **Fails:** findings 1, 2, 4 and 6.
2. Identify emails without regard to case or surrounding whitespace; rename existing contacts, create new ones, and count each email once, using its last valid row. **Fails:** finding 3. Normalization is traced through `ContactStore`.
3. Return created and updated counts and rejected rows. **Fails:** findings 3–5 and 7.
4. Write nothing when the CSV cannot be parsed. **Fails:** finding 1.
5. Ignore only physically empty lines; treat whitespace-only and incomplete rows, including `""`, as rows. **Fails:** finding 4.
6. Use the address book’s existing email validation; rejected duplicates must not replace earlier valid rows. **Fails:** finding 2.

## Verdict

The import does not yet meet the task: it writes while parsing, accepts addresses rejected elsewhere in the address book, miscounts duplicates, and silently drops some rows. The tests cover only a narrow happy path and also assert behavior that conflicts with the task.

**Target:** Parse the complete input with `parseCsv`, validate rows with `isEmail`, and collect the last valid row per normalized email alongside rejections. Then apply each collected contact once through `ContactStore` and return the requested counts and rejections. Keep the existing store and email helpers; replace the handwritten parser and unsupported modes.

**Recommendation:** Fix in place.

1. Replace parsing and stage rows before writes (findings 1 and 4).
2. Reuse validation, deduplicate, and remove silent exclusions and unsupported modes (findings 2, 3, 5 and 6).
3. Remove the retry and extra result data; add focused regression tests (findings 7–9).

## Findings

### 1. Parsing and writing are interleaved, and malformed CSV is accepted (behavior; traced)

`src/contacts/import.js:13`: Splitting on physical newlines cannot parse quoted multiline fields and never rejects an unclosed or misplaced quote. Earlier rows are already written before a later parse error could be detected. This breaks requirements 1 and 4.

**Shown by:** For `name,email\nAnn,ann@site.test\n"Bad,bad@site.test`, line 87 inserts Ann and the unclosed quote is not reported as a parse error. A valid quoted name containing a newline is split into separate rows. `src/lib/csv.js:6` parses whole records and `src/lib/csv.js:27` and `:31` reject malformed quotes.

**Fix:** Parse the entire text with `parseCsv` before any store write; use each returned record’s starting `line`.

### 2. Import uses a different email definition (behavior; traced)

`src/contacts/import.js:1`: `EMAIL_RE` accepts `ann@site`, while the existing validator rejects an address without a domain suffix. Such a row is imported instead of rejected; if it duplicates an earlier accepted row, it can also replace that row’s name. This breaks requirements 1 and 6.

**Shown by:** `src/contacts/email.js:1` and `:7` define validation; `test/create.test.js:11` exercises `ann@site`.

**Fix:** Use `isEmail(email)` for every import row.

### 3. Repeated emails are counted and written per row (behavior; traced)

`src/contacts/import.js:76`: Every valid row immediately looks up and writes its contact. Two rows for a new email produce one creation and one update, although the task requires that email to count once. Repeated rows for an existing email likewise increment `updated` more than once. This breaks requirements 2 and 3.

**Shown by:** The task explicitly says the same email twice counts once and the last valid row wins. The second row reaches `result.updated++` at line 81 after the first inserts it.

**Fix:** Collect valid rows by normalized email, replacing the previous valid value, then apply each email once and count according to whether it existed before its application.

### 4. Whitespace-only physical lines are discarded (behavior; traced)

`src/contacts/import.js:21`: `line.trim() === ""` skips a line containing spaces, although it is a row and must be rejected for its empty name. This breaks requirements 1, 3 and 5.

**Shown by:** The task distinguishes a physical line with no characters from one containing spaces. `src/lib/csv.js:20` records non-newline characters, including spaces.

**Fix:** Use the existing parser’s records and validate the resulting name.

### 5. Valid addresses on one domain disappear silently (behavior; traced)

`src/contacts/import.js:73`: A valid address ending in `@example.invalid` is neither imported nor reported as rejected. This breaks requirements 1–3 and 6.

**Shown by:** `isEmail` accepts `ann@example.invalid` under `src/contacts/email.js:1`; the task specifies no domain exclusion. The test at `test/import.test.js:24` pins the exclusion.

**Fix:** Remove the exclusion and its test; include such addresses in normal validation and import.

### 6. Optional modes introduce behavior contrary to the task (behavior and necessity; traced)

`src/contacts/import.js:5`: `strict` throws on a rejected row instead of reporting it and continuing; `legacy` changes the delimiter without a task requirement. In strict mode, earlier valid rows may already have been written when a later row throws. This breaks requirement 1.

**Shown by:** The task requires rejected rows not to stop the import; the only repository calls selecting these modes are the new tests at `test/import.test.js:16` and `:20`.

**Fix:** Remove the mode option and its mode-specific tests; use the existing comma-separated parser.

### 7. Insert retries hide a failed import (necessity; traced)

`src/contacts/import.js:83`: The loop catches every insertion error three times and then silently skips the contact, so the returned result does not report that it was not imported. For the supplied synchronous `ContactStore`, the only explicit insertion error is a duplicate, already checked immediately before insertion; the task specifies no retry policy. This undermines requirement 3.

**Shown by:** `src/contacts/store.js:12`–`:17` defines insertion and its duplicate error; `src/contacts/import.js:76` checks the same normalized key first.

**Fix:** Insert once and let an insertion error reach the caller rather than silently returning an incomplete result.

### 8. The result includes an unrequested copy of imported rows (necessity; traced)

`src/contacts/import.js:7`: `rows` is maintained in addition to the requested counts and rejections. No repository consumer uses it except the new test, and it records every processed row rather than the deduplicated contacts required by the task.

**Shown by:** `brief.md` requests created and updated counts and rejected rows; `test/import.test.js:13` is the only use of `result.rows`.

**Fix:** Remove `rows`, its append at line 98, and the corresponding assertion.

### 9. Tests do not establish the import contract (tests; traced)

`test/import.test.js:6`: The main test checks counts and rejection length only. A regression that does not rename the existing contact, returns the wrong rejection line or reason, mishandles duplicates or whitespace-only rows, accepts malformed CSV after writing, or diverges from existing email validation can pass it. The remaining tests pin unsupported or incorrect behavior described in findings 5 and 6.

**Shown by:** The assertions at lines 10–13 do not inspect stored names or rejection contents; no import test covers the listed inputs.

**Fix:** Test the resulting store and exact rejections, duplicate counts and last valid row, whitespace and missing fields, multiline records and starting lines, validator parity, and no writes on a parse error after a valid row.
