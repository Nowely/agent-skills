## Change

Adds CSV contact import, row rejection reporting and import counts. Source: the author’s task in `brief.md`.

Requirements:

1. Reject empty names and invalid emails, report the physical starting line and reason, and continue importing. **Fails**: findings 1, 2, 4 and 6.
2. Identify emails without regard to case or surrounding spaces; create or rename contacts; count each email once and let its last valid row win. **Fails**: findings 1, 3 and 5.
3. Return created and updated counts and rejected rows. **Fails**: findings 3 and 5.
4. Write nothing when CSV parsing fails. **Fails**: finding 1.
5. Skip only physical lines with no characters; treat spaces, missing columns and a quoted empty field as rows. **Fails**: findings 1 and 4.
6. Use the existing email validator; a rejected duplicate must not replace a valid one. **Fails**: finding 2. The duplicate behavior is otherwise traced for rows the importer rejects.

## Verdict

The import handles the basic example but does not meet the CSV, validation or duplicate-counting requirements. In particular, it can write contacts from malformed CSV and accepts addresses rejected by the existing form.

Target: parse the entire file with `parseCsv`, validate rows with `isEmail`, and collect the last valid row per normalized email before writing. Use `ContactStore` once per distinct email; retain the rejection reporting and counts, without the extra modes, retry or result rows.

Recommendation: **fix in place**.

1. Replace the parser and validator and correct duplicate handling and blank-line behavior (findings 1–4).
2. Remove unsupported filtering, modes, retries and output (findings 5–8).
3. Add behavioral tests for persisted results and the specified boundaries (finding 9).

## Findings

### 1. The importer does not parse CSV before writing (behavior; traced)

`src/contacts/import.js:13`: splitting at physical newlines loses quoted multiline fields and never checks whether quotes close or enclose whole fields. Earlier rows are written as the loop proceeds even if a later record is malformed. This breaks requirements 1, 2, 4 and 5.

**Shown by:** the task’s CSV input. For `name,email\nAnn,ann@site.test\n"Bob,bob@site.test`, Ann is inserted and the unclosed quote is not reported as a parse error. A quoted name containing a newline is instead split into separate records. `src/lib/csv.js:21`–`31` handles both cases.

**Fix:** call `parseCsv(text)` to completion before any store mutation and process its records and starting line numbers.

### 2. Email validation differs from the address book (behavior; traced)

`src/contacts/import.js:1`: `^\S+@\S+$` accepts addresses such as `ann@site` and `a@b@site.test`, which the existing validator rejects. This breaks requirements 1 and 6 and can let an invalid duplicate replace a valid row.

**Shown by:** `src/contacts/email.js:1`–`8` and `test/create.test.js:11`–`12`; the task explicitly selects that validator.

**Fix:** use `isEmail` for each row.

### 3. Duplicate rows are counted more than once (behavior; traced)

`src/contacts/import.js:76`: every valid row is immediately written and counted. Two rows for a new email produce `created: 1, updated: 1`; two for an existing email produce `updated: 2`. Requirement 2 says each email counts once.

**Shown by:** `name,email\nFirst,a@site.test\nLast, A@SITE.TEST ` against `ContactStore`: its normalized lookup finds the first insertion on the second row (`src/contacts/store.js:8`–`16`). The final name is Last, but the counts are wrong.

**Fix:** retain the last valid row per normalized email, then create or update each distinct email once.

### 4. Lines containing only spaces disappear (behavior; traced)

`src/contacts/import.js:21`: `line.trim() === ""` skips a spaces-only row rather than rejecting its empty name. This breaks requirements 1 and 5.

**Shown by:** `name,email\n   \n` returns no rejection, although the task says a line containing spaces is a row. `parseCsv` preserves it as a record (`src/lib/csv.js:20`, `:29`, `:32`).

**Fix:** use the existing parser’s blank-record handling and validate the resulting row.

### 5. Valid addresses in a domain are silently skipped (behavior; traced)

`src/contacts/import.js:72`: a valid `@example.invalid` address is neither created or updated nor rejected, breaking requirements 2 and 3.

**Shown by:** `Ann,ann@example.invalid` satisfies `isEmail` at `src/contacts/email.js:1`–`8`, and the added test at `test/import.test.js:24` explicitly exercises the skip. The task specifies no domain exclusion.

**Fix:** remove the domain special case and its test.

### 6. Extra modes change the required import behavior (necessity; traced)

`src/contacts/import.js:5`: `strict` stops at a rejected row, contrary to requirement 1; `legacy` changes the delimiter without a task requirement. The tests at `test/import.test.js:16`–`22` protect these extra behaviors.

**Shown by:** the task requires rejected rows not to stop import and describes a CSV file; no repository caller requires either mode.

**Fix:** remove the mode option and its tests; use the existing CSV parser.

### 7. Insert retries suppress an error without a supported recovery case (necessity; traced)

`src/contacts/import.js:83`: insertion is attempted three times, and all failures are silently discarded. The existing synchronous `ContactStore.insert` throws for a duplicate, but immediately preceding `findByEmail` uses the same normalization; no repository entry changes the store between them.

**Shown by:** `src/contacts/store.js:8`–`16` and `src/contacts/import.js:76`–`87`. Removing the retry preserves the required behavior under that store contract and lets an unexpected error reach the caller.

**Fix:** call `insert` once and remove `MAX_RETRIES`.

### 8. The result includes an unrequested row log (necessity; traced)

`src/contacts/import.js:7`: `rows` adds an output field and per-row bookkeeping that no requirement or repository caller uses. It also records duplicate rows separately despite the task’s distinct-contact counts.

**Shown by:** the task asks for counts and rejected rows; the only repository consumer of `rows` is the added assertion at `test/import.test.js:13`.

**Fix:** remove `rows`, its pushes and that assertion; retain counts and rejections.

### 9. Tests do not verify the resulting contacts or rejection details (tests; traced)

`test/import.test.js:6`: the basic test checks counts and rejection length but not stored names, emails, line numbers or reasons. Removing `store.rename` would still pass it, as would reporting the wrong rejection line or reason.

**Shown by:** the assertions at `test/import.test.js:10`–`13`; no other import test checks these outcomes.

**Fix:** assert the store contents and exact rejections, including normalized duplicates with a later rejected row. Add import-level cases for malformed and multiline CSV, spaces-only and missing-column rows, and the existing email validator.
