## Change

Adds CSV import for an address book: parse rows, validate and deduplicate them, then create or rename contacts and report counts and rejections.

Source: `brief.md`.

Requirements:

1. Reject empty names and invalid emails, reporting the starting physical line and reason without stopping the import — **met by tracing**; integration coverage is incomplete ([finding 3](#3-test-blank-and-incomplete-records-through-the-import-tests-traced)).
2. Match emails regardless of case and surrounding spaces; rename existing contacts and create new ones — **met by tracing**.
3. Count each email once and let its last valid row win, even when a later duplicate is rejected — **met by tracing**; regression coverage is incomplete ([finding 2](#2-test-rejected-duplicates-and-returned-counts-tests-traced)).
4. Return created and updated counts and rejected rows — **met by tracing**; duplicate counts lack an import-level test ([finding 2](#2-test-rejected-duplicates-and-returned-counts-tests-traced)).
5. Write nothing when parsing fails — **met by tracing**.
6. Ignore physically blank lines, but treat spaces, missing cells and a single quoted empty field as rows; report the physical starting line — **met by tracing**; integration coverage is incomplete ([finding 3](#3-test-blank-and-incomplete-records-through-the-import-tests-traced)).
7. Use the existing email validator — **met by tracing**.

## Verdict

The implementation meets the specified behavior in the paths traced. Its main gaps are tests for rejected duplicates and CSV edge cases through the public import function. The separate exported plan and its two operation arrays are unnecessary for the stated atomicity requirement.

**Target:** Parse the whole file first; validate rows and collect the last valid name per normalized email; then traverse that map once to write contacts and count creates and updates. Reuse `parseCsv`, `isEmail`, `normalizeEmail` and `ContactStore`. Keep the validation and deduplication decisions.

**Recommendation:** Fix in place: simplify the plan ([1](#1-remove-the-separate-operation-plan-necessity-traced)), then add import-level regression tests ([2](#2-test-rejected-duplicates-and-returned-counts-tests-traced), [3](#3-test-blank-and-incomplete-records-through-the-import-tests-traced)).

## Findings

### 1. Remove the separate operation plan (necessity; traced)

`src/contacts/import.js:20`: `create` and `rename` arrays and the exported `planImport` add an intermediate representation before the same operations are immediately applied. Requirement 5 needs parsing to finish before writes; it does not require a second plan after the valid rows have been deduplicated.

**Shown by:** `parseCsv` completes or throws before returning (`src/lib/csv.js:31-37`); the only repository caller of `planImport` outside its tests is `importContacts` (`src/contacts/import.js:31`).

**Fix:** After parsing and building `names`, look up and write each distinct email directly, incrementing the appropriate count. Preserve validation before adding a row to the map.

### 2. Test rejected duplicates and returned counts (tests; traced)

`test/import.test.js:15`: The duplicate test checks the intermediate plan for two valid rows, but no test imports a valid row followed by an invalid row for the same email or checks counts for repeated emails. Regressions in requirements 3 and 4 can pass: an invalid later row could replace the valid one, or repeated rows could be counted more than once.

**Shown by:** The existing duplicate test calls `planImport` and checks only its arrays (`test/import.test.js:15-20`); the import-level count test contains no duplicate (`test/import.test.js:23-29`).

**Fix:** Import repeated emails with case and spacing variants, including a later rejected duplicate, and assert the final stored name, rejection and one create or update count. Cover an existing contact as well.

### 3. Test blank and incomplete records through the import (tests; traced)

`test/import.test.js:23`: No import test checks a spaces-only line, missing name or email cells, a single quoted empty field, and the physical line after a multiline record. A regression that drops one of those rows or reports its wrong line can pass, breaking requirements 1 and 6.

**Shown by:** Parser tests cover quoted empty and blank rows and line numbering in isolation (`test/csv.test.js:22-27`), while the import test exercises only a comma-separated empty name (`test/import.test.js:26-27`).

**Fix:** Add an import-level CSV example containing those cases and assert its rejected rows and physical line numbers.
