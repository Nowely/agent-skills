Review of CSV import of contacts

HEAD~1...HEAD
The change

Import contacts from CSV text into the address book, creating or renaming by email and reporting rejected rows.

The brief asks for a bulk import with per-row rejection, email-keyed upsert, de-duplication inside a file, and no writes when the file cannot be parsed.

  • src/contacts/import.js: importContacts with its own CSV splitter, validation, upsert, retry loop, strict and legacy modes, and a skip of a test domain
  • test/import.test.js: four tests, one of them for each extra

Sources: /tmp/review-run-k6dXb5/brief.md; the diff HEAD~1..HEAD

Verdict

The happy path works, but the change misses two requirements: a repeated email in one file is counted as created plus updated, and an unparseable file is not detected, so earlier rows are already written. It also adds a second CSV parser and email check beside the project's own, plus several unrequested mechanisms (modes, retry, domain skip, rows) that silently drop rows or write partially.

Recommendation

Rewrite as the target, about 30 lines. Fix findings 1 and 2 first (they break stated requirements), then delete 4, 5 and 6, reuse isEmail (3), and add the tests of 7.

Target: the smallest clean solution
importContacts(text, store): parseCsv(text) (throws CsvError before any write), then validate each row with isEmail/normalizeEmail into a Map keyed by normalized email (last row wins), collecting rejected {line, reason}; then apply the map with store.findByEmail/insert/rename and count created/updated. Keeps only the validation reasons and upsert idea of the change.

Findings

1. Own CSV splitter instead of parseCsv: unclosed quotes undetected, multi-line fields break, writes happen while parsing

behaviortracedsrc/contacts/import.js:13B5B6B7B8

The text is split on \n and each line parsed alone, while src/lib/csv.js parseCsv already handles BOM, CRLF, quoted line breaks and throws CsvError for an unclosed quote. With 'name,email\nAnn,ann@site.test\n"Bob,bob@site.test\n' Ann is inserted, then the unclosed quote just ends the line: no error, so nothing tells the caller the file is bad (requirement 4). A quoted name containing a newline is cut in two lines, giving wrong rejections and, after it, wrong line numbers (i+1 counts physical lines). A lone \r line ending is not split. Parsing, validating and writing are done in one loop, so no write can be held back until the parse succeeds. Breaks requirement 4, 1.

Fix: Call parseCsv(text) first (its rows carry line and the header-keyed cells), let CsvError propagate, and only then touch the store.

2. A repeated email in one file is counted as created and updated

behaviortracedsrc/contacts/import.js:76B6B11B12

Rows are written as they are read. For 'Ann,a@x.test' then 'Anne,a@x.test' the first row inserts (created 1), the second finds it with findByEmail and counts updated 1. The brief says the same email twice counts once, last row wins: expected created 1, updated 0 with name Anne. The test suite has no such case. Breaks requirement 2.

Fix: Collect the valid rows into a Map keyed by normalizeEmail(email) (later rows overwrite), then upsert once per key.

3. Private email regex differs from isEmail

necessitytracedsrc/contacts/import.js:1B1B9

EMAIL_RE = /^\S+@\S+$/ accepts 'a@b' and 'a@@b', which src/contacts/email.js isEmail (and so createContact) rejects, since it requires a dot in the domain and one @. The same address is valid through the import and rejected by the form. The email is also normalized by hand five times instead of normalizeEmail. Breaks requirement 1.

Fix: Import isEmail and normalizeEmail from ./email.js and delete EMAIL_RE.

4. Rows of @example.invalid are silently dropped

behaviortracedsrc/contacts/import.js:72B10B19

A comment calls it temporary; no requirement asks for it. A valid row of that domain is neither created, updated nor rejected, so the user is not told, and it contradicts 'rows are rejected only when name or email is invalid'. Its test pins the behavior. Breaks requirement 1.

Fix: Delete the branch and its test.

5. Retry loop around insert is unnecessary and swallows errors

necessitytracedsrc/contacts/import.js:83B2B13

ContactStore.insert throws only when the email already exists; this was just checked with findByEmail, so a retry cannot succeed and the same error repeats three times. When it fails the row is dropped with continue: not created, not rejected, no reason. MAX_RETRIES has no source.

Fix: Call store.insert once; let an unexpected error propagate.

6. Unrequested modes and result.rows

necessitytracedsrc/contacts/import.js:5B3B4B8B9B14B17B18

mode 'strict' throws on the first bad row after earlier rows were written, so it leaves a partial import, and the brief says bad rows do not stop the import. mode 'legacy' changes the separator to ';' that nothing requires, and options.mode is read by no caller. result.rows is not in the return contract and holds the raw, unnormalized email. Each adds branches and a test.

Fix: Remove options, mode, separator and result.rows; return {created, updated, rejected}.

7. Tests miss the requirements and pin the extras

testsjudgmenttest/import.test.js:6B16

No test for a duplicate email in a file (finding 2 passes), for case or space differences in the email (an uppercase 'ANN@Site.test' row), for the rejection line number and reason (only the length is checked), for a rename actually changing the name, or for an unclosed quote writing nothing (finding 1 passes). Three of four tests cover extras (strict, legacy, example.invalid). Breaks requirement 2, 4.

Fix: Add those tests; drop the three that pin removed behavior.

Questions and oddities

  • src/contacts/import.js:81 A row that renames to the same name counts as updated; the brief says an existing email 'renames', so this is probably intended, to be confirmed.
