Review of CSV import of contacts

HEAD~1..HEAD

The change does not do its task. It misses two stated rules: a repeated email in one file is counted as created and then updated instead of once, and a file that cannot be parsed still writes contacts. It also ignores the existing `parseCsv`, `isEmail` and `normalizeEmail`, and adds three behaviours nobody asked for (strict and legacy modes, a skip of `@example.invalid` addresses, an insert retry). Most important: the broken parse-failure and duplicate rules, then the hand-rolled CSV parser.

Target: the smallest clean solution
`importContacts(text, store)` in about 25 lines, in three steps. 1. `parseCsv(text)` from `src/lib/csv.js`. A `CsvError` propagates before anything is written. Each row already carries its `line`. 2. Validate each row with `name.trim()` and `isEmail`. Rejected rows go into `rejected` as `{line, reason}`. Valid rows go into a `Map` keyed by `normalizeEmail(email)`, so the last row wins. 3. Apply the map: `store.findByEmail` gives `updated++` (plus `rename` when the name differs), otherwise `store.insert` gives `created++`. Only the result shape `{created, updated, rejected}`, the empty-name and bad-email reasons, and the `findByEmail`/`rename`/`insert` calls survive from the change.

Findings

1. A file that cannot be parsed still writes contacts

behaviortracedsrc/contacts/import.js:20-48B3B5

The file is parsed and written line by line, and nothing ever throws on a parse problem. Trigger: "name,email\nAnn,ann@a.test\nBob,\"bob@b.test\n" (unclosed quote). The unclosed quote simply swallows the rest of the line. No error is raised, the Ann row is already inserted, and the Bob row is rejected or mangled. Requirement 4 ("nothing is written if the file cannot be parsed") fails. The strict throws at lines 66 and 72 also fire mid-loop, after earlier rows were inserted. That is a partial write.

Fix: Call parseCsv (it throws CsvError on an unclosed quote) and do all validation before the first store call, as in the target.

2. The same email twice in one file is counted as created plus updated, not once

behaviortracedsrc/contacts/import.js:76-96B7

The first row inserts, so created++. The second row with the same normalized email finds that contact through findByEmail and does updated++. Trigger: Ann,a@x.test then Ann2,A@X.test gives created 1, updated 1, and the name is correct only by accident. The task says it counts once, with the last row winning.

Fix: Dedupe into a Map keyed by normalizeEmail before touching the store, as in the target.

3. A hand-written CSV parser duplicates src/lib/csv.js and is worse

designtracedsrc/contacts/import.js:10-48B3B4

BOM handling, CRLF handling, quote handling and header lookup are all re-implemented, and parseCsv already does all of this. Splitting on "\n" first breaks quoted fields that contain line breaks. A row such as "Smith,\nJo",a@b.co is cut in half. Line numbers go wrong after any multi-line field, because i + 1 is used instead of the record's start line. The header is re-searched on every row (lines 52-53).

Fix: Use parseCsv. This also fixes finding 1.

4. The email rule is a weaker copy of the project's own

necessitytracedsrc/contacts/import.js:1,69B1B5

The import uses /^\S+@\S+$/ (lines 1 and 69). src/contacts/email.js already has isEmail (/^[^\s@]+@[^\s@]+\.[^\s@]+$/) and normalizeEmail, and createContact uses them. Trigger: Bob,bob@localhost or Bob,a@@b is accepted by the import and rejected by the single-contact form, so the same rule behaves differently in two places. email.trim().toLowerCase() is repeated 5 times where normalizeEmail exists.

Fix: Use isEmail and normalizeEmail.

5. A temporary skip silently drops @example.invalid rows

behaviortracedsrc/contacts/import.js:75-79B6B14

No requirement asks for it, and the comment itself says "temporary". Such rows are neither created nor rejected. The caller is never told, which contradicts "rejected rows are reported".

Fix: Delete it, and delete its test at test/import.test.js:24-26.

6. The insert retry loop is a crutch, and it silently loses rows

necessitytracedsrc/contacts/import.js:82-95B1B8

MAX_RETRIES and the try/catch. ContactStore.insert throws only when the email already exists (store.js:15). findByEmail just ruled that out, so a retry can never succeed. If it did fail, the row would be dropped with no report: the continue at line 91 skips both the count and rejected, and catch (e) swallows the error.

Fix: A single store.insert. Let an unexpected throw propagate.

7. Unrequested mode option (strict, legacy, lenient)

necessitytracedsrc/contacts/import.js:4-5,60-61,66,72B2B5B12B13

Nothing in the brief asks for any mode. separator is a parameter that switches the behaviour of the whole function, and strict is the source of the partial-write throw in finding 1.

Fix: Remove the option, the separator variable, both strict branches, and their tests.

8. result.rows is unrequested, and its email is not normalized

necessitytracedsrc/contacts/import.js:5,97B2B9

The task says to return created, updated and rejected only. rows pushes the raw email, so its casing and spacing differ from what was stored.

Fix: Remove it.

9. Tests pass for the wrong reasons and miss the stated rules

teststracedtest/import.test.js:6-26B11B12B13B14

Missing tests, each with a regression that passes today: a duplicate email in one file, with the last row winning (finding 2); case and space variants of the same email counting as one contact; rejected line and reason values (the first test only checks rejected.length); the renamed name after an update (store.findByEmail("ann@site.test").name is never asserted, so removing store.rename would still pass); an unparseable file writing nothing (finding 1); a quoted field with a comma or line break, and CRLF line endings. Tests that pin unrequested behaviour: strict, legacy and example.invalid (lines 17-26). They pass today only because of findings 5 and 7.

Fix: Add a test for each missing case above, and delete the strict, legacy and example.invalid tests when those features are removed (findings 5 and 7).

10. Nested else after continue, and unnecessary indirection

designjudgmentsrc/contacts/import.js:56-97B10

if (...) { continue; } else { if ... continue; else {...} } nests the happy path three levels deep, although each branch already ends in continue. The name/email extraction with cells[i] !== undefined repeats what parseCsv already does (?? ""). Cost: this is why the dedupe and validation cannot be separated from the writes. The target's validate-then-apply split removes it.

Fix: Use the target's validate-then-apply split, with parseCsv for the cells.

Questions and oddities

  • src/contacts/import.js:80-83 An existing contact with the same name is counted as updated although nothing changed. The brief says "a row whose email already exists renames that contact", so it is probably intended. Confirm with the author or the requester.
  • src/contacts/import.js:51 A header with missing name or email columns rejects every row with a reason about the row, not the header. Would a parse error be wanted? The brief does not say.
