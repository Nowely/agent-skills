Review of Overdue invoice email

HEAD~1..HEAD
The change

Email a customer once when an invoice becomes overdue, from the nightly job, through mailer.send.

The task asks for one notification per overdue invoice, naming number, amount and due date, with failed sends retried the next night.

  • invoices/overdue.js: detectOverdue emits an invoice.overdue event for each unpaid invoice with dueDate <= today
  • events/bus.js: EventBus with handlers and middleware
  • notifications/*: NotificationService, ChannelRegistry, NotificationChannel, EmailChannel, TemplateEngine, templates, config with deep merge
  • jobs/nightly.js: builds all of the above on every run and calls detectOverdue after closePaidInvoices
  • test/notifications.test.js: tests of the registry, template engine, bus and service

Sources: /tmp/review-run-xZuYE3/brief.md; the diff

Verdict

The change does not meet its task. The email sent is the generic fallback template, with no invoice number, amount or due date, because the template key does not match the event name. Nothing records that an invoice was notified, so every unpaid overdue invoice is emailed every night. About 250 lines of event bus, registry, channel, template engine and config are built for a single email, and none of the tests would catch these defects.

Target: the smallest clean solution
One function in invoices/overdue.js, notifyOverdue(repo, mailer, today), called from runNightly after closePaidInvoices. For each unpaid invoice with dueDate < today and no overdueNotifiedAt, it calls mailer.send(customerEmail, subject, body) with the body built from formatAmount, and on success sets overdueNotifiedAt via repo.update. A failed send is caught per invoice, so the others go on and the invoice stays unmarked for tomorrow. Reuses mailer, InvoiceRepo.update and formatAmount. Only the idea of detectOverdue's loop survives; the bus, notifications/* and their tests go.

Findings

1. The overdue email is the generic fallback and names no invoice

behaviortracedsrc/notifications/templates.js:2B10B13

TEMPLATES is keyed invoice_overdue, but NotificationService.notify looks it up with getTemplate("invoice.overdue") (NotificationService.js:21, nightly.js:19). The lookup misses and falls back to DEFAULT_TEMPLATE, so the customer gets subject "Notification" and body "You have a new notification: invoice.overdue." The number, amount and due date never appear. The silent fallback hides the miss, and no test renders the real template. Breaks requirement 2.

Fix: Build the subject and body directly in the overdue function from invoice.number, formatAmount(amountMinor, currency) and dueDate, and drop the template layer and its fallback.

2. Nothing records that an invoice was notified, so it is emailed every night

behaviortracedsrc/invoices/overdue.js:2B2B6B10

detectOverdue takes every repo.unpaid() invoice past due and emits for it; no flag or timestamp is written. An invoice that stays unpaid is emailed on each run. The same gap means that retry-next-night works only by accident: a failed and a successful send look the same afterwards. NotificationService also logs the failure and returns, so the job never learns which sends failed. Breaks requirement 3, 4.

Fix: Set overdueNotifiedAt through repo.update after a successful mailer.send, and skip invoices that have it. Leave it unset when send rejects, and catch the rejection per invoice.

3. An invoice due today is treated as overdue

behaviortracedsrc/invoices/overdue.js:3B2

dueDate <= today is true on the due date itself. The task says the due date has passed, and closePaidInvoices uses strict comparison for a similar night-after rule. A customer is told an invoice is overdue on the day it is due, and for dueDate equal to today the email is early by a night. Breaks requirement 1.

Fix: Compare invoice.dueDate < today (YYYY-MM-DD strings compare correctly).

4. A bus, registry, channel hierarchy, template engine and deep-merged config for one email

designjudgmentsrc/notifications/ChannelRegistry.js:1B1B2B3B4B5B7B8B9B10B11B12B13

Every layer has a single implementation and a single use: EventBus has one handler and unused middleware; ChannelRegistry has one factory, plus an instance cache, has() and list() that nothing calls; NotificationChannel is an abstract base with one subclass and an unused name getter; TemplateEngine has upper, lower and registerFilter that nothing uses; loadConfig deep-merges a config that only toggles one event; runNightly gains a config option the task does not ask for. All of it is rebuilt on every nightly run. The project's own precedent is closePaidInvoices: a plain function taking repo and today. Each layer also adds a place where the real requirements went wrong (finding 1) and where errors disappear into a log.

Fix: Delete notifications/*, events/bus.js and the config option. Send directly with mailer.send in overdue.js, as in the target.

5. No test covers the task, and the tests that exist pass with the defects

teststracedtest/notifications.test.js:87B14

No test runs runNightly with an overdue invoice. The service test uses a fake registry and checks only that send was called once and to is right, so it passes with the fallback template (finding 1). Nothing runs the job twice (finding 2), tests a due-today invoice (finding 3), or makes send reject and checks the other invoices still go and the failed one is retried. The registry, engine and bus tests pin scaffolding that should not exist.

Fix: Replace the file with nightly tests using InvoiceRepo and a fake mailer: the subject/body contain number, amount and due date; a second run sends nothing; due today sends nothing; a rejected send leaves the others sent and is sent again on the next run.
