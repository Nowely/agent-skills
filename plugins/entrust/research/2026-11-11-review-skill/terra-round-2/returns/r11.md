## Verdict

The import does not yet meet the task: malformed CSV can leave contacts written, repeated emails are counted more than once, and some valid or invalid addresses are handled incorrectly.

The smallest solution is to parse the entire file with the existing CSV parser, validate rows with the existing email validator, retain the last valid row per normalized email, then apply each contact once. The store’s lookup, insert and rename operations can remain.

Requirements:

1. Reject rows with an empty name or invalid email, reporting line and reason while continuing.
2. Match emails case-insensitively and without surrounding spaces; create or rename contacts. Count each email once per file, with the last row winning.
3. Return created and updated counts and rejected rows.
4. Write nothing if parsing fails.

## Findings

### 1. Parsing is incomplete and writes happen before it finishes (behavior; traced)

`src/contacts/import.js:13`: Splitting by newline breaks valid quoted multiline fields. The loop also never checks whether a quote was closed. For `name,email\nAnn,ann@site.test\n"Bob,bob@site.test`, Ann is inserted before the malformed final record is encountered, and no parse error is raised. The existing `src/lib/csv.js:5` handles multiline records and throws on an unclosed quote.

Fix: call `parseCsv` on the whole input before writing any contact, and use its record line numbers.

### 2. Repeated emails are counted for every row (behavior; traced)

`src/contacts/import.js:76`: With an initially empty store, `Ann,ann@site.test` followed by `Anna, ANN@SITE.TEST ` creates one contact but returns `created: 1, updated: 1`. For an existing contact, two rows increment `updated` twice. The final name wins, but the counts violate the once-per-file requirement.

Fix: collect the last valid row for each normalized email before looking up and writing each distinct contact.

### 3. Email validation differs from the address book’s validator (behavior; traced)

`src/contacts/import.js:1`: `^\S+@\S+$` accepts `ann@site` and `ann@@site.test`; `src/contacts/email.js:1` rejects both, and the single-contact form uses that validator. These rows are imported instead of rejected.

Fix: reuse `isEmail`.

### 4. Valid addresses on one domain disappear silently (behavior; traced)

`src/contacts/import.js:72`: `ann@example.invalid` passes the project’s email validator but is neither imported nor reported as rejected.

Fix: remove the domain-specific skip and its test.

### 5. Strict mode stops an import on a rejected row (behavior; traced)

`src/contacts/import.js:58`: With `{ mode: "strict" }`, an empty name or invalid email throws instead of reporting the row and continuing. Earlier rows may already have been written. The task specifies continued import for rejected rows and does not request this mode.

Fix: remove strict mode and always append the rejection.

### 6. Insert retries suppress errors without a supported need (necessity; traced)

`src/contacts/import.js:83`: The supplied synchronous `ContactStore.insert` throws for a duplicate email, but the preceding lookup checks that same normalized key. The three retries therefore have no demonstrated recovery case; if an insert does throw, the catch discards the error and silently omits the contact from the result.

Fix: call `insert` once and let failures propagate.

### 7. Legacy mode and returned row details add unrequested behavior (necessity; traced)

`src/contacts/import.js:5`: The semicolon mode adds a second parsing format, and `src/contacts/import.js:98` adds a `rows` result. Neither serves a stated requirement or has a production caller in the repository; the mode also prevents direct reuse of the project CSV parser.

Fix: remove the mode and return only the counts and rejected rows.

### 8. Tests miss the contract’s consequential regressions (tests; traced)

`test/import.test.js:6`: The happy-path test checks counts and lengths, but not stored names, rejected line numbers or reasons. Removing the rename call would still pass. No import test covers repeated normalized emails, invalid email rejection, multiline CSV or a parse error after a valid row; the existing parser tests do not exercise import atomicity. Tests at lines 16–25 instead pin the unsupported strict mode, legacy mode and domain skip.

Fix: test the resulting store and full rejection details, duplicate counting and last-name wins, valid multiline records, and unchanged store after a later parse error.
