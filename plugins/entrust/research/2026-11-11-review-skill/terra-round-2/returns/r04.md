## Verdict

The sequential happy path meets the task, but overlapping runs can send the same invoice twice, and an invoice paid while the job is waiting can still be emailed. The tests do not cover either case or a due date in the future.

Requirements: 1. Notify unpaid invoices only after their UTC due date, with number, amount and due date. 2. Notify each invoice once. 3. Continue after a failed send and retry it the next night.

Target: keep the nightly step and existing mailer and formatting utility. Serialize notification runs for a repository, and check payment immediately before each send; retain marking only after successful delivery.

## Findings

### 1. Overlapping runs can send the same invoice twice (behavior; traced)

`src/invoices/overdue.js:9`: Two calls to `runNightly` sharing a repository can both pass the notification check before either awaited `mailer.send` completes. Each then sends and marks the same invoice, violating requirement 2. The existing repeated-run test waits for the first run to finish.

Fix: serialize notification runs for the same repository, including the check, send and update; test two overlapping runs with a controlled pending send.

### 2. An invoice paid while an earlier send is pending is still emailed (behavior; traced)

`src/invoices/overdue.js:8`: `repo.unpaid()` builds its list once. If invoice B is paid via `repo.update` while the job awaits invoice A’s send, B remains in that list and is sent an overdue email despite now being paid.

Fix: recheck the invoice’s payment status immediately before its send. Test payment of B while A’s send is pending.

### 3. A future due date is not tested (tests; traced)

`test/nightly.test.js:19`: The date test covers the due date and the following day, but never a date before the due date. A regression that skips only invoices due today would pass these tests while notifying future invoices.

Fix: run the job before the due date and assert that no email is sent.
