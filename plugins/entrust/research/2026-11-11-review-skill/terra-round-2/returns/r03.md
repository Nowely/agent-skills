## Verdict

The list uppercases archive currencies, but the CSV export leaves them lower case and the invoice page changes supported currencies outside a three-code list to USD.

Requirements: 1. Uppercase codes in the invoice list. 2. Uppercase codes on the invoice page. 3. Uppercase codes in the CSV export.

**Target:** Uppercase `cur` when `readArchive` converts archive rows, then retain the existing `formatPrice` calls in the list and page. The billing client already supplies uppercase codes, and the CSV will receive the normalized archive values. Keep tests that verify all three outputs through the supported sources.

## Findings

### 1. CSV retains lower-case archive currencies (behavior; traced)

`src/export/csv.js:2`: An archive row with `cur: "usd"` passes through `readArchive` unchanged and is exported as `usd`, contrary to requirement 3.

Fix: Uppercase the archive currency in `readArchive`, so every consumer receives the corrected value.

### 2. The page changes valid currency codes to USD (behavior; traced)

`src/invoices/price.js:8`: Both the archive schema and billing client allow three-letter codes beyond USD, EUR and GBP. An invoice with `jpy` in the archive or `JPY` from the service displays as `USD` on the page, changing the meaning of the amount.

Fix: Remove the whitelist and preserve the code while uppercasing the archive value.

### 3. Missing-currency handling is unsupported (necessity; traced)

`src/screens/list.js:4` and `src/invoices/price.js:4`: The installed billing client requires a non-null uppercase currency, and the archive schema requires a three-letter string. The USD defaults and non-string/empty checks therefore handle inputs excluded by both sources. The comment cites documentation explicitly written for billing-client 1.x, while `loadInvoices` uses 2.3.0.

Fix: Remove the defaults and checks, and remove the obsolete comment. Uppercase the required archive string at its source.

### 4. The page suppresses errors with a fabricated price (necessity; traced)

`src/screens/page.js:5`: The supported sources provide a string currency and integer amount; formatting those values does not require a catch. If an unexpected formatting error does occur, the catch instead displays `USD 0.00`, hiding the failure and presenting an invented amount.

Fix: Remove the catch and use the existing price formatter.

### 5. Price formatting is duplicated across screens (design; judgment)

`src/screens/list.js:5` and `src/screens/page.js:6`: Both screens now own copies of the amount formatting that `formatPrice` already owns. A future formatting change must update multiple places and can make the screens disagree.

Fix: Normalize the archive currency once and restore both calls to `formatPrice`.

### 6. Tests do not cover the supported end-to-end paths (tests; traced)

`test/price.test.js:10`: The added tests exercise the helper and list directly, but no test checks an archive invoice on the page or in CSV. The unchanged lower-case CSV and the page’s substitution of `jpy` both pass this suite. The null test also pins behavior excluded by the source contracts.

Fix: Test an archive row with a lower-case code outside the whitelist across list, page and CSV; retain a service invoice case to verify its code is preserved. Remove tests for unsupported null input and USD substitution.
