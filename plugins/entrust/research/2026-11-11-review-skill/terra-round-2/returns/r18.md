## Change

The nightly job should email each customer once when an unpaid invoice’s UTC due date has passed, while continuing after send failures. Source: `brief.md`.

1. Select unpaid invoices only after their due date.
2. Send the invoice number, amount and due date using `mailer.send`.
3. Do not notify the same invoice twice.
4. Continue after a failed send and retry that invoice the next night.

## Verdict

The change sends an email for eligible invoices, but its default template omits all invoice details, it sends again every night, and it includes invoices due today. The new tests do not exercise the nightly workflow, so they miss these failures.

Target: add one nightly invoice step that selects overdue, unpaid, unnotified invoices, formats the message using `formatAmount`, sends via the existing mailer and records success through `repo.update`. Catch each send failure without recording success. Keep the existing paid-invoice step and add workflow tests.

Recommendation: fix in place around that target, addressing findings 1–3 first and replacing the notification framework with the direct workflow.

## Findings

### 1. Successful notifications are never recorded (behavior; traced)

`src/invoices/overdue.js:2`: Every unpaid overdue invoice is emitted on every invocation. Neither this path nor `NotificationService.notify` updates the invoice, so a successful send on one night is repeated on the next and on a replay of the same night. This breaks requirement 3.

Fix: record successful delivery on the invoice and exclude recorded invoices; do not record failed sends. The current `InvoiceRepo.update` provides a place to store the marker.

### 2. The event key selects the generic template (behavior; traced)

`src/notifications/templates.js:2`: The registered template key is `invoice_overdue`, while `src/jobs/nightly.js:19` calls the service with `invoice.overdue`. `getTemplate` therefore returns `DEFAULT_TEMPLATE`, and the customer receives “Notification” with the event name instead of the invoice number, amount and due date. This breaks requirement 2.

Fix: use the actual event key or format the one required email directly.

### 3. Invoices are treated as overdue on their due date (behavior; traced)

`src/invoices/overdue.js:3`: For a due date of `2026-03-12` and today `2026-03-12`, `<=` selects the invoice although its due date has not passed. This breaks requirement 1.

Fix: compare `invoice.dueDate < today`, consistent with the date representation in `src/invoices/repo.js:1`.

### 4. A general notification framework obscures the single required operation (design; judgment)

`src/jobs/nightly.js:14`: A bus, registry, channel hierarchy, configurable event router and template engine stand between the nightly step and the existing `mailer.send`. Only one event and one channel are used by production code. Adding success tracking now requires passing invoice identity and delivery outcome back through these layers, while the service currently swallows failures. This makes requirements 3 and 4 harder to implement and verify.

Fix: call the mailer from the invoice notification step, use the existing `formatAmount`, and catch errors per invoice. Remove the unused framework and its framework-specific tests.

### 5. Tests do not exercise the requested workflow (tests; traced)

`test/notifications.test.js:87`: The only enabled-event test checks message count and recipient; it does not check subject or body. No test invokes `runNightly` with an overdue invoice, repeats a successful run, checks the due-date boundary, or fails one send before retrying it. Consequently findings 1–3 pass the added tests, and a regression stopping the batch or marking a failed send as complete would pass too.

Fix: test the nightly workflow with paid, future, due-today and overdue invoices; assert the actual message, repeat the run, and verify that a failed invoice is retried while another succeeds.

## Questions and oddities

- `src/invoices/overdue.js:4`: The repository has no durable transaction or mailer idempotency mechanism visible here. The task does not specify behavior if the process stops after mail delivery but before recording success, or if nightly jobs overlap. A delivery and concurrency contract would settle the expected guarantee for those cases.
