## Change

Uppercase invoice currency codes in the list, invoice page and CSV export. Source: `brief.md`.

1. Show currency codes in uppercase on all three outputs.
2. Preserve the invoice’s currency and amount.
3. Support invoices from both the billing service and the local archive.

The change adds a currency normalizer, changes the two screens and adds tests; CSV is unchanged.

## Verdict

The list uppercases archive currencies, but the CSV still exports them in lowercase, and the invoice page changes currencies outside a three-code whitelist to USD. The tests miss both failures.

**Target:** Normalize archive currency codes when `readArchive` converts archive rows to invoices. Keep the service client’s validated uppercase codes, reuse `formatPrice` in both screens and keep CSV serialization unchanged. Test all three outputs with an archived currency outside the whitelist.

**Recommendation:** Fix in place, starting with the incorrect page currency and CSV export, then remove the unsupported fallbacks and duplicated formatting.

## Findings

### 1. The invoice page changes valid currencies to USD (behavior; traced)

`src/invoices/price.js:8`: A service invoice with `currency: "JPY"`, or an archive row with `cur: "jpy"`, reaches `renderPage` and displays `USD` instead. The installed client accepts three uppercase letters, and the archive schema permits three lowercase letters; neither limits codes to USD, EUR and GBP. This breaks requirements 1–3.

Fix: uppercase the existing code without a whitelist or currency substitution.

### 2. CSV exports archive currencies in lowercase (behavior; traced)

`src/export/csv.js:2`: `loadInvoices` passes archive currencies through unchanged, and CSV writes `invoice.currency` directly. An archive row with `cur: "usd"` therefore exports `usd`, breaking requirements 1 and 3.

Fix: normalize archive currencies before the common invoice reaches the output paths.

### 3. Missing-currency fallbacks have no supported input (necessity; traced)

`src/invoices/price.js:3` and `src/screens/list.js:4`: The direct billing client rejects missing or null currency, and the closed archive schema requires a three-letter string. The fallback to USD is unnecessary for both supported sources. The comment in the list cites documentation for client 1.x, while `loadInvoices` imports the installed 2.3.0 client.

Fix: remove the fallback and the misleading comment. Remove the test that pins null-to-USD behavior.

### 4. The page hides formatting errors behind a fabricated price (necessity; traced)

`src/screens/page.js:5`: Valid source contracts provide a string currency and integer amount, so the catch is unnecessary for supported invoices. If formatting does throw, the page instead reports `USD 0.00`, hiding the error and inventing a price.

Fix: remove the `try`/`catch` and use the shared formatter.

### 5. The list duplicates price formatting (design; judgment)

`src/screens/list.js:5`: The list now owns a copy of the amount formatting already in `formatPrice`. A future price-format change must update both paths, and they can diverge.

Fix: restore the `formatPrice` call after normalizing the archive input.

### 6. Tests do not cover the page or CSV requirements (tests; traced)

`test/price.test.js:10`: The new test checks the helper and list only. A page that substitutes USD for JPY and a CSV that emits lowercase archive currencies both pass the suite. The `xxx` test also pins the unsupported whitelist behavior.

Fix: test an archive invoice through list, page and CSV, asserting that its uppercase currency and amount are preserved; include a code outside USD, EUR and GBP.
