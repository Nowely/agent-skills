## Review of the last commit (HEAD~1..HEAD)

Scope: I read the full diff, the brief, and the surrounding code (`src/orders/*`, `src/api/*`, `contracts/order.schema.json`, `test/*`). I did not run anything. Findings are from static tracing.

### Defects

1. **The CSV export is not changed, so it still shows "Shipped" for late orders.** This misses an explicit requirement ("The CSV export must show the same label as the screen").
   - `src/orders/export.js:4` still calls `statusLabel(order.status)` from `labels.js`. That function only maps status and ignores the promised date.
   - A late shipped order therefore reads "Delayed" on screen and "Shipped" in the CSV.
   - There is no test for the export.
   - Fix: have `toCsv` use the same function as `renderList`, passing the same `now`.

2. **The boundary is wrong: on the promised date itself the order shows "Delayed" instead of "Shipped".** This contradicts the brief ("on the promised date itself it is still 'Shipped'").
   - `badge.js:21` does `promised < now`.
   - The contract says `promisedAt` is a date-only `YYYY-MM-DD` string, and `new Date("2026-03-20")` parses as 00:00 UTC.
   - With `now = 2026-03-20T09:00Z` (the same day), `promised < now` is true, so the label is "Delayed" for the entire promised day.
   - The label flips at the start of the promised day, not the day after.
   - The calendar day also depends on timezone. The comparison should be between calendar dates, for example comparing `promisedAt` to the `YYYY-MM-DD` of `now` in a defined zone. The `YYYY-MM-DD` format sorts as a string, so `promisedAt < today` works.
   - The brief doesn't say which timezone defines "today". The author should pick one deliberately and state it.

### Unnecessary complexity (premises checked against the contract and `fetchOrders`)

All orders pass through `fetchOrders()`. It validates each order against the schema and throws `ContractError` otherwise. The schema requires `status`, makes it an enum of five values, and requires `promisedAt` to be a valid date string or null.

- **`order.status ?? "unknown"`, the `"Unknown"` default and `options.fallbackLabel`** (`badge.js:10-12`, `:9`)
  - The premise is a missing or unrecognised status. The contract rules that out, and the brief does not ask for it.
  - `options.fallbackLabel` is a new public option with no caller, and the `?? "unknown"` line has no purpose.
  - Remove them. The two tests that exercise them (`test/badge.test.js:15-21`) assert behaviour that cannot occur and should go too.
- **`try { new Date(...) } catch`** (`badge.js:15-19`)
  - `new Date(string)` never throws. An invalid string yields an Invalid Date, and comparing that gives false.
  - The validator already rejects malformed dates, so this is dead code. It also suggests invalid dates are handled, when they are not.
- **A second copy of the label map** (`badge.js:1-7`)
  - `LABELS` duplicates `STATUS_LABELS` in `labels.js`. The two can drift, and the new copy is likely why the export wasn't updated.
  - Reuse `statusLabel` and add only the delay rule.
- **`badge.js` as a new module that replaces `statusLabel` in `list.js`**
  - A simpler path is a single function, for example `displayLabel(order, now)` in `labels.js`. Both `list.js` and `export.js` call it, which satisfies the "same label" requirement by construction.

### Design and readability

- Rules in `badgeLabel`: (a) map status to a base label, (b) fall back for an unknown status, (c) parse the promised date, (d) override to "Delayed" if shipped and late. The order is base label, then fallback, then override, then return.
- The only real rule is the delay override. Rules (b) and (c)'s guard are the unnecessary parts above. Once they are removed, the function is a few lines and no boundary change is needed.
- The `let label` followed by a conditional reassignment is awkward. An early return for the delayed case reads more directly.
- `renderList(orders, now = new Date())` is reasonable for testability. The same `now` should be passed to the export.

### Tests

- Nothing tests the export, so the missed requirement passed unnoticed.
- No boundary test covers the promised date itself or the day after. The tests use dates about three weeks apart, so they would not catch defect 2.
- No test covers a null `promisedAt` on a shipped order (the in-store case the contract describes). It should stay "Shipped".
- The existing `list.test.js` only covers a paid order.
- Useful tests to add: shipped on the promised date is "Shipped"; shipped the day after is "Delayed"; a shipped order with null `promisedAt` is "Shipped"; and `toCsv` shows "Delayed" for a late order.

### Summary

The "past promised date" case works for dates well apart. The commit misses the CSV requirement and gets the promised-day boundary wrong. It adds untested-by-contract fallback and try/catch code and duplicates the label map. The API client and contract were not touched, which is correct.
