### Findings

- **[P2] Orders become delayed on the promised date itself** — [badge.js](case/head/src/orders/badge.js:21) compares an instant with the current time. A date-only value such as `2026-03-20` parses as midnight UTC, so at `2026-03-20T09:00:00Z` a shipped order is already labelled “Delayed”. The requirement says it remains “Shipped” for the entire promised date. Compare calendar dates using the intended day boundary.

- **[P2] CSV export still labels delayed orders “Shipped”** — [list.js](case/head/src/orders/list.js:4) uses the new helper, but [export.js](case/head/src/orders/export.js:4) still calls `statusLabel(order.status)`. A shipped order past its promised date therefore differs between screen and export. Use the same date-aware label calculation in both paths.

### Unnecessary complexity

- [badge.js](case/head/src/orders/badge.js:1) duplicates the existing status-label map, adding a second source that can drift. The contract requires a status from the existing enum, and the brief says both consumers receive orders through `fetchOrders()`, which validates that contract. The missing-status and custom-fallback behavior and the `try/catch` around date construction therefore support inputs outside the stated flow. Reuse `statusLabel` for the normal case and handle the contract-supported `null` promised date explicitly.

### Design and tests

The new helper implements status-to-label mapping and fallback, date parsing, and the shipped/past-date override in that order; it has no side effects. The override and normal label lookup belong in one shared decision flow, while the existing label map can remain the sole source of ordinary labels.

The new tests cover clearly past and future dates but omit the promised date itself, the following day, a shipped order with `promisedAt: null`, and screen/CSV parity. Those cases would catch the two defects and protect the supported null contract. The fallback tests instead exercise statuses the stated input contract rejects.
