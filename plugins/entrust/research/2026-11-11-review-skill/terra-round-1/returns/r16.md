## Verdict

The change retries temporary responses and stops within three attempts per invocation, but it does not enforce the limit across queue redelivery or preserve acknowledgements across process death. It also records permanent failures as successful acknowledgements, breaking the operator redelivery path.

## Findings

### 1. Acknowledgements disappear when the worker process dies (behavior; traced)

- **Where:** `src/delivery/deliver.js:8` — `if (wasAcknowledged(message.id)) return { kind: "ok", skipped: true };`
- **What happens:** If the endpoint returns `ok` and the worker dies before returning, the queue hands the job to another process. That process has an empty acknowledgement set and sends the message again.
- **Evidence:** `src/delivery/store.js:1-8` stores acknowledgements in a process-local `Set`; `src/queue/worker.js:3-4` explicitly describes redelivery after process death.
- **Fix:** Persist acknowledgements across worker processes and cover process restart in a test. The remaining window between the endpoint accepting a request and the acknowledgement being persisted also needs a protocol capable of satisfying the stated no-resend guarantee.

### 2. The attempt limit resets on queue redelivery (behavior; traced)

- **Where:** `src/delivery/deliver.js:11` — `for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {`
- **What happens:** If the worker dies after one or more temporary responses, a new invocation starts at attempt one and can send three more times. Thus one message can exceed three total attempts.
- **Evidence:** The counter is local to `deliver`; `src/queue/worker.js:3-6` permits the same job to be handed out again after the handler process dies.
- **Fix:** Persist the attempt count for the message across queue redelivery, accounting for an attempt before sending. Test a restart after a temporary response.

### 3. Permanent failures are recorded as acknowledgements (behavior; traced)

- **Where:** `src/delivery/deliver.js:17` — `if (result.kind !== "temporary") markAcknowledged(message.id);`
- **What happens:** A `400` response is marked acknowledged. An operator subsequently redelivering the message after fixing the endpoint receives `"delivered"` without a request being sent.
- **Evidence:** `src/delivery/send.js:8` maps `400` to `permanent`; `src/admin/redeliver.js:4-7` provides the redelivery path; `src/delivery/deliver.js:8` converts the stored marker into a skipped `ok`.
- **Fix:** Mark only `ok` as acknowledged and test permanent failure followed by operator redelivery.

### 4. The worker waits after the final attempt (behavior; traced)

- **Where:** `src/delivery/deliver.js:14` — `await sleep(backoffMs(attempt));`
- **What happens:** After the third temporary response, the worker waits eight seconds even though no further attempt will be made. This delays returning the final result and extends the period in which a worker death can cause queue redelivery.
- **Evidence:** The loop ends after attempt three at `src/delivery/deliver.js:11`; `src/delivery/backoff.js:1-4` supplies an eight-second delay for that attempt.
- **Fix:** Sleep only when another attempt remains. Assert the number and values of sleeps in the three-temporary-responses test.

### 5. Tests do not verify the required backoff (tests; traced)

- **Where:** `test/deliver.test.js:9` — `const sleep = async () => {};`
- **What happens:** Removing the sleeps entirely or passing incorrect backoff durations leaves all tests passing.
- **Evidence:** The retry tests at `test/deliver.test.js:25-35` assert results and send counts but never inspect sleep calls; the required values are supplied by `src/delivery/backoff.js:1-4`.
- **Fix:** Record sleep arguments and assert the existing backoff between attempts.

## Questions and oddities

How is the absolute no-resend guarantee intended to cover a worker dying after the endpoint accepts the request but before the worker records that acknowledgement? The current idempotency key can help an endpoint deduplicate processing, but `src/delivery/send.js:5` still sends the request. The endpoint and queue protocol would settle what guarantee is achievable.

## Coverage

1. **At most three attempts per message:** partial. `src/delivery/deliver.js:11-15` limits one invocation, but the count does not survive process death.
2. **Retry only temporary answers; stop on `ok` or `permanent`:** partial. The loop stops correctly, but permanent results are incorrectly stored as acknowledgements.
3. **Existing backoff between attempts:** partial. The loop uses `backoffMs`, but also waits after the last attempt; tests do not verify delays.
4. **Never resend an acknowledged message, including queue redelivery:** partial. It works for repeated calls in one process, but not after process death.
