## Verdict

The change labels some overdue shipped orders as “Delayed” on the screen, but it does so too early on the promised date. CSV export still uses the original status label, so the two outputs disagree.

The new label function also duplicates the existing status mapping and adds fallback behavior for inputs excluded by the contract.

## Findings

### 1. Orders become delayed during the promised date (behavior; traced)

- Where: `src/orders/badge.js:21` — `promised < now`
- What happens: For a shipped order promised on `2026-03-20`, at `2026-03-20T09:00:00Z`, the parsed promised date is midnight UTC and is earlier than `now`. The screen shows “Delayed” even though it must still show “Shipped” that day.
- Evidence: `contracts/order.schema.json:8–11` defines `promisedAt` as a calendar date; `src/orders/list.js:3–4` uses this function for the screen.
- Fix: Compare calendar dates, marking the order delayed only when today is after the promised date. Establish which timezone defines today.

### 2. CSV export never uses the delayed label (behavior; traced)

- Where: `src/orders/list.js:1` — `import { badgeLabel } from "./badge.js";`
- What happens: A shipped order whose promised date has passed is “Delayed” on the screen but “Shipped” in the CSV.
- Evidence: `src/orders/export.js:1–4` still calls `statusLabel(order.status)`, which maps `shipped` to “Shipped” at `src/orders/labels.js:1–5`.
- Fix: Use the same order-aware label calculation for both list and export.

### 3. Status labels have two independent sources (design; judgment)

- Where: `src/orders/badge.js:1` — `const LABELS = {`
- What happens: Changing a status label or adding a supported status requires maintaining both mappings; otherwise the screen and CSV can diverge.
- Evidence: The same five mappings already exist in `src/orders/labels.js:1–7`, which the export continues to use.
- Fix: Reuse the existing mapping in the shared order-aware label calculation.

### 4. Fallbacks and exception handling cover inputs excluded by the contract (necessity; traced)

- Where: `src/orders/badge.js:9–17` — `options = {}`, `order.status ?? "unknown"`, `options.fallbackLabel || "Unknown"`, and `try {`
- What happens: The custom fallback, missing-status fallback, and date-construction catch add behavior and tests for unsupported inputs. A valid status always has a mapping, and `promisedAt` is a string or `null`; constructing a date from a string does not throw.
- Evidence: `contracts/order.schema.json:4–11` requires the status and restricts both fields; `src/api/client.js:8–14` validates orders before returning them. The brief states that screen and export receive orders only through `fetchOrders()`. The only custom-fallback call is the test at `test/badge.test.js:19–20`.

### 5. Tests miss the date boundary and the export path (tests; traced)

- Where: `test/badge.test.js:7–12` — the tests use dates weeks before and after `now`.
- What happens: The same-day defect and the unchanged CSV export both pass the current tests. Deleting the shipped-status condition or mishandling a `null` promised date would also escape coverage.
- Evidence: `test/badge.test.js:7–20` tests the helper only; `test/list.test.js:5–7` checks a paid order, and there is no export test.
- Fix: Cover the promised date and the following day, a non-shipped order, a shipped order with `null` promised date, and matching screen/CSV labels for an overdue order.
