### Findings

1. **[P1] A permanent rejection is recorded as an acknowledgement.** [deliver.js:17](case/head/src/delivery/deliver.js:17) marks both `ok` and `permanent` results. After a 400 response, the supported [admin redelivery](case/head/src/admin/redeliver.js:4) will skip the send and report `"delivered"`, even if the endpoint has since been fixed. Record acknowledgement only for `ok`.

2. **[P1] A worker restart loses acknowledgement state.** [store.js:1](case/head/src/delivery/store.js:1) keeps acknowledgements in a process-local `Set`, while the [queue contract](case/head/src/queue/worker.js:3) explicitly permits a job to be handed out again after the worker process dies. The next worker can therefore send an already acknowledged message again. The store is pre-existing, but the change does not fulfill the new requirement across this supported flow. Durable state is needed, and the crash window between endpoint acceptance and recording it also needs a delivery protocol capable of meeting the stated “never sent again” guarantee; the idempotency key alone does not prevent another HTTP send.

3. **[P1] The attempt limit resets on each queue delivery.** [deliver.js:11](case/head/src/delivery/deliver.js:11) counts attempts only within one invocation. If a worker dies after sending one or more temporary attempts, a subsequent worker starts at one and can send three more, exceeding three attempts for the message. Track attempts across job handoffs in durable state, with a defined treatment of an attempt interrupted by process death.

4. **[P2] The final temporary response incurs an unnecessary eight-second wait.** [deliver.js:14](case/head/src/delivery/deliver.js:14) sleeps after the third attempt even though there is no next attempt. This delays returning the final result and holds the queue handler unnecessarily. Sleep only when another attempt remains.

### Tests and design

The tests cover the basic result sequences but do not assert the backoff calls, permanent rejection followed by admin redelivery, or state across a worker restart. Those cases would expose the issues above. A restart test also needs to model the interruption between endpoint acknowledgement and local recording.

The changed delivery function groups the acknowledgement check, attempt limit, response-based retry decision, backoff, and final state update in execution order. Those rules are understandable together; no separate structural change is warranted beyond correcting their boundaries. The injected `sleep` is useful for testing delays, and I found no additional simplification supported by the inspected contracts.
