### Findings

1. **[P1] The promised day is marked delayed too early.** [badge.js:21](case/head/src/orders/badge.js:21) compares an instant with `now`. A date-only string such as `2026-03-20` parses as midnight UTC, so at `2026-03-20T09:00:00Z` the order is already labelled “Delayed”. The requirement says it must remain “Shipped” throughout the promised day. Compare calendar dates, with an explicit choice of timezone for the current date.

2. **[P1] CSV export never uses the delayed label.** [list.js:1](case/head/src/orders/list.js:1) switches only the screen to `badgeLabel`; [export.js:4](case/head/src/orders/export.js:4) still calls `statusLabel`, which always returns “Shipped” for shipped orders. Use the same date-aware label calculation for both paths.

3. **[P2] The new fallback and duplicate status map have no supported input.** [badge.js:1](case/head/src/orders/badge.js:1) duplicates the existing map, and lines 10–12 add missing/unknown-status and configurable-fallback behavior. The task states that both consumers receive orders through `fetchOrders()`, whose contract requires one of the five known statuses. The custom fallback has no production caller. Reuse `statusLabel` for the ordinary label and remove the unsupported fallback and its tests. Likewise, the `try/catch` around date construction is unnecessary for the contract’s string-or-null input.

### Tests

Add cases for the promised day and the following day, and verify both `renderList` and `toCsv` produce the same labels. Cover a shipped order with a null promised date and a non-shipped order with an earlier date; these distinguish the status and date rules. The current tests cover neither the boundary nor CSV integration, and two exercise inputs excluded by the contract.

### Design and scope

`badgeLabel` currently resolves a status and fallback, parses the promised date, then applies the shipped-and-overdue override. The latter two rules belong together as the date-aware label decision; the separate duplicated status map and configurable fallback add a second source of label rules without a supported need. `renderList` captures one `now` for its rows, which keeps its calculation consistent.
