# Reflection

Reflection looks back over a run for what the run itself could not see. Its first purpose is a leap: a change
that would make the skill work where the present approach cannot. Its second is the facts such a change must
stand on: what the run did, against what the user said and the record claims. Fresh agents do both; you wrote
the run, so you do neither. The one part you do is [the questions you answer yourself](#questions-you-answer-yourself).

This page has [the parts](#the-parts-and-the-step-each-hangs-on), [briefing a part](#briefing-a-part),
[what a part returns](#what-a-part-returns), [the questions you answer yourself](#questions-you-answer-yourself),
[what you do with a return](#what-you-do-with-a-return),
[the sources table as the digest](#the-sources-table-as-the-digest) and
[a retro on a use of this skill](#a-retro-on-a-use-of-this-skill).

Run only the parts the plan names. Each but the questions is an agent, so each is on the plan with its model before
the user accepts it; the plan writes "this session" for the questions, on its Agents line. A part never edits the
skill: it returns, and you act as this page says. A lens is any part but the audit and the questions. The record is
what the run has written so far: the sheet, the sources table, the plan with its log, the returns and the check's
files.

## The parts, and the step each hangs on

| Part | It looks for | Step, in Create and in Change | It runs when |
|---|---|---|---|
| evidence | the cause of each result of a check, by what the sessions did | 8; 9 | the check ran sessions |
| from zero | what a skill for this job would be, designed without the present one | 4; never | a new major version of a skill that exists, once |
| prior art | what other skills and guides do that this one lacks | 4; 5 | the skill's sources table has a row that is new, read in part, or whose version or date has changed; the first version reads its sources at step 2 and runs no lens |
| combinations | two or three changes that fail apart and may work together | 10; 9 | an audit of this run lists a thing dropped on opinion, or tested without a named partner |
| audit | where the run left the user's words, its own promises or its own rules | 10, before delivery; 9 | the plan's check ran sessions, or the plan named a lens; or, at [a correction](../SKILL.md#a-correction), it is the user's second since the plan |
| questions | what you believe about your own run, for the audit to check | 10, before the audit; 9 | with the audit of step 10 or 9, as [the section](#questions-you-answer-yourself) says |

A run whose check ran no session has no part of this page, but for the audit at the user's second
correction: a dry run's agent, a confirmer of marks and a reader of sources do not count. It still has its [close-out](plan.md#a-close-out). What the two early
parts return reaches the sheet as [a correction](../SKILL.md#a-correction).
A baseline's session does not count either. Change's step 9 holds Create's 7 to 10: a part
the table gives step 9 runs where Create's column says, inside it.

## Briefing a part

Brief each part as [every brief](critics.md#every-brief), with its row below as the role. Start the lenses of
one step together, and forbid each one the others' return files: a lens that has read another's return is no
longer a second view. Use no copy of this session as an agent; it holds what the part must not see.

| Part | It reads | It must not open, besides the other parts' returns |
|---|---|---|
| evidence | the skill; the record; the check's rule and marks; every session's outputs and transcript | nothing |
| from zero | the user's messages; the repository as it was before the skill; then the skill | the skill and its record, until its own sketch is written to its return file |
| prior art | the skill; the sources table; each source in a row that is new, changed or read in part, whole | nothing |
| combinations | the skill; the record; the plan's log; the audit's list of what was dropped | nothing |
| audit | the plan and its log; the file of the user's messages; this session's transcript, where the host keeps one; the run's files; the record; `questions.md`, after its tables are written | your state statement, `questions.md` and the log's `deviation` rows, until its own tables are written |

Before the audit starts, write a state statement from what you hold in context, opening no file: what was
asked, what was agreed, what is done, what is open, each as a numbered claim. It is the audit's last input but for `questions.md`.

## What a part returns

A lens returns at most five hypotheses, ranked, and marks its own top two. Each has:

```text
the change, in three lines at most
the result it would move, with the evidence and how sure it is: 1 the text says so, 2 an independent reader would agree, 3 it was seen
why the skill as it stands misses it, with file and line
the cheapest test that could refute it
its cost, marked as an estimate
the partner change without which it cannot work, or "none"
```

It ends with one line that says which hypotheses are judgement. It returns no verdict on the skill.

The audit returns tables, each row with a status and a place: every instruction and question of the user; every
promise you made; every claim of the state statement; every answer of `questions.md`, marked `holds`, `part` or
`does not hold`, with the place and what the run shows that the answer missed; everything dropped, and whether by a
rule written before the result or on opinion; every rule changed after a result was seen; every figure the record
gives, recounted. Then at most five findings, and what it could not read. It returns no verdict and no opinion of
what a finding does to one. One of its tables is the spend by requirement line, recounted, beside the lines the
user's messages weigh most.
A row of its table of the user's instructions and questions that the work does not meet goes into the result, as
[the result](../SKILL.md#the-result) says.

## Questions you answer yourself

This part is the one you answer yourself, because what you believe about the run is what the audit must check.
Before the audit starts, write your answers in `questions.md` in the run directory, one paragraph each, from what
you hold in context, opening no file, as a state statement is written; change nothing in it after. The audit holds
them against the files. It writes its other tables first, then opens `questions.md` and adds its table of the answers.
The part runs only with an audit the plan named at step 3 for step 10 in Create or step 9 in Change, and not on a
retro. The plan writes it on its Agents line as `questions`, with "this session" for its model.

1. What assumption is the whole approach built on, and what would show that the goal itself is wrong, not only the
   means?
2. Which belief about the result do you hold most firmly; what speaks for it and against it, and what other
   explanation fits the same facts?
3. What do you put the failures and the successes down to, and which of the causes were in your control?
4. Which figures in the record did you take without recounting them, and are any two compared in different units?
5. Which files, returns and outputs did you not open yourself, relying on a summary of them?
6. Where did a brief you wrote hand an agent your expected answer or your own reading?
7. How may your present state be shaping how you read this run: a long or summarised context, the latest results,
   haste near a limit, wanting the work to look finished, or wanting to agree with the user?

Which questions find most is judged across runs by the owner of this skill, not within a run. In the questions' row of the scorecard, a find is an answer that gave a point the plan took; its
`effect` is filled when a later run shows it.

## What you do with a return

- A finding of the audit is opened at its place. Confirmed, it is [a correction](../SKILL.md#a-correction), and
  where it touches a verdict you recompute the verdict as
  [handling a return](critics.md#handling-a-return) says. Its tables are trusted only when they hold, from before it
  opened them, the deviations the log already records.
- An answer of `questions.md` that the audit marks `part` or `does not hold` is one of the audit's findings and is
  handled as the audit's other findings are, and does not count toward its limit of five.
- Hypotheses are merged by the rule the plan wrote before any return came. A rule to start from: duplicates
  are merged with every source kept; none is dropped without a reason; disagreement between lenses is kept as
  written; the order is expected gain over cost.
- Show the user the merged list and, beside it, each lens's own top two. The user chooses. A hypothesis is never
  applied because a lens offered it: one that is chosen becomes requirement lines of a new plan, with its
  refuting test as that plan's check.
- Write the scorecard in the run directory, one row a part:

```text
part | model | tokens, and where the figure comes from | minutes | offered | confirmed or taken | only this part | read another part's return: yes or no | effect
```

  The row of the questions has no model or tokens, and carries the audit's mark of each answer by its number.

  `effect` stays empty until a hypothesis that was taken has been tested; then it is `held` or `refuted`.
  Taken is a choice and effect is a result. Keep the scorecards of a skill together in its record: the next
  run of a part is compared with the last.
- Close each run of a part with [a close-out](plan.md#a-close-out). A lens that has given nothing taken in
  two runs is left out of the next plan.

## The sources table as the digest

Prior art is dear to read and changes slowly. The sources table of step 2, kept in the skill's record with the
date each source was read and its version, is all that later versions need: a row read whole stands until its
source changes.

## A retro on a use of this skill

A session that used this skill on a skill is a run of this skill, and where it went wrong there is this skill's
next observation. A retro reads such a session after it ended. It runs when the user asks for one; the result
of every use says that it can.

1. The session is collected by entrust's [prepare-feedback](../../prepare-feedback/SKILL.md), which the user
   starts by name, with that session as its scope and this question: where did this skill's steps fail,
   mislead, or cost without a gain, each with its address. Where that skill is not installed,
   [hosts.md](hosts.md) says how a past session is read.
2. Two parts of this page then read the same session with the run directory it left, briefed as
   [briefing a part](#briefing-a-part) says: the audit, always, and evidence, when that use ran a check with
   sessions. The audit gets no state statement and reads that session's transcript. No other part runs on a
   retro.
3. What prepare-feedback and the two parts return is the observation of a Change to this skill, at its step 1; nothing is applied
   from a retro without that route.
4. Add to the scorecard one row for each part, and one for each judge that use started, from its run
   directory: the judge, its model, what it offered, what was taken, and `effect` when a later run shows it.
   The rows join the scorecards kept in this skill's record, in the repository that holds its source; a
   session that cannot write there leaves them in prepare-feedback's private folder and names the path in its
   result. What was read from the session stays private, as prepare-feedback's report rule says.
