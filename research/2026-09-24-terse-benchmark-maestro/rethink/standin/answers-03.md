# Question set 03: how the skills reach the reader's project

Each answer below is marked as one of three kinds:

- **Snapshot**: the files show it (file:line, paths relative to the snapshot).
- **Inferred**: my reading of the files; nothing in the snapshot shows it and I have not run it.
- **Owner decision**: what the README tells the reader.

I read only the snapshot and the run directory.

## (a) `npx skills add sharpdeveye/maestro`

**Snapshot.**

- `skills-lock.json` sits at the repo root and is committed; no line of `.gitignore` matches it.
  - It records `"version": 1` (`:2`) and 22 skills. Each has `"source": "sharpdeveye/maestro"`, `"sourceType": "github"` and a `"computedHash"` (the first entry is at `:4-8`).
  - The 22 are every skill that existed before 2.0. The extension then shipped "22 bundled skills" (`maestro-extension/CHANGELOG.md:40`), and the list includes the core `agent-workflow` (`skills-lock.json:14-18`).
  - The three missing ones (`/capture`, `/recap`, `/reflect`) arrived in 2.0.0 (`CHANGELOG.md:15-17`).
- `maestro-extension/CHANGELOG.md:11` says: "This fixes a bug where users using `npx skills add` received raw, unresolved templates." So the CLI installs the `SKILL.md` files as they are committed, with no build step.
- Nothing else in the snapshot names the skills CLI: no script, workflow or other document. I checked with grep for "skills add", "npx skills" and "skills-lock".
- The folders the CLI wrote into the Maestro checkout are not in the snapshot, because all ten provider folders are gitignored (`.gitignore:16-27`).

**Inferred.**

- **Where:** into the project it is run in. The lock file sits in the root of the project where the CLI was run, which here was the Maestro checkout itself.
  - The snapshot shows no install into a home directory (global install).
- **What:** every skill folder in the repo, which is 25 today, `agent-workflow` included.
  - The lock of 22, when 22 existed, is the evidence.
  - Whether `agent-workflow/reference/` comes along is not shown.
- **For which of the ten agents:** not shown. The snapshot has no list of the agents the CLI supports, so I don't know.

**Owner decision: what the README says.**

- Run `npx skills add sharpdeveye/maestro` in the root of the project you work in. It installs Maestro's skills into that project and writes `skills-lock.json` there.
- Install all 25 skills. Every command starts by invoking the core skill ("Invoke /agent-workflow", for example `diagnose/SKILL.md:12`).
- Name no agents for this route; the CLI chooses the agent folders. A reader whose tool the CLI doesn't cover uses the manual line in (b).
- Describe the project install only, not a global one. Maestro works per project: `/teach-maestro` is "Run once per project" (`teach-maestro/SKILL.md:3`), and `.maestro.md` and `.maestro/` live in the project.

## (b) The clone-and-build way

**Snapshot.**

- `npm run build` writes only inside the clone.
  - `ROOT` is the clone (`scripts/build.js:10`), and each provider folder is `path.join(ROOT, provider)` (`:73`).
  - `source/skills/` is copied into each folder unchanged (`:80`, using the plain recursive copy at `:27-44`).
  - The ten folders are gitignored as "generated by scripts/build.js" (`.gitignore:16-27`).
- Nothing in the snapshot says how to get those folders from the clone into another project.
- Nothing else uses the build's output. The extension and the MCP server bundle straight from `source/skills/` (`maestro-extension/scripts/bundle-skills.js:13`, `scripts/bundle-skills.js:13`).

**Owner decision.**

- **Default taken.** Clone-and-build is the contributor's way to check a change, not a reader's install route, and the README says so.
  - The contributor line is: edit `source/skills/`, run `npm run check`, then `npm run build`, then open an agent in the clone to try the change there.
  - Offering clone-and-build to readers in set 01, item 3, was a mistake. That was wrong.
- **Added: one manual line for readers.** Copy the skill folders from `source/skills/` into your agent's folder in your project, using the ten paths in `scripts/build.js:14-25` (for example `.claude/skills/`).
  - Reason: this is exactly what the build and the extension do (`scripts/build.js:80`; `maestro-extension/src/extension.ts:234-240`). It is also the one skill-files way that doesn't depend on a CLI command I have not run.

## (c) The extension and the MCP server

### Extension: confirmed, with three corrections

**Confirmed.**

- The extension starts on startup (`"onStartupFinished"`, `maestro-extension/package.json:32-33`).
- `activate` calls `autoInstallSkills` (`maestro-extension/src/extension.ts:38-39`).
- That writes each bundled skill as `<project>/<provider>/skills/<name>/SKILL.md` for all ten providers (`:197-208`, `:215-241`).
- The bundle is built from `source/skills/` when the extension is built (`maestro-extension/scripts/bundle-skills.js:12-13`, `:71`).

**Corrections.**

1. **Only each skill's `SKILL.md` reaches the project.** The bundler reads only `SKILL.md` (`maestro-extension/scripts/bundle-skills.js:71`), and the sync writes only `SKILL.md` (`extension.ts:240`). The seven reference files of `agent-workflow` are not copied, although its `SKILL.md` links to them (`agent-workflow/SKILL.md:66`, `:88`, `:110`, …).
2. **"The project" means the first workspace folder.** Nothing is written when no folder is open (`extension.ts:194-195`).
3. **The files are rewritten on every activation** (`extension.ts:236-240`). A reader's edits to the synced copies are gone at the next start.

**Also.** The extension adds the MCP server to the workspace config (`maestro-extension/src/adapters/mcp-config.ts:42-45`, `:49-75`). So an extension user's agent can also fetch the skills from the server.

### MCP server: confirmed

**Compiled into the package.**

- `build` is bundle plus esbuild (`mcp-server/package.json:11-12`).
- The bundler reads every `source/skills/*/SKILL.md` and the seven `agent-workflow/reference/*.md` files (`scripts/bundle-skills.js:76`, `:99-110`) into `src/generated/skills-data.ts`.
- esbuild bundles that into `dist/index.js` (`mcp-server/esbuild.config.cjs:9-11`), and the package ships `dist/` (`mcp-server/package.json:46-47`).

**Served on request, never copied.**

- Prompts, one per command (`mcp-server/src/prompts.ts:8-43`).
- The `maestro_run_command` tool, which returns a command's text (`tools.ts:154-217`).
- Resources for the core skill and the seven references (`resources.ts:7-56`).
- No code under `mcp-server/src/` writes a file: grep finds no `writeFileSync` or `appendFileSync` there.

**Its one write into a project is not a skill.** It writes `.maestro/`, meaning the decision log, the sessions folder and `.gitignore`, when the agent calls `maestro_write_decision` (`tools.ts:426-466`, via `packages/core/src/decisions.ts:42-61`, `:85-104`).
